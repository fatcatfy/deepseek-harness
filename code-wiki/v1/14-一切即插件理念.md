# "一切即插件"理念说明书

> 基于 DeepSeek Harness（DSH）仓库源码与官方架构文档的系统阐述

## 摘要

DeepSeek Harness 的核心设计哲学可以概括为一句话：**"没有特权核心"**——模型适配器、工具注册表、会话日志、Agent 循环本身，乃至 Web 服务器与桌面壳，都是同一棵 Cordis 插件树上的普通节点。本文从设计原则、形态分类、生命周期、通信机制、核心/扩展实现与工程价值六个维度，系统说明这一理念如何在代码、配置与运行时被贯彻，以及它为 agent 系统带来的结构性优势。

---

## 1. 理念总述

传统 agent 框架通常呈现"内核 + 扩展"结构：一个不可替换的循环引擎负责调度模型与工具，外围通过 hook 或回调暴露有限的定制点。DSH 彻底反转了这一假设：

- **Agent 循环是插件**——你可以挂载另一个 `AgentFactory` 实现，而现有的子系统（重试、压缩、计划模式）依然正常工作，因为它们只依赖 `dsh-agent` 声明的事件契约，不依赖具体驱动器。
- **会话日志是插件**——`SessionStore` 通过 `SessionPersistence` 接缝接入，JSONL 后端只是众多可能实现之一；你可以为云端、嵌入式设备或审计系统写新的持久化后端，而 agent-loop 的代码一行不改。
- **产品面是插件**——Web 服务器、浏览器客户端模块、Electron 主进程、SDK JSON-RPC 服务器，全部以 bundle/patch 的形式组合进同一棵树；`dsh-headless` 与 `dsh-web-app` 共享 `dsh-base` 的同一套核心，只在顶层换了几行配置。

这一理念的权威表述在 [architecture.md](../docs/architecture.md)：

> "There is no privileged core to patch: you extend dsh by mounting a plugin beside the others, and registrations are effects that unwind when their plugin unloads."

## 2. 设计原则

"一切即插件"不是口号，而是由以下八条可执行的工程原则支撑的：

### 2.1 注册即效应（Registrations are effects）

每一个对系统行为的贡献——注册一个工具、挂载一个提示词段、监听一个事件、添加一个模型适配器——都必须通过 `ctx.effect()` 或 `ctx.on()` 完成。效应的 disposer 逆序执行，fiber 卸载时自动清理。这保证了一棵树的任意子树可以被拆除而不留下 dangling state。

> 实现：[vendor/cordis/src/fiber.ts](../vendor/cordis/src/fiber.ts) `Fiber.effect()`；仓库加固：UNLOADING 期拒绝新效应、子 fiber 先拿 parent-owned disposer。

### 2.2 能力接缝三角色完整（A capability seam comprises three roles）

新增一个可替换能力，必须同时设计：
- **Service Definition**（声明接口，如 `ctx.llm`、`ctx.shell`）
- **Service Provider**（实现，如 `DeepSeekAdapter`、`bash-local`）
- **Consumer**（使用方，如 agent-loop、tool-bash）

只有一个角色不算接缝；换 provider 即换产品行为，但 Consumer 代码不受影响。

> 权威定义：[../docs/glossary.md](../docs/glossary.md)；实现样本：dsh-shell 的 request/spec split（[shell/src/index.ts](../packages/shell/shell/src/index.ts)）。

### 2.3 事件优先于接口变更（Plugins, not loop changes）

新行为应挂载到已记录的扩展点（`agent/pre-step`、`tools/execute`、`llm/stream`……），而不是修改循环代码。约一半子系统是循环事件的纯消费者，它们从不 import agent-loop 的实现。如果一件事需要改循环才能做，说明缺少一个扩展点，应该补事件定义，而不是打补丁。

> 扩展点总表：[architecture.md](../docs/architecture.md) "Where new behavior goes"（20+ 行映射）。

### 2.4 显式解析优于隐式默认（Explicit > implicit at package boundaries）

默认值填充与上限钳制是 owning implementation 里显式的 `resolve(request): Spec` 一步，绝不在 `run()` 里藏 `?? default`。这让配置行为完全可审计——`dsh --dump-config` 能打印出机器实际看到的每一行配置的来源。

> 样本：dsh-shell 的 `resolve()`（[shell/src/index.ts](../packages/shell/shell/src/index.ts)）、DeepSeek 配置的 `resolveAdapterOptions()`（[llm-deepseek/src/config.ts](../packages/llm/llm-deepseek/src/config.ts)）。

### 2.5 配置失败要响（Misconfiguration fails loud）

无法解析的 patch 文件、缺失的依赖引用、冲突的 isolate realm、不兼容的 peer 版本——全部在加载期抛出带标签的诊断，绝不静默跳过。这让"机器实际启动了什么"与"机器**拒绝**启动什么"都完全确定。

> 实现：`loadOptionalPatches`/`loadOverlayPatches`（[app-boot/src/index.ts](../packages/boot/app-boot/src/index.ts)）、`auditStartupEntries`、peer 版本准入（[compatibility-preflight.ts](../packages/boot/app-boot/src/compatibility-preflight.ts)）。

### 2.6 信任 TypeScript，验证在边界

类型化同进程边界不加运行时校验；校验只发生在 parser/config、模型 JSON、持久化文件、进程间与 wire 边界。这消除了大量无意义的防御代码，同时把真正的安全闸门放在系统边缘。

> 规则来源：[../AGENTS.md](../AGENTS.md) "Trust TypeScript at typed same-process boundaries."。

### 2.7 Source plane ≠ artifact plane

静态门禁（测试、类型检查、文档链接）经 tsconfig `paths` 解析到 `.ts` 源；运行时入口消费 built `lib/` 的必须显式声明。两者永不混用，防止"只在 built 树通过"的隐藏依赖。

> 说明：[../docs/development.md](../docs/development.md) "TypeScript project layout"。

### 2.8 模型可见 ⟺ 已日志（Model-visible means logged）

任何进入模型请求的内容都必须能从会话日志重建。这条不变量把"记忆"从运行时内存状态解耦为持久事件流——你可以 fork、resume、审计、重放，全部是对日志的操作，而不是对运行对象的操作。

> 实现：`deriveMessages()`（[core/session/src/index.ts](../packages/core/session/src/index.ts)）、`markAgentLoopRequest()`（[llm/src/call-config.ts](../packages/llm/llm/src/call-config.ts)）。

## 3. 插件的定义与分类

在 DSH 中，"插件"是一个运行时概念，涵盖从单一函数到完整应用的所有形态。按照组合层级，可分为五类：

### 3.1 基础插件（Cordis Plugin）

最小的可装载单元：一个实现 `Service` 的类，或一个带 `inject` / `apply(ctx)` 字段的函数。它在 `cordis.yml` 中占一行，通过 Loader 激活。

```ts
// 最小形态：一个函数
export function apply(ctx: Context) {
  ctx.effect(() => {
    const handle = setInterval(() => {}, 1000);
    return () => clearInterval(handle);
  });
}
```

> 框架定义：[vendor/cordis/src/registry.ts](../vendor/cordis/src/registry.ts) `isApplicable()`。

### 3.2 Library（库）

无插件表面的纯代码包，被其他包 import 使用，不单独装载。如 `dsh-brand`（branded 类型）、`dsh-timeout`。在文档体系中被分类为 `package-library`。

### 3.3 Bundle（组合包）

声明 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }` 的 npm 包。它本身不暴露新代码，而是把一组插件行和配置打包成可复用的层。`dsh-base`、`dsh-web-app`、`dsh-headless` 都是 bundle。

> 定义：[packages/util/package-manifest/src/types.ts](../packages/util/package-manifest/src/types.ts)。

### 3.4 Profile（运行剖面）

命名存储在 `$DSH_HOME/profiles/<name>/` 的组合：有序 bundle 清单 + 用户 patch。profile 决定**进程**启动时加载什么。shipped 模板：web、headless、sdk、sdk-minimal、acp。

### 3.5 Agent Preset（会话能力集）

在独立 scope + 内存 Loader 树中挂载的完整 Cordis entry 列表。它决定**每个 Agent（会话）**看到什么工具、提示词和技能。Host 进程共享一个 Agent loop；每个 Agent 只看到自己 preset 的 revision。

> 实现：[packages/preset/agent-preset-registry/src/mount.ts](../packages/preset/agent-preset-registry/src/mount.ts) `mountPreset()`。

这五层的关系：

```
Profile（进程级组合）
  └─ Bundle（可分发配置层）
       └─ Plugin（最小装载单元）
            └─ Service / Event / Effect（运行时贡献）

Agent Preset（会话级组合，与 Profile 正交）
  └─ 同一套 Plugin 形态，但在 isolate realm 中运行
```

## 4. 插件生命周期

DSH 插件的生命周期由 Cordis 框架管理，分为四个阶段：

### 4.1 装载（Load）

Loader 按 profile/bundle/patch 的层次 flatten 后，逐行 `import()` 插件模块、构造 fiber。`inject` 声明决定激活顺序：依赖服务可用后，插件才进入 setup。

### 4.2 初始化（Setup / Service.init）

`Service` 子类可选择实现 `async* [Service.init]()` generator——yield disposer 表示初始化步骤的可逆部分。`AgentPreset` 用此模式在构造后 yield `ctx.agentPresets.register(config)` 的 disposer。

> 实现：[vendor/cordis/src/service.ts](../vendor/cordis/src/service.ts)。

### 4.3 活跃（Active）

插件通过 `ctx.effect()` 注册提示词段、工具、事件监听器、适配器；通过 `ctx.on()` 订阅事件。所有注册都返回 disposer，或自动收集在 fiber 的效应列表中。这是插件"做功"的阶段。

### 4.4 卸载（Teardown）

当 patch 被移除、profile 切换或进程退出时，fiber 进入 `UNLOADING`：
- 新效应被拒绝（`INACTIVE_EFFECT`）
- 已收集的 disposer **逆序执行**
- 服务从 `ctx` 注销
- 监听器自动移除

这保证了热重载（HMR）的安全性：一个模块替换不会泄漏旧版本的监听器或定时器。

> HMR 实现：[packages/boot/hmr/](../packages/boot/hmr/)；`runExclusive()` 把模块替换、Include 刷新、配置变更序列化在同一队列。

## 5. 插件间通信机制

DSH 不提供"插件直接调用插件"的 API；所有交互通过两种中介完成：

### 5.1 服务依赖（Service Dependency）

插件通过 `static inject = ['tools', 'llm', 'sessions']` 声明所需服务。Cordis 在服务可用后才激活该插件；运行时通过 `ctx.tools` / `ctx.llm` 调用方法。这是**直接能力调用**的通道。

### 5.2 类型化事件（Typed Events）

服务间的**拦截、策略与观察**通过事件完成。事件声明经 TypeScript declaration merging 注册到 `Context.Events`，保证编译时类型安全。

五种 dispatch 模式（[cordis-primer.md](../docs/cordis-primer.md)）：

| 模式 | 语义 | 典型用例 |
|---|---|---|
| `emit` | 观察，无返回值 | `agent/status`（UI 更新状态指示灯） |
| `waterfall` | around-中间件，必须调 `next()` 委托 | `agent/pre-step`（改写或拒绝消息）、`tools/execute`（包装超时） |
| `serial` | 顺序执行，可 bail | `agent/turn-stopping`（按序询问是否续命） |
| `parallel` | 并发，全部完成 | `session/flush`（多个持久化后端并发刷盘） |
| `bail` | 顺序，首个非空值短路 | — |

### 5.3 Scope 过滤

同一进程内运行多个 Agent 时，`dsh-scope` 为每个 Agent 建立独立的 context filter。子代理的事件不会泄露到父代理的监听器，除非监听器显式注册在父 scope 链上。这让"一个进程同时承载多个会话能力集"成为可能。

> 实现：[packages/core/scope/src/index.ts](../packages/core/scope/src/index.ts) `scopeTarget()`。

### 5.4 会话日志作为共享总线

持久事件（`turn/*`、`tool/*`、`user/message` 等）既是模型记忆，也是插件间交换 durable 状态的媒介。compaction-basic 在 `agent/pre-step` 写 `compaction/start` 事件；todo 在工具 execute 中写 `todo/write` 事件；token-meter 重放日志计算用量——它们互不 import，只通过日志协作。

## 6. 核心功能的插件化实现

以下功能在传统框架中通常被视为"内核"，在 DSH 中全部是普通插件：

### 6.1 Agent 循环

- **契约包** `dsh-agent` 声明 `Agent` 接口与 `agent/*` 事件
- **实现包** `dsh-agent-loop` 提供默认驱动器 `ReactLoopAgent`
- 你可以写第三个包实现 `AgentFactory`，替换 `ctx.agentLoop`，而 `llm-retry`、`compaction-basic`、`goal-round-driver` 等消费者完全不受影响

> 文件：[packages/core/agent/](../packages/core/agent/)、[packages/core/agent-loop/](../packages/core/agent-loop/)。

### 6.2 会话持久化

- **Service Definition** `SessionPersistence`（抽象服务）
- **Provider** `session-persistence-jsonl`（本地 JSONL + zstd）
- 换云端存储只需实现 `SessionPersistence` 的 `create/open/stat/list/export`，挂载为新插件

> 文件：[packages/session/session-persistence/](../packages/session/session-persistence/)、[packages/session/session-persistence-jsonl/](../packages/session/session-persistence-jsonl/)。

### 6.3 模型调用

- **Service Definition** `LlmRuntime`（`ctx.llm`）
- **Provider** `llm-deepseek`（官方路由）、`llm-pi-ai`（多网关）
- **Consumer** agent-loop、compaction、session-title
- 新增 provider = 写适配器插件 + `registerAdapter()`，零代码方式可用 pi-ai 配置

> 文件：[packages/llm/llm/](../packages/llm/llm/)、[packages/llm/llm-deepseek/](../packages/llm/llm-deepseek/)。

### 6.4 工具注册表

- `ToolRuntime`（`ctx.tools`）是独立插件；agent-loop 只通过事件契约消费它
- 工具按 scope 分层（全局遮蔽、agent 作用域）；`guard()`、`restrict()`、`presentAs()` 全部是注册时 API

> 文件：[packages/core/tools/](../packages/core/tools/)。

### 6.5 Web 服务器与浏览器客户端

- `webserver`、`frontend-static`、`api-gateway`、`ui-chat`、`ui-conversation`……全是独立插件
- Web profile 与 headless profile 共享 `dsh-base`，只在顶层 patch 中插入/禁用行即可切换产品面

> bundle 对比：[packages/bundle/web-app/cordis.patch.yml](../packages/bundle/web-app/cordis.patch.yml) vs [packages/bundle/headless/cordis.patch.yml](../packages/bundle/headless/cordis.patch.yml)。

## 7. 扩展功能的插件化实现

DSH 的扩展不是"写钩子"，而是"写插件并挂载到正确位置"。

### 7.1 新增模型 provider

两条路径：零代码（pi-ai 配置）或写适配器插件（继承 `LlmAdapter`，`registerAdapter()`）。逐步手册：[adding-an-llm-adapter.md](../docs/cookbook/adding-an-llm-adapter.md)。

### 7.2 新增工具

实现 `ToolDefinition`（含 `execute`、`output.render`、`presentCall/presentResult`），在 `apply()` 中 `ctx.tools.register()`。模型自动看到 schema；Web UI 自动获得卡片（通过原始事件 + meta 派生）。手册：[adding-a-tool.md](../docs/cookbook/adding-a-tool.md)。

### 7.3 新增 UI 节点

注册 `ConversationNodeDefinition` + keyed renderer。`ui-chat` 的节点注册表就是插件树的一部分。见 [12-产品面](12-产品面.md)。

### 7.4 新增持久化后端

实现 `SessionPersistence` 接口，挂载为插件。adjacent migration 机制保证历史格式可读，新后端只负责当前版本的写入。

### 7.5 新增会话能力集

写一个 `agent-preset` 行，其 `config.plugins` 声明完整的 entry 列表。用 `isolate` realm 把 provider 与 consumer 关在同一作用域。示例：shipped presets（standard、ptc、minimal、cordis）。

### 7.6 运行时自修改

`cordis-host-runner` 提供 `ctx.dynamicCordisRunner`，让会话内代码动态定义和运行插件——但受限于 vm 沙盒、session-scoped、进程本地，且不能创建持久安装。这是"插件之插件"的极限实验。

## 8. 核心价值：灵活性、可扩展性、可维护性

### 8.1 灵活性（Flexibility）

同一套代码库可以产出五种产品面（CLI headless、Web、Desktop、SDK、ACP），不是通过 `#ifdef` 或条件编译，而是通过**组合不同的 bundle 和 patch**。`dsh-web-app` 在 `dsh-base` 之上插入浏览器行并禁用不需要的 agent 面行；`sdk-minimal` 完全不加载 `dsh-base`，自建一棵最小树。这种灵活性是数据层面的，不是代码层面的。

### 8.2 可扩展性（Extensibility）

扩展不需要改框架代码。新增能力 = 写插件 + 声明事件 + 注册服务 + 组合进 profile。因为接缝三角色完整，换 provider 即换产品行为：把 `ctx.fs` 从本地实现换成远程沙箱实现，Bash、PTY、LSP 全部跟着迁移——Consumer（tool-bash、tool-lsp）一行不改。

### 8.3 可维护性（Maintainability）

- **依赖方向清晰**：约一半子系统只消费事件，不 import 循环实现；包图经 `module-graph.md` 可视化，静态门禁校验依赖合法性。
- **变更影响可控**：修改一个插件的 config schema 不会导致未引用该插件的 profile 失效；waterfall 事件的监听器失败被遏制在 listener 级别，不拖垮整个 dispatch。
- **可审计**：`dsh --dump-config` 输出带来源注释的完整 YAML；会话日志是可重放的确定性证据链；每个持久化格式版本有相邻迁移链和 SHA-256 指纹。
- **可测试**：keyless 录制会话快照建立在对日志的纯函数重放上——不需要模型 key 就能回归测试 agent 行为。

### 8.4 可靠性（Reliability）

"注册即效应"带来可预测的 teardown：HMR、profile 切换、进程退出时，旧插件的资源被逆序释放，不存在"重启才能清理"的累积状态。崩溃恢复（resume）也得益于此——`interruptedTurnClosers` 为未完成的 turn 合成关闭事件，作为普通日志批次 append，不需要专门的恢复模式。

## 9. 与传统架构的对比

| 维度 | 传统"内核+扩展" | DSH"一切即插件" |
|---|---|---|
| Agent 循环 | 内核代码，打补丁或 fork | 普通插件，可替换 `AgentFactory` |
| 模型适配 | 配置文件切换路由 | 完整 provider 插件，可自定义序列化/重试/鉴权 |
| 工具系统 | 回调注册表 | 作用域注册表 + 五阶段执行管线 + 守卫链 |
| 持久化 | 内置格式 | 接缝接口，可换后端 |
| 新增能力 | 改内核或写 hook | 写插件，组合进 profile/preset |
| 产品面差异 | 条件编译或独立仓库 | 同一仓库，不同 bundle/patch 组合 |
| 崩溃恢复 | 专门恢复代码 | 日志操作 + 普通 append |
| 热更新 | 重启或部分重载 | HMR：模块替换 + 效应逆序清理 + 重新激活 |

## 10. 结语

"一切即插件"在 DSH 中不是营销用语，而是一套从框架层（Cordis 的 service/event/effect）、到架构层（capability seam 三角色、事件优先于接口变更）、到产品层（profile/bundle/preset 组合）、再到工程纪律（注册即效应、模型可见即已日志、fails loud）的完整设计体系。

它的最终效果是：**系统的复杂度不随功能增长而超线性膨胀**。每新增一个模型 provider、一个工具、一个 UI 节点、一个持久化后端，都只是往树上挂一个新节点——节点的内部可以任意复杂，但节点与树的关系永远是同一种简单契约。

这就是"一切即插件"的深层价值：不是让一切变得可插拔，而是让一切插拔的方式都相同。

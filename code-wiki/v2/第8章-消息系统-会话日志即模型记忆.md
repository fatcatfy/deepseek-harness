# 第8章 消息系统：会话日志即模型记忆

## 1. 本章导读

前几章我们攒齐了一台 Agent 机器的全部零件：Cordis 内核提供服务与事件（[第3章](./第3章-Cordis内核-服务依赖注入与上下文.md)、[第4章](./第4章-事件驱动-五路派发与三个事件域.md)），agent-loop 让模型转起来（[第5章](./第5章-Agent-Loop-让模型转动起来的引擎.md)），工具系统接上外部世界（[第7章](./第7章-工具系统-能力接缝与执行管线.md)）。但有一个根本问题我们一直绕着走：**对话本身存在哪里？**

本章回答它，而答案出人意料地简洁：DSH 里没有"存对话"这回事。存在的是一份事件溯源（event sourcing）的仅追加日志（append-only log），对话、工具调用、请求配置、乃至系统提示词，全部是日志里的事件；模型看到的 messages 数组只是这份日志的一个投影（projection）。打个比方：日志是底片，消息数组是每次冲洗出来的照片——照片可以重洗，底片只有一张。

学完本章，你应该能回答四个问题：

1. `SessionEventMap` 里的各种事件分别记录什么？为什么 system prompt 是一个"事件"而不是请求头里的一个字段？
2. surface（表面）是什么？为什么"模型看到的对话"和"用户看到的对话"是两个视图？压缩历史时，用户已经看过的旧消息为什么不会凭空消失？
3. "Model-visible means logged"（模型可见即已记录）这条不变量，靠哪些具体机制保证？
4. 新增一种事件类型，为什么通常不需要升级 `SESSION_FORMAT_VERSION`？

核心源码在 [packages/core/session/src/](../../packages/core/session/src/)（全部加起来约三千行）和 `packages/session/` 组。这是全书理念核心章之一，请给 3.3 节多留一点时间——surface 机制是 DSH 最精妙的一处设计。

## 2. 从一个问题出发

设想你写了一个最朴素的 Agent 聊天程序：

```ts
// 教学虚构：最常见的"内存 messages 数组"写法
const messages: Message[] = []
while (true) {
  messages.push({ role: 'user', content: await readUserInput() })
  const reply = await llm.chat(messages)
  messages.push(reply)
}
```

现在问三个问题。**进程崩了呢？** `messages` 随进程蒸发，用户聊了两小时的工作上下文一秒归零。**关掉明天重开呢？** 没有持久化，一切都得从头再来。**"刚才模型说的那段不对，回到三轮前重来"呢？** 数组只能向前 push，"回退"意味着你还得自己发明一套快照机制。

这三个问题的共同病根：**对话被建模成了可变状态**。可变状态天生只属于当下这个进程，崩溃、重启、回退对它都是灾难。你在数据库课上学过解法——append-only log（只许追加、不许改写的日志）：先写日志再做事，崩溃后重放日志即可恢复。数据库的 WAL（write-ahead log）靠它保证事务持久性。

既然你熟悉 WAL，先用一张对照表给本章定坐标：

| 数据库 WAL | DSH 会话日志 | 差异要点 |
|---|---|---|
| 先写日志再改数据页 | 先记事件再派发模型/工具 | 侧业变主业：日志不再是恢复用的影子，它就是对话本身 |
| 崩溃后重放到故障点 | 重放出完整对话（resume/fork） | "恢复"语义更强：能回到任意 seq 前缀重来 |
| checkpoint 推进检查点 | `session/flush` 屏障 + 策略 | 语义检查点：请求前缀落盘后才发网络请求 |
| 数据页另有正身 | 一切"当前值"都是投影 | todo、goal、inbox 无一自建状态 |

但注意一个方向性差异：WAL 记录的是**页的修改**，"数据"另有其地；DSH 的日志记录的**就是对话数据本身**，别处只有投影。这是"事件是一等公民"的准确含义，也是本章标题"会话日志即模型记忆"的由来——模型的记忆不是被"备份"到日志里，它从来就只存在于日志里。

DSH 把这个思想推到了极致：**整个对话本身就是日志**。不是"对话旁边配一本日志"，而是对话、以及产生对话的一切事实（请求配置、工具调用、重试、压缩、fork 切割点），全部且仅以事件形式存在于一份日志中。这份日志就是 `Session` 类（[packages/core/session/src/index.ts](../../packages/core/session/src/index.ts) L442），它对外的自我介绍写在模块头注释里（L1-L7）：

> Event-sourced session service: append-only session log, in-memory store, and the derived LLM message history. Persistence is a plugin concern (subscribe to `session/event`, drain on `session/flush`).

拆开读：事件溯源的会话 = 仅追加日志 + 内存 store + **派生**出来的 LLM 消息历史；持久化是插件的事。最后那半句藏着本章 3.4 节的主角——热路径不碰 I/O。

## 3. 正文

### 3.1 `SessionEventMap`：对话的词汇表

打开 [packages/core/session/src/types.ts](../../packages/core/session/src/types.ts)，L281 起是全章的主角：

```ts
/**
 * The merge-extensible, append-only source of truth for an agent interaction.
 * Message history is derived from this log. Every event is lossless JSON and
 * sequence numbers stay contiguous. Assistant attempt events embed their exact
 * compact raw streams so persistence stores one durable settlement per attempt.
 */
export interface SessionEventMap {
  'turn/start': { turn: number }
  // ……共 14 个核心成员，见 3.2 节全表
}
```

四个词定调。**merge-extensible**（可合并扩展）：插件能往里加新事件类型；**append-only**：事件一旦入日志永不改写；**source of truth**（唯一真源）：它就是全部事实，别处只有副本；**derived**（派生）：消息历史是算出来的，不是存的。

它怎么做到"可扩展"？靠 TypeScript 的声明合并（declaration merging）——你在[第3章](./第3章-Cordis内核-服务依赖注入与上下文.md)已经见过 Cordis 用它扩展 `Context` 接口。任何插件只要写一段：

```ts
// packages/compaction/compaction/src/types.ts（L17-L23，真实代码）
declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    'compaction/start': { compactionId: CompactionId; sourceCommandId?: CommandId; turn: number | null }
    // ……compaction/summary、compaction/end、compaction/prune
  }
}
```

`SessionEventMap` 就多了四个成员，压缩插件的事件从此与核心事件平起平坐：类型检查、`session.append()` 校验、持久化目录收录，一视同仁。生成文件 [packages/core/session/src/known-event-types.ts](../../packages/core/session/src/known-event-types.ts)（L22-L82）枚举了本仓库全部已知事件——`KNOWN_SESSION_EVENT_TYPES` 共 59 个条目，其中压缩、审批（`approval/*`）、反馈（`feedback/*`）、待办（`todo/write`）等大半都是插件合并进来的。核心与插件的边界在这里是模糊的，而且是有意模糊的。

再看每条日志长什么样。`SessionEvent<T>`（types.ts L493-L516）：

```ts
export type SessionEvent<T extends SessionEventType = SessionEventType> = {
  [K in SessionEventType]: {
    type: K
    seq: SessionSeq        // 单调递增序号
    time: number            // epoch 毫秒
    data: SessionEventMap[K]
    ignorable?: true       // 未知读者可安全跳过的标记，见 3.6 节
  } & (K extends SurfaceEventType ? SurfaceIntent<K> : { surfaceOp?: never; sourceEventSeqs?: never })
}[T]
```

注意这是一个映射类型套交叉类型——**真正的可辨识联合（discriminated union）**，而不是"独立的 type 联合 + data 联合"。所以 `switch (event.type)` 直接窄化 `event.data`，不需要任何类型断言；而最后那个条件交叉意味着 `surfaceOp` / `sourceEventSeqs` 字段**只允许出现在五类 surface 事件上**，编译器在 `session.append()` 调用点就替你把关。

还有一条贯穿全仓库的编码纪律在此处显形：**可合并扩展的联合禁止 `assertNever`**。封闭联合的 switch 以 `assertNever` 收尾（让新增变体变成编译错误）；但 `SessionEvent` 的变体会随插件增长，未知变体是**合法的运行期值**——所以处理已知 case 后必须在 `default` 里放行。你会在 `deriveEventMessage`（surface.ts L147-L150 的注释直说"Merge-extensible union: no assertNever here"）和第 4 章讲过的派发分发里反复看到这个模式。判断一个联合该用哪种收尾，先问它归谁所有：编译期封闭的归 `assertNever`，运行期开放的归文档化的 `default`。

落到磁盘，JSONL 后端每行一条事件（[docs/subsystems/session.zh.md](../../docs/subsystems/session.zh.md) L761）。下面是一段示意（简化后的形态，非真实抓取）：

```jsonl
{"type":"turn/start","seq":0,"time":1760000000000,"data":{"turn":1}}
{"type":"step/start","seq":1,"time":1760000000030,"data":{"turn":1,"step":1}}
{"type":"request/header","seq":2,"time":1760000000032,"data":{"header":{"config":{...}},"reason":"initial"}}
{"type":"system/message","seq":3,"time":1760000000033,"data":{"turn":1,"step":1,"message":{...}},"surfaceOp":"append"}
{"type":"user/message","seq":4,"time":1760000000040,"data":{"role":"user","id":"u-1","source":{...},"content":[{"type":"text","text":"帮我修一下挂掉的测试"}]},"surfaceOp":"append"}
{"type":"assistant/message","seq":5,"time":1760000001500,"data":{"turn":1,"step":1,"message":{...},"stream":[...],"usage":{...}},"surfaceOp":"append"}
```

`seq` 的连续性是一条硬契约：`seq = log.length`（index.ts L676-L679 的 getter 注释直接称之为 "the `seq = log.length` contiguity contract"）。日志里第 n 条事件的 seq 必然是 n——seed 校验（index.ts L572-L574）和 surface 折叠（surface.ts L518-L520）都据此拒绝任何跳号。这让"日志位置"成为全系统通用的寻址语言：后面你会看到 replace 引用它、投影水位线引用它、fork 切割点也引用它。

顺带澄清一个容易混淆的邻居：`SessionHeader`（types.ts L94-L131）——格式版本、会话 id、创建时间、cwd、fork 血统（`parentSession` / `isSeeded`）、subagent 委托深度（`delegationDepth`）、agent 预设名（`agentPreset`）。它是持久化元数据，**故意不进事件日志**：`Session.header` 的 JSDoc（index.ts L455-L459）说得很直白——"it is a storage concern, not replayable conversation state"（它是存储关注点，不是可重放的对话状态）。日志回答"发生了什么"，header 回答"这是谁、以哪种格式、在什么血统下发生"；fork 时两者一起复制，但校验与持久化路径各自独立。还有一个细节顺便记住：`delegationDepth` 持久化的理由（types.ts L118-L123）是"重启续聊时，只在运行期记的深度会把子会话重置成顶层"——**只有落盘的状态才能在重启后原样回来**，这条朴素原则在本章会反复回响。

### 3.2 事件全表：一次对话由哪些事实构成

核心事件共 14 类。我把它们按功能分组，标注各自载荷——这是本章主干，建议精读：

| 事件 | 载荷（data） | 性质 |
|---|---|---|
| `turn/start` | `{turn}` | 仅日志 |
| `turn/end` | `{turn, reason: TurnEndReason}` | 仅日志 |
| `step/start` / `step/end` | `{turn, step}` | 仅日志 |
| `user/message` | **data 即 UserMessage 本体** | surface |
| `developer/message` | `{turn, step, message, headerSeq?}` | surface |
| `system/message` | `{turn, step, message: SystemMessage}` | surface |
| `assistant/message` | `{turn, step, message, stream, usage?, interrupted?}` | surface |
| `assistant/attempt` | `{turn, step, stream}` | 仅日志 |
| `tool/call` | `{turn, step, callId, name, arguments}` | 仅日志 |
| `tool/result` | `{turn, step, message: ToolResultMessage, error?, meta?}` | surface |
| `request/header` | `{header: EpochHeader, reason, startsSeries?}` | 仅日志 |
| `request/context` | `RequestContext` | 仅日志 |
| `session/end-seed` | `{inherited?: true}` | 仅日志 |

逐个讲值得注意的细节：

**轮次与步骤边界。** 一个 turn（轮次）= 模型拿到输入后到它彻底干完；一个 step（步骤）= 一次模型调用加它请求的工具执行。`turn/end` 的 `reason` 来自 `TurnEndReasonMap`（types.ts L201-L229）——一个同样可合并扩展的求和类型，七个成员：`completed` / `aborted` / `blocked` / `error` / `max-tokens` / `interrupted` / `forked`。后两个是"事后补记"：`interrupted` 是 agent-loop 恢复时给崩溃孤儿轮次补的闭合标记（循环从不实时发出它），`forked` 是 fork 种子构造时给源会话仍开放的轮次合成的闭合标记。崩溃不删除已记录的事件，只补一个"这一轮没能正常结束"的说明。看它的真实形状（节选）：

```ts
// packages/core/session/src/types.ts（L201-L229，节选）
export interface TurnEndReasonMap {
  completed: { kind: 'completed' }
  /** A cancellation request interrupted the live turn. */
  aborted: { kind: 'aborted'; reason: TurnEndCancelCause }
  blocked: { kind: 'blocked' }
  /** The turn failed. `error` is always a structured failure: the `LlmError`
   * facts verbatim, or `{ message, code: 'UNKNOWN' }` flattened from any other error. */
  error: { kind: 'error'; error: LlmFailure }
  /** At least one step reached its output-token ceiling, even if a plugin continued the turn. */
  'max-tokens': { kind: 'max-tokens' }
  interrupted: { kind: 'interrupted' }
  forked: { kind: 'forked' }
}
```

两处细节值得咀嚼。其一，`max-tokens` 的注释：**只要轮次里有任何一步达到输出上限，整个轮次就以 `max-tokens` 结束**——哪怕插件随后让轮次继续，"截断发生过"这个事实优先于"最终完成了"。这是审计思维的典型体现：结束原因记录的是"发生了什么"，不是"你希望怎么解释它"。其二，`error` 字段永远是结构化的 `LlmFailure`——要么原样保留 `LlmError` 的事实，要么把任意其他错误压平成 `{ message, code: 'UNKNOWN' }`。日志里不留"只有一串字符串"的错误，重放与统计才能机器可读。

**`user/message`：data 就是消息本体。** 注意它和别的事件不同——不是 `{turn, step, message}` 的包装，`data` 本身就是 `UserMessage`（含 `role`/`id`/`source`/`content`）。人类直接输入、`agent.inject()` 合成的上下文（文件变更通知、子目录 AGENTS.md、技能内容、定时任务提醒……）、goal 续轮，三种来源**共用这一种事件**，靠 `source` 字段区分；三者都原样投影 `content`。这是"注入上下文也是模型可见输入，所以也必须入日志"的直接体现。`source` 的类型是 `MessageSourceMap`（[packages/llm/llm/src/message.ts](../../packages/llm/llm/src/message.ts) L110-L115）——又一张可合并扩展的表：`user`、`model`、`tool`、`system-prompt` 四个核心 kind，每个生产方在自己的模块里声明自己的 kind，**没有共享的万能 `plugin` kind**。读者对未知 kind 落入默认分支放行。换句话说，连"这条消息是谁塞进来的"这个归因问题，答案也在类型系统里以同一套声明合并模式管理着。

**`developer/message`：增量会话变更。** 典型场景是运行中工具增删：内容块是 `tool-addition` / `tool-removal`。有个精巧的约束（surface.ts L194）：只要内容含 `tool-addition`，就必须带 `headerSeq` 指向定义该工具的那条更早的 `request/header`——工具定义不复制进 developer 消息，而是引用历史快照，校验器（`assertDeveloperHeader`，surface.ts L368-L395）会确认该 header 里恰好有一个同名且定义完整的工具。

**`system/message`：system prompt 是 surface 节点 0，不是请求头字段。** 这是最反直觉的一条。`EpochHeader`（types.ts L240-L251）里只有调用配置和工具 schema，`system` 字段被声明为 `never` 并标注 `@persistenceReserved`——**禁止**把系统提示词塞进请求头。渲染后的 system prompt 以 `system/message` 事件进入日志，第一条被追加为 surface 的第 0 号节点，位于本步第一条 `user/message` 之前。为什么？因为 system prompt 会变（提示词模板、注入的上下文都会演进），而"模型在第 n 步看到了什么系统提示词"是重建第 n 次请求所必需的事实——事实就该进日志。对比一下你在[第9章](./第9章-上下文工程-一次请求里塞了什么.md)会看到的：每次请求的上下文组装是临时的，但组装结果中模型可见的部分全部落了日志。

**`assistant/message`：内嵌完整定时流。** 它不只存最终文本！`stream: AssistantStreamRecord[]` 把模型原始输出流（压缩但不拼接 delta 边界）逐条持久化，`usage` 挂在旁边——模型输出与计费证据一起入日志，没有独立的 usage 记录。取消场景的处理见 L341-L349 的 JSDoc：中途取消的轮次把已送达的文本/推理前缀定稿为一条 `interrupted: true` 的 `assistant/message`，未派发的工具调用不会出现；完全没流出内容的取消轮次则没有任何 assistant 事件。

**`assistant/attempt`：失败尝试的诚实记录。** 一次没产生 surface 消息的模型尝试——失败、重试、取消、流错误——把原始流记入 `assistant/attempt`。关键语义是"保留原始流但**不伪造模型可见历史**"：一轮内前 4 次尝试都失败、第 5 次才成功时，模型下次看到的对话里不会凭空多出 4 条半截 assistant 消息，但 4 次失败的完整证据（含 provider usage）都在日志里。每个 attempt 恰好对应一条 `assistant/message` 或 `assistant/attempt`（"one durable settlement per attempt"，types.ts L279）。

**`tool/call` + `tool/result`：配对与分工。** `tool/call` 记录模型请求的工具调用，`arguments` 是**模型产出的未解析原始 JSON 字符串**——不 parse、原样存，审计时能看到模型到底说了什么。`callId` 把它和 `tool/result` 配成一对。注意分工：`tool/call` 是仅日志事件（调用块已经内嵌在 assistant 消息的 content 里了），`tool/result` 才是 surface 事件——**结果**是模型下次要看到的输入。`tool/result` 的 `meta` 字段是工具私有的 JSON 展示载荷（core 不理解它的结构，产出工具自己读写，比如 `dsh-tool-fs` 把结果时上下文 diff 放这里）；`error` 在模型内容之外，仅当消息 `isError: true` 才允许携带（surface.ts L212-L219 强制）。

**`request/header`：完整请求头快照。** "下一次请求"的完整信封——call config、adapter 提供的默认值标记、已组装的工具 schema。`reason` 四种（types.ts L273）：`initial`（新对话第一条）、`resume`（进程重启或 fork 后、日志已有 header 时的第一问）、`change`（请求变了）、`series`（header 没变但显式开启新消息序列）。重建请求头 = 取最新快照（`foldRequestHeader`，request-header.ts L63-L69）。

**`request/context`：路由元数据，仅变化时记录。** provider、model、`contextWindow`、`systemPromptUpdate`——路由的容量与能力说明。它不参与请求重建，只在变化时追加一条（agent.ts L660-L666 逐字段比较后才决定写入）。与 `request/header` 的分工：header 是"请求输入是什么"，context 是"这次路由到了哪、容量多大"。

**`session/end-seed`：fork 的切割标记。** 日志里继承前缀与本会话自有历史的分界线。`{inherited: true}` 形态的标记只有 `Session` 构造器和 `buildForkSeed` 可以创建（types.ts L416-L418 明说：append 不拒绝其他写入者，但插件若自己写一条，会静默把它之前的所有实时事件错划成种子历史）。第 11 章讲 fork 时它会再登场。

把 14 类事件拼成"一个真实步骤"，次序如下（每一跳的写入点都标了源码位置，你可以按图索骥地读 agent-loop）：

```
turn/start            agent.ts L305
  step/start          agent.ts L329
    request/header    agent.ts L620-L633（步内派发前）
    request/context   agent.ts L660-L666（仅路由变化时）
    system/message    agent.ts L417（首步：surface 节点 0）
    user/message      agent.ts L421
    assistant/message agent.ts L522（流结算后）
      tool/call       tool-calls.ts L264
      tool/result     tool-calls.ts L282
    （工具结果回流 → 可能再来一次模型调用，即下一步）
  step/end            agent.ts L356
turn/end              agent.ts L385
```

注意两处"反直觉的晚"：`tool/call` 在 `assistant/message` **之后**（先有流结算的 assistant 消息，才谈得上派发其中请求的工具）；`system/message` 不必每步出现（首步追加为节点 0，后续步骤复用它；提示词变化时按路由能力改写头部或追加后续系统节点，见 types.ts L318-L329 的 JSDoc）。这张次序图就是 3.4 节检查点策略的"何时该 flush"地图：每次进入 `llm/stream` 前，图中它之前的所有事件都必须已落盘。

### 3.3 Surface：模型视图的投影接缝

现在到了全章最难、也最精彩的部分。问题：日志里有 59 种事件，但模型请求的 `messages` 数组只该有五种 role 的消息——**哪些事件变成消息、以什么顺序变？**

DSH 的回答分两层。第一层，划定资格：只有五类事件产生 LLM 消息、可进入有序 surface：

```ts
// packages/core/session/src/types.ts（L439-L444）
export type SurfaceEventType =
  | 'system/message'
  | 'developer/message'
  | 'user/message'
  | 'assistant/message'
  | 'tool/result'
```

`turn/start`、`assistant/attempt`、`tool/call`、`request/header`……全部出局。它们是结构信息和审计证据，不是对话内容。判断函数是 `isSurfaceEligibleType`（surface.ts L63-L65）。

第二层，声明入会方式：每个 surface 事件必须携带 `surfaceOp`，声明自己如何加入 surface：

```ts
// packages/core/session/src/types.ts（L462-L464）
export type SurfaceOp =
  | 'append'
  | { op: 'replace'; startSeq: SessionSeq; endSeq: SessionSeq }
```

`append` 是尾部追加，普通消息的常规路径。`replace` 是**替换**：本事件替换 surface 上 `startSeq` 到 `endSeq`（闭区间）的现有节点。谁在用 replace？压缩插件——把几十条旧消息概括成一条摘要消息时，摘要以一条 `user/message` 事件入日志，`surfaceOp` 声明替换被概括的节点区间。另外 `sourceEventSeqs` 字段要求引用"我派生自哪些更早的事件"；replace 的 `sourceEventSeqs` 必须完整覆盖被遮蔽的所有节点（surface.ts L361-L364）。这个字段的设计里藏着一次类型层面的例外处理，值得看原文（types.ts L470-L478）：

```ts
export type SurfaceIntent<T extends SurfaceEventType = SurfaceEventType> = {
  surfaceOp: SurfaceOp
} & (T extends 'assistant/message' ? {
  /** Assistant messages embed their provider stream instead of citing source events. */
  sourceEventSeqs?: never
} : {
  /** Complete non-empty set of known earlier source-event seqs. */
  sourceEventSeqs?: SessionSeq[]
})
```

`assistant/message` 被类型系统**禁止**引用来源事件——它的证据是内嵌的原始流，不需要也不应该再引用别的节点。一个 `never` 就把"assistant 例外"从注释升级成了编译期契约（运行期同样拒绝，surface.ts L335-L337）。

这里请停一下，想一个严肃的问题：**replace 之后，旧事件去哪了？**

答案：哪也没去。日志是 append-only 的，replace 只在 **surface 投影**里遮蔽（shadow）旧节点——旧事件还在日志里，一动不动。surface 是"哪些事件节点当前模型可见"的有序列表，由 `SurfaceManager`（surface.ts L612）增量维护。这就引出全章核心图景——**两层视图**：

```
事件日志（append-only，全部事实，永不改写）
   │
   │  foldSurface() 按 surfaceOp 重放
   ▼
surface 节点序列（当前模型可见的有序事件，如 [seq3, seq4, seq5, seq9]）
   │                                    │
   │ deriveMessages()                   │ isAppendSurfaceEvent() 过滤
   ▼                                    ▼
模型视图（messages 数组）          人类视图（transcript）
 replace 会遮蔽旧节点                只看追加来源的事件
 → 压缩后旧消息"消失"               → 压缩后旧消息仍在
```

用个比喻：这本账本不许涂改，但可以在旧账页上贴一张更正条，声明"本条替代第 3 至 8 笔"。翻账本看**当前结论**的人（模型）顺着更正条读出新结论；想看**完整流水**的人（用户）逐页翻原始记录，更正条拦不住他。`isAppendSurfaceEvent`（surface.ts L89-L93）就是"这条是原始记录而非更正条"的判据，其 JSDoc（L80-L87）写得很清楚：模型可见的 surface 会故意遮蔽替换概括的范围，用它做人类 transcript 是错的——"a landed replacement would erase conversation the user already saw"（落地的替换会抹掉用户已经看过的对话）。

为什么值得这么大费周章地维护两个视图？因为**模型需要省 token，用户需要完整历史**，两者的正确性标准根本不同。第 10 章讲压缩时你会看到这套机制的完整用法；这里先记住结论：**压缩对模型是"忘掉细节"，对用户是"什么都还在"**。

replace 的校验相当严格，都在 `planSurfaceEvent`（surface.ts L510-L547）里：区间端点必须是当前 surface 节点（`replacementRange`，L415-L435）；`tool/result` 的替换只能改自己一条消息的 content（`assertToolResultRewrite`，L456-L485）；surface 第 0 号节点若承载 system prompt，只允许被一条恰好覆盖它单节点的 `system/message` 改写（`assertSystemHeadRewrite`，L493-L507）——系统提示词的"根"地位受保护，但后续系统节点是普通历史，压缩可以遮蔽。

看一次具体的压缩替换怎么走（载荷为示意，规则照抄源码）。假设当前 surface 节点序列是：

```
[seq3(system) seq4(user) seq5(assistant) seq7(tool/result) seq8(user) seq10(assistant)]
```

压缩插件想把 seq4 到 seq8 这段概括成一条摘要。它先追加仅日志的 `compaction/summary`（记录摘要内容、被遮蔽区间、以及摘要模型调用的完整证据——provider、model、usage，"哪台模型写的这份摘要"有持久答案），紧接着追加真正上 surface 的替换事件：

```jsonl
{"type":"user/message","seq":21,"time":1760001000000,"data":{"role":"user","id":"u-9","source":{...},"content":[{"type":"text","text":"（此前对话的摘要）……"}]},"surfaceOp":{"op":"replace","startSeq":4,"endSeq":8},"sourceEventSeqs":[4,5,7,8]}
```

`foldSurface` 重放到 seq21 时：先在当前节点列表里定位 startSeq=4、endSeq=8 的区间下标，确认两个端点都是当前节点；`sourceEventSeqs` 必须完整覆盖 [4,5,7,8]（缺一个即拒绝，surface.ts L361-L364）；校验通过后 `splice` 把这四项换成 seq21 一项（`applySurfacePlan`，L563-L585），`replaceGeneration` 与 `contentGeneration` 各自加一。之后：

```
模型视图 surface：[seq3(system) seq21(摘要) seq10(assistant)]     ← 下次请求的 messages
人类视图 transcript：追加事件流照旧包含 seq4/5/7/8 的原文          ← 用户界面不变
```

那两个 generation 计数器（`SessionSurface`，surface.ts L245-L252）不是摆设：`deriveMessages()` 的缓存靠 `contentGeneration` 失效（index.ts L860-L864），纯尾部增长时 O(新节点) 追加，任何替换后整体重建——消费方因此能廉价区分"对话正常变长"与"历史被改写"这两种完全不同的世界。

还有一类特殊的投影：**插件拥有的消息投影**（`SessionMessageProjection`，surface.ts L35-L47）。它解决另一类需求——**改变现有消息的内容而不改节点成员、不改消息身份**。真实案例是 image-offload（图片挪出）：把旧消息里的大图片替换成占位文本，消息还是那条消息，内容变了。插件经 `SessionStore.registerMessageProjection`（index.ts L938-L946）注册一个纯函数解释器，输入事件和历史上下文，输出按原事件 seq 索引的新消息。注意它与 replace 的分工：replace 是**换掉节点**（成员变化），projection 是**改写节点内容**（成员不变）。压缩摘要用 replace，图片挪运用 projection。有一个必须存在的解释器清单：`MESSAGE_PROJECTION_EVENT_TYPES`（known-event-types.ts L85-L87），目前只有 `image/offload` 一员——加载日志时若缺解释器，折叠直接拒绝（surface.ts L529-L531），不静默降级。

最后，`foldSurface(events, projections)`（surface.ts L594-L609）是纯函数版：给一段完整日志，重放所有 surfaceOp，返回当前节点序列 + 替换历史 + 投影消息表。`SurfaceManager` 是增量版，被 `Session` 持有为唯一 owner（index.ts L445 注释："Single incremental owner of surface acceptance and projection state"）。浏览器端的 Web 客户端也复用这份代码（surface.ts 文件头注明 browser-safe），离线重建与在线推导走同一套规则。折叠器对插件事件的处理也值得一瞥（`surfaceOpOf`，surface.ts L301-L327）：未知且标了 `ignorable` 的事件，其元数据原样保留、不影响 surface；而一个**非** surface 类型若试图携带 `surfaceOp` 或 `sourceEventSeqs`，直接抛错——surface 资格由 `SurfaceEventType` 集合静态划定，携带字段冒充不了成员。

### 3.4 写入路径：`Session.append()` 与持久化屏障

事件怎么进日志？`Session.append()`（index.ts L718-L769），分四步：

```ts
// packages/core/session/src/index.ts（L718-L769，节选）
append<T extends SessionEventType>(
  type: T,
  data: SessionEventMap[T],
  ...opts: T extends SurfaceEventType ? [opts: SurfaceIntent<T>] : []
): SessionEvent<T> {
  const dataSnapshot = snapshotJsonValue(data)          // ① 一次遍历：读取+校验+复制
  if (dataSnapshot === undefined) {
    throw new Error(`session event "${type}" carries non-JSON-serializable data`)
  }
  // …surface 元数据同样 snapshot…
  const event = deepFreeze({
    type,
    seq: SessionSeq(this.log.length),                  // ③ 连续性契约
    time: Date.now(),
    data: dataSnapshot,
    ...
  } as unknown as SessionEvent<T>)
  validateSessionEventData(event, ...)                  // ② 载荷校验
  this.surfaceManager.validateNext(event as SessionEvent) // ② 先计划后入 log
  // …④ 发布…
  this.log.push(event as SessionEvent)
  ...
}
```

**① `snapshotJsonValue(data)`：一次遍历完成读取、校验、复制。** 这个设计值得细品。它不是"先 JSON.stringify 验一下再 structuredClone 存一份"，而是一趟遍历边读边验边拷。为什么？JSDoc（L710-L712）给了答案：一个带状态的 getter 可能在校验时返回一个值、存储时返回另一个值。一次遍历保证"校验过的就是存进去的"。非无损 JSON（BigInt、循环引用、稀疏数组、Map/Set/Date……）在写入点抛错——坏事件绝不入日志（"a bad event fails at the append site rather than later during a backend flush"，L712-L714）。

**② 候选先计划、后入日志。** `validateSessionEventData` 校验载荷局部不变量（header 无 `system` 字段、空 tools 省略、developer 与角色一致等，surface.ts L166-L220）；`SurfaceManager.validateNext` 把候选事件的 surface 迁移**先计划出来**（pendingPlan），等 `log.push` 之后才真正应用（surface.ts L637-L646 与 `_processDelta` L681-L696 的配合）。失败时 surface 状态零污染——不会出现"日志没写进去但 surface 已经改了"的分裂。

**③ seq 与冻结。** `seq = log.length`、`time = Date.now()`、`deepFreeze` 深冻结，推入数组。返回值是入日志的那份快照，调用方手里还捏着的可变输入永远不会污染日志。

**④ 热路径不碰 I/O。** 注意 `append` 里没有任何 `await`、没有任何写盘。持久化在哪？在 Cordis 事件层（index.ts L38-L84 声明合并进 `Context`）：

- `session/created` / `session/disposed`：会话进出的生命周期通知；
- `session/event`：**提交后的 fire-and-forget 追加流**——监听器快照在 log push 之前解析、回调在 push 之后执行；观察者失败按 listener 遏制（记 warn 日志），绝不让已提交的 append 反悔（L665-L674 的 JSDoc）；
- `session/flush`：**awaited parallel 持久性屏障**。持久化插件监听它，把异步缓冲的事件真正刷盘。

"按 listener 遏制"具体长这样（index.ts L398-L416，`session/event` 与 `session/disposed` 共用）：

```ts
function invokeContainedSessionObservers(ctx, name, id, args, callbacks): void {
  for (const callback of callbacks) {
    try {
      const returned: unknown = callback(...args)
      void Promise.resolve(returned).catch((error: unknown) => {
        ctx.logger.warn(`session "${id}": ${name} listener rejected: ${String(error)}`)
      })
    } catch (error: unknown) {
      ctx.logger.warn(`session "${id}": ${name} listener threw: ${String(error)}`)
    }
  }
}
```

每个监听器单独 try/catch，同步抛错与异步拒绝都只记一条 warn，循环照常走完。这与[第4章](./第4章-事件驱动-五路派发与三个事件域.md)讲的原生 `ctx.emit` 形成对照：`Array.map` 式派发里一个监听器抛错会断送后面所有监听器；而 `session/event` 播报的是"已提交的事实"，一个观察者的崩溃没有资格让其他观察者失明。还有两道防护值得知道：其一，append 的接纳/发布临界区禁止重入（L736-L739 直接抛错："session append cannot reenter while another append is being published"）；其二，`session/created` 与 `session/event` 语义刻意不对称——created 是**同步边界**，监听器同步抛错会否决整个会话的发布并连带回滚（`announce` 的 JSDoc，L1129-L1163），而追加只能被观察、不能被否决。一句话：会话的创建可以被否决，创建之后的历史不能。

`session/flush` 的唯一合法触发入口是 `SessionStore.flush(session)`（index.ts L1190-L1207，JSDoc 称之为 "THE flush entry point"——一个 owner、一种拼法），内部 `Promise.allSettled` 所有监听器、全部 settle 后才返回或抛错。

那什么时候 flush？什么时候该等盘？这是 [packages/session/session-checkpoint-policy/src/index.ts](../../packages/session/session-checkpoint-policy/src/index.ts) 策略化回答的——三个语义检查点（L63-L82）：

1. **`llm/stream` 前**（L64-L68）：派发 adapter 之前先 `await ctx.sessions.flush(session)`，保证请求前缀落盘之后才真正发出网络请求——崩溃后重放，这次请求要么完整可查、要么根本没发过；
2. **顶层 `tools/execute` 前**（L70-L75）：工具产生副作用之前，它前置的 `tool/call` 已落盘；
3. **`agent/pre-step`**（L79-L82）：每步开始前 flush 上一步提交的全部事件。

三个检查点都是 fail-closed（故障关闭）：flush 失败就不派发下游。注意轮次边界**不** flush（`turn/end` 的 JSDoc，types.ts L292-L295 明言）——持久化节奏由检查点策略拥有，而不是循环的每个边界。

再补一个入口侧的事实：日志不是只能"活着长出来"。`Session` 构造器接受 seed（重放 / fork 的种子事件），并用**与 `append` 完全相同的校验**逐条验收——index.ts L557-L563 的注释解释了为什么：一个坏种子若不在此处拦截，只会推迟成后端拒绝、或活日志与磁盘静默分叉。每条种子事件都要过信封校验、seq 连续性检查、surface 迁移计划；任何一条失败，构造直接抛错，不存在"半个会话"。第 11 章的 resume 与 fork 全部踩在这块地板上。

顺带把开头"回到三轮前重来"的承诺落到实处方才算数。看 fork 的公开实现（`SessionStore.fork`，index.ts L1251-L1269）：解析边界 seq、`buildForkSeed` 构造种子（开放尾部补合成闭合器）、`create(childId, { seed, inheritedEventCount, meta: { parentSession, isSeeded: true } })`——**没有一行代码在"复制对话"**，因为它复制的就是日志本身，对话只是日志的投影。那个看似需要专门发明的"回退"功能，在这个体系里的全部实现是"取前缀、做种子、建新会话"。

### 3.5 "Model-visible means logged"：本章的灵魂不变量

[docs/architecture.md](../../docs/architecture.md) L127 有一句权威表述：

> **Model-visible means logged.** Every model request must be reconstructable from the log. New model-visible inputs require session events.

"每个模型请求都必须能从日志重建。"这不是愿望，是被一整套机制钉死的不变量。我们从五个角度清点执行点：

**① 模型历史只有一个来源：`Session.deriveMessages()`**（index.ts L856-L877）。它沿 surface 节点序列逐个投影（`deriveEventMessage`，surface.ts L120-L152），带缓存（纯尾部增长 O(新节点)，replace 或消息投影触发重建），返回冻结快照。agent-loop 每步组请求时调的就是它：

```ts
// packages/core/agent-loop/src/agent.ts（L669-L686，节选）
// canonicalHeader is shallow; append logs a detached snapshot, not these local values.
deepFreeze(header)
const boundaryMessages = session.deriveMessages()
for (const message of boundaryMessages) {
  if (this.frozenMessages.has(message)) continue
  deepFreeze(message)
  this.frozenMessages.add(message)
}
Object.freeze(boundaryMessages)
const request = markAgentLoopRequest(Object.freeze({
  ...header.config,
  messages: boundaryMessages,
  toolHistory: session.toolHistory(),
  ...header.tools !== undefined ? { tools: header.tools } : {},
  sessionId: this.session.id,
  signal,
}))
```

派生历史装进请求后被再次冻结，`frozenMessages` 集合跳过重复冻结。`toolHistory()`（index.ts L825-L829）随请求一起取走——历史工具定义加增量更新，供 provider 声明工具（[第7章](./第7章-工具系统-能力接缝与执行管线.md)）。第 5 章讲过的循环引擎，每转一步都是本章投影的消费者。

**② system prompt 必须是事件。** 不是请求头字段（`EpochHeader.system` 是 `never`），而是 `system/message` 事件占 surface 节点 0。"模型这次看到了什么系统提示词"因此可重建。

**③ 注入上下文必须是事件。** `agent.inject()` 合成的上下文以带 `source` 的 `user/message` 入日志，与人类输入同台投影。不存在"偷偷塞给模型但不留痕"的通道。

**④ agent/request waterfall 不能改消息。** [第4章](./第4章-事件驱动-五路派发与三个事件域.md)讲过 `agent/request` 是 waterfall 事件，但它的裁决对象是**请求配置**（provider/model/effort 等标量，agent.ts L576-L579）——waterfall 的文档明确不许动 messages。配置怎么变都行，反正每次变化都会以 `request/header` 落日志。

**⑤ 改消息内容的唯一合法通道是纯投影。** 插件想改写已记录的消息（如 image-offload），只能注册 `SessionMessageProjection` 纯函数——投影本身也要经 `foldSurface` 重放，改写本身因此可重建。想绕过投影、直接在 `deriveMessages()` 的返回值上动手脚？返回的是深冻结快照（数组与消息都冻结），写入在运行期即抛错；架构上也不存在第二个入口。

存储侧还有最后一道闸：`validateStoredEvents`（[packages/session/session-persistence/src/storage-contract.ts](../../packages/session/session-persistence/src/storage-contract.ts) L69-L77）——读到本构建不认识、又没标 `ignorable` 的事件类型，**拒绝解释整个日志**并报错"it was likely written by a newer harness"（它多半是更新的 harness 写的）。fail-closed，宁可拒读，不可错读。

### 3.6 `ignorable` 契约：词汇如何增长而版本不动

上一节留下的问题：新 harness 写的新事件类型，旧 harness 凭什么敢拒读？反过来，加一个新事件类型，要不要给磁盘格式升版本？

答案是 `SessionEvent.ignorable`（types.ts L503-L511）。默认**缺省即必需**：读者遇到不认识的必需事件，必须拒绝重建会话，而不是静默丢弃——因为一个不认识的必需事件可能改变整段日志的解读方式，跳过它等于悄悄恢复了一个被掏空的会话。只有**纯信息性**记录才可标 `ignorable: true`（丢掉也不影响重建）。注释里有一句漂亮的权衡（L509-L510）：默认必需意味着"忘记打标记"的代价是多拒绝（不便），而不是静默读出残废会话（错误）——**宁可过严，不可错宽**。

于是版本升级的判据变得很清晰（types.ts L74-L87 写明）：**只有结构性变化才 bump `SESSION_FORMAT_VERSION`**——header 形状、事件信封、核心事件语义、surface 机制（`SurfaceEventType` 集合与 `SurfaceOp` 变体）。新增普通事件类型不 bump，`ignorable` 负责兼容。当前版本是 4（types.ts L89）。

判据的锚点也值得抄下来——types.ts L74-L75 说明 bump 的判断永远看**写者**而非读者："Whether a bump is needed is decided by what the WRITER emits, never by what a newer reader can accept"（是否需要 bump 由写者发出什么决定，从不由新读者能接受什么决定）。"老读者解析不报错"不等于"老读者读得对"——静默跳过会影响重建的内容，就是读错了。文档还给出了一条实用主义的默认（L84-L86）："When in doubt, bump"（拿不准就 bump）——一次近乎恒等的迁移步骤几乎免费，一次漏掉的 bump 却会让旧运行时静默读错新日志。错误的不对称性决定了默认的方向。版本迁移链（v0→v1→…→v4）与"已发布格式不可回改"的规矩属于[第11章](./第11章-会话管理-持久化格式迁移与分叉.md)的主题，这里只立此存照。

### 3.7 投影接缝：`ctx.sessionProjections`

surface 回答"模型看到什么"，但 Agent 系统还有大量"当前值"问题：todo 列表现在长什么样？goal 进行到哪了？收件箱里有几条待处理？llmRetry 重试了几次？这些值如果各自维护一套状态，就会和日志渐行渐远。DSH 的答案还是投影——[packages/session/session-projection/](../../packages/session/session-projection/) 提供的 `ctx.sessionProjections` 注册表。

模式是"框架驱动、领域计算"，且有一条写在模块头的硬规则（index.ts L13-L15）——全值事件规则（whole-value event rule）：

> A state-carrying log event MUST carry the complete post-change state, never a bare delta — it keeps every unit's transition trivially cheap and every served value self-describing.

（携带状态的日志事件必须携带变更后的完整状态，绝不携带增量 delta——这让每个单元的转移极其廉价、每个交付的值自我描述。）与第 3 章的 `dsh-shell` request/spec 分割一样，这是"显式优于隐式"原则在事件负载上的投影：delta 语义要求读者维护前置状态，全值语义让任何一段日志都能独立读懂。领域插件注册一个 `ProjectionDefinition`（index.ts L48-L93）：

```ts
// packages/session/session-projection/src/index.ts（L48-L69，节选）
export interface ProjectionDefinition<K, S> {
  key: K                       // SessionProjectionStateMap 里的状态键
  stateSchema: ZodType<S>       // 持久化状态的 schema
  init(header, inheritedEventCount): S   // 空日志的初始状态
  apply(state, event): S       // 纯转移：前状态 + 一个已提交事件 → 新状态
  wire?: { viewSchema, view }  // 可选的客户端视图
  stateVersion: number         // 持久化缓存失效版本
}
```

注册表只订阅**一次** `session/event`，把每个已提交事件推过每个单元的 `apply`（急切驱动，index.ts L220-L222 与 `drive` L657-L704）；不感兴趣的事件返回同一引用，零下游开销（`Object.is` 判等）。宿主侧用 `stateOf(session, key)` 读类型化状态，载体用 `snapshot(session)` 一次切出同一水位线（watermark，`asOfSeq`）上的一致读切面。`SessionProjectionMap` / `SessionProjectionStateMap`（types.ts L17 / L22）是两张可合并扩展的空表——和 `SessionEventMap` 一样的声明合并戏法，todo、goal、inbox、turnBoundary、llmRetry 各自的领域包往里合并自己的键。agent-loop 自己就注册了 `turnBoundary` 与 inbox 两个单元（[packages/core/agent-loop/src/index.ts](../../packages/core/agent-loop/src/index.ts) L364-L365）。`turnBoundary` 的定义本身就是一份好教材（真实代码节选）：

```ts
// packages/core/agent-loop/src/index.ts（L57-L94，节选）
/** Host projection of agent turn and step boundaries. */
export const turnBoundaryProjectionDefinition = {
  key: 'turnBoundary',
  stateVersion: 2,
  stateSchema: turnBoundaryProjectionSchema,
  init: () => ({ openTurnStartSeq: null, lastStepStartSeq: null, lastStepBoundary: null, lastTurn: 0 }),
  apply: (state, event) => {
    switch (event.type) {
      case 'turn/start': return { ...state, openTurnStartSeq: event.seq, lastTurn: event.data.turn }
      case 'turn/end':   return { ...state, openTurnStartSeq: null }
      case 'step/start': return { ...state, lastStepStartSeq: event.seq, lastStepBoundary: { kind: 'start', seq: event.seq } }
      case 'step/end':   return { ...state, lastStepBoundary: { kind: 'end', seq: event.seq } }
      default:           return state   // 不相关的事件：返回同一引用，零下游开销
    }
  },
} satisfies ProjectionDefinition<'turnBoundary', TurnBoundaryProjection>
```

读懂它你就读懂了整个投影体系：状态是纯 JSON（缓存持久化的前提），`apply` 是纯函数（同状态加同事件必得同结果，`snapshot()` 的文档明言单元必须同步——异步单元会撕裂载体的一致切面），`stateVersion: 2` 意味着这个单元的语义改过一次——旧缓存行按版本不匹配整行丢弃重折，而不是把过期状态向前折成垃圾。UI 层问"当前有没有开放的轮次"，答案是 `stateOf(session, 'turnBoundary')`；崩溃重启后，同一个问题从日志重放免费得到同一个答案。

注意投影与缓存的本质区别：投影是**语义视图**——todo 列表的当前值**就是**日志重放的结果，它是权威本身；缓存只是加速。冷启动时任何投影都能从日志免费重建，这正是 [packages/session/session-projection-cache/](../../packages/session/session-projection-cache/) 存在的意义：把 `(sessionId, key, ver, seq, val)` 检查点持久化，冷读时跳过已折叠前缀、只重放尾部。还有一个值得记住的架构决策（[.agents/notes/implemented/architecture/2026-08-19-session-projection-mandatory-seam.md](../../.agents/notes/implemented/architecture/2026-08-19-session-projection-mandatory-seam.md)）：宿主读者要么在 `inject` 里声明依赖该服务，要么显式失败——**不允许静默默认**。找不到投影就是找不到答案，不给"看起来空"的假象。

最后简述读模型组（[第11章](./第11章-会话管理-持久化格式迁移与分叉.md)展开）：`ctx.sessionQuery`（`SessionQueryEngine`，[packages/session-query/session-query/src/index.ts](../../packages/session-query/session-query/src/index.ts) L140-L184）提供 `observeSession` 一次原子观察、`searchSessions` / `searchEvents` 检索、`listSessions`、`readSession` 完整重放验证，外加 `SessionLineageTrace`（fork 血统树，L327）与 `SessionEventTrace`（事件替换链，L340）；`session-query-sqlite` 用 FTS5 派生全文索引加速检索（schema.ts L127 的 `USING fts5` 虚表，schema 版本不匹配时原地重置）；`tool-session-query` 给模型侧提供 `session_search` 等工具；`session-log-export` 把日志打成 ZIP 归档。它们全是日志的下游，无一持有独立状态。

### 3.8 这么麻烦，图什么？——设计收益清点

把对话建模成事件溯源日志，代价是本章这些机制；收益则贯穿整个系统：

1. **可重放**：任何历史请求逐字节重建（`request/header` 快照 + surface + 日志）。DSH 的快照测试体系（`pnpm run test:snapshot`，无 key 重放录制会话）就建立在"重放日志必须得到相同的模型输入"之上——测试基础设施本身就是这条不变量的第一个受益者。
2. **免费 fork / resume**：回到三轮前 = 取日志前缀做种子（`session/end-seed` 切割）；重启续聊 = 重放日志。没有快照机制的额外发明（[第11章](./第11章-会话管理-持久化格式迁移与分叉.md)展开）。
3. **免费 transcript / UI**：人类视图就是 `isAppendSurfaceEvent` 过滤后的追加事件流——压缩不删人类历史，UI 永远能显示完整对话。
4. **免费遥测 / 统计**：token 计量（[packages/llm/token-meter/](../../packages/llm/token-meter/)）与会话统计（[packages/session/session-stats/](../../packages/session/session-stats/)）从日志重放即可得到——usage 与流同住 `assistant/message`，连失败尝试的计费证据都一条不丢。
5. **模型行为可审计**：`request/header` + `request/context` 记录每一次路由决策的证据链——"当时为什么用这个模型、容量多大、系统提示词长什么样"全部有据可查。

如果要用一句话把收益收拢：**为"把对话当日志"多付的每一行代码，都在 fork、resume、压缩、UI、统计、测试这六处各还了一次**。这不是优雅的巧合，而是"唯一真源 + 全员投影"的必然算术——任何下游消费都不再需要自己的状态副本，也就不再有状态同步的 bug。

## 5. 常见误区

**误区一："assistant 消息不就是存了段文本吗？"** 不。`assistant/message` 内嵌完整的定时模型流（`stream: AssistantStreamRecord[]`），压缩但不拼接 delta 边界；usage 挂在事件上而不是单独记录。重放、计费、UI 动画三者的证据都在这一条事件里。相应的，失败的尝试是 `assistant/attempt`——保留流但不伪造模型可见历史。

**误区二："replace 把旧消息删了。"** 日志是 append-only 的，replace 只在 surface 投影里**遮蔽**旧节点，旧事件原封不动躺在日志里。人类 transcript 读追加来源事件（`isAppendSurfaceEvent`），被压缩概括的旧消息在用户视图里完好如初。把"模型视角的遗忘"当成"数据被删除"，是读这套代码最容易犯的错。

**误区三："所有事件模型都看得见。"** 59 种事件类型里只有五类 `SurfaceEventType` 产生 LLM 消息。`tool/call`、`request/header`、`assistant/attempt`、`turn/*` 全是仅日志事件。反过来说也对：**所有**模型可见输入必须有事件——包括 system prompt（节点 0 的事件）和注入上下文（带 `source` 的 `user/message`）。

**误区四："新增事件类型要 bump `SESSION_FORMAT_VERSION`。"** 恰恰相反，普通事件类型的增长由 `ignorable` 契约兜底，不 bump；只有结构性变化（header 形状、信封、核心事件语义、`SurfaceEventType` 集合与 `SurfaceOp` 变体）才 bump。而且默认必需意味着：忘了标 `ignorable` 的后果是旧读者拒读（明显且可发现），而不是静默读错（隐蔽且致命）。

**误区五："投影就是缓存。"** 投影是**语义视图**：todo 列表的当前值就是日志重放的确定性结果，它语义上权威，重建只是加速路径（`session-projection-cache`）。把投影当缓存理解，就会得出"投影丢了可以不管、反正有原始数据"的错误结论——投影丢了，读模型就丢了，直到重放补回。

**误区六（送一条）："对话应该存在数据库表里，一张 messages 表。"** 那是"以消息为一等公民"的建模。DSH 反其道而行：**事件是一等公民，消息是派生物**。存消息表会把"模型看到什么"与"发生了什么"两件事强行合一，压缩、fork、审计都失去支点。判断一个 Agent 框架的设计成熟度，看它把什么当一等公民，是个不错的启发式。

**误区七："本章讲了两种'投影'，是同一回事。"** 恰恰要分开。`SessionMessageProjection`（消息投影，surface.ts L35）是**改写已有 surface 节点内容**的解释器——消息身份和成员不变，image-offload 是唯一现役案例；`ProjectionDefinition` / `ctx.sessionProjections`（投影单元）是**从日志派生领域当前值**的读模型——todo、goal、inbox 都住在这里。前者改"模型看到的消息"，后者算"领域状态现在如何"；前者由 Session 折叠时应用，后者由注册表急切驱动。两个都叫投影，因为都遵循"日志重放得出结果"的同一哲学——但接入点、注册方式、消费方完全不同。

```
seq0  turn/start            ┄┄ 仅日志
seq1  step/start            ┄┄ 仅日志（step 1）
seq2  request/header        ┄┄ 仅日志（reason: initial）
seq3  system/message        ── surface（append，surface 节点 0）
seq4  user/message          ── surface（append）
seq5  assistant/message     ── surface（append，含 tool-call 块）
seq6  tool/call             ┄┄ 仅日志（原始 arguments JSON 字符串）
seq7  tool/result           ── surface（append，callId 与 seq6 配对）
seq8  step/end              ┄┄ 仅日志
seq9  step/start            ┄┄ 仅日志（step 2：工具结果回流后的第二次模型调用）
seq10 assistant/message     ── surface（append，最终文本）
seq11 step/end              ┄┄ 仅日志
seq12 turn/end              ┄┄ 仅日志（reason: completed）

最终 surface：[seq3, seq4, seq5, seq7, seq10] → 5 条派生消息
```

做完后自查三个追问：`deriveMessages()` 在这个 surface 上返回几条消息？如果 seq4 之后发生压缩（replace seq4-seq7 为一条摘要），模型视图和人类视图各变成什么？`tool/call` 为什么不需要是 surface 事件？（答案方向：调用意图已内嵌在 seq5 的 content 块里，结果才是模型下一轮的输入。）

**练习四：设计一个新事件（纸面作业）。** 假设你要给 DSH 加一个"费用上限提醒"插件：每次模型调用后检查累计 token 是否超过用户设的阈值，超过了就提醒用户。不要写代码，回答四个问题，并到源码里验证答案：

1. 你真的需要新事件类型吗？（提示：累计值可以从 `assistant/message` / `assistant/attempt` 的 `usage` 派生——也许你要的是一个投影，而不是一个新事件。）
2. 如果确实要新事件：它是 surface 还是仅日志？载荷是否纯 JSON？要不要标 `ignorable: true`？（自问：丢弃它会不会改变其余日志的解读？）
3. 它属于哪个插件包？`declare module` 写在哪个 `types.ts`？相邻的事件（比如 `todo/write` 的所属包）是怎么组织词汇的？
4. 写完后 `KNOWN_SESSION_EVENT_TYPES` 会怎么变？（提示：重新生成目录，不手改。）

这道题的目的是让你走一遍 DSH 的决策路径：**先问"这是不是日志事实"，再问"谁拥有它"，最后才问"怎么存"**。多数"需要新状态"的需求，其实需要的是一个投影。

## 7. 本章小结

1. DSH 没有"存对话"：对话是事件溯源的仅追加日志（`SessionEventMap`，types.ts L281），消息历史是**派生**投影。
2. `SessionEventMap` 经声明合并可扩展（compaction 合并了 `compaction/*` 四事件）；`SessionEvent<T>` 是真可辨识联合，`switch (event.type)` 直接窄化 `event.data`。
3. `seq = log.length` 连续性契约让日志位置成为全系统寻址语言（replace 区间、投影水位线、fork 切割点都用它）。
4. 14 类核心事件各有分工：边界（turn/step）、五类 surface 消息、失败尝试、工具配对、请求快照、路由元数据、fork 切割标记。
5. system prompt 是 `system/message` 事件、surface 节点 0，`EpochHeader.system` 是 `never`——请求头不携带提示词。
6. `assistant/message` 内嵌完整定时流与 usage；`assistant/attempt` 保留失败尝试的证据但不伪造模型可见历史。
7. surface = "当前模型可见节点"的有序投影；`SurfaceOp` 有 `append` 与 `replace` 两种入会方式；replace 只遮蔽不删除。
8. 模型视图（`deriveMessages()`，可被 replace 遮蔽）与人类视图（`isAppendSurfaceEvent` 过滤，永不被抹）是两层投影——压缩对模型是遗忘、对用户是全存。
9. `Session.append()` 四步：单遍"读取-校验-复制"快照 → 先计划后入日志的双重校验 → 冻结入日志 → fire-and-forget 发布；热路径零 I/O。
10. 持久化经 Cordis 事件：`session/event` 追加流（fire-and-forget）+ `session/flush` awaited parallel 屏障；checkpoint-policy 在 llm/stream 前、顶层 tools/execute 前、agent/pre-step 三个语义点 fail-closed 地 flush。
11. "Model-visible means logged"由五道闸保证：`deriveMessages()` 唯一来源、system prompt 必须是事件、注入必须是带 source 的 `user/message`、waterfall 不许改消息、内容改写唯一通道是纯投影；存储侧 `validateStoredEvents` fail-closed。
12. `ignorable` 契约：事件默认必需（未知必需事件 → 拒绝重建），纯信息性才可标 ignorable；因此新增普通事件不 bump 版本，`SESSION_FORMAT_VERSION = 4` 只在结构性变化时增长。
13. `ctx.sessionProjections` 是"框架驱动、领域计算"的读模型注册表；todo/goal/inbox/turnBoundary 等当前值全部从日志派生，重启免费重建；`session-projection-cache` 持久化检查点加速冷读。
14. session-query 组（引擎、FTS5、模型侧工具、导出）是日志的下游读模型，无一持有独立状态。
15. 设计收益：可重放、免费 fork/resume、免费 transcript、免费遥测、行为可审计——事件是一等公民，消息是派生物。

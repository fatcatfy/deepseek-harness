# 第12章 扩展系统：配置即组合，一切皆插件

## 1. 本章导读

前十一章，你把 DSH 拆成了一堆零件：Cordis 的服务与事件（[第3章](./第3章-Cordis内核-服务依赖注入与上下文.md)、[第4章](./第4章-事件驱动-五路派发与三个事件域.md)）、让模型转起来的 agent-loop（[第5章](./第5章-Agent-Loop-让模型转动起来的引擎.md)）、模型适配器（[第6章](./第6章-模型调用-llm能力接缝与适配器.md)）、工具执行管线（[第7章](./第7章-工具系统-能力接缝与执行管线.md)）、会话日志（[第8章](./第8章-消息系统-会话日志即模型记忆.md)）、上下文组装与压缩（[第9章](./第9章-上下文工程-一次请求里塞了什么.md)、[第10章](./第10章-上下文压缩-当对话太长怎么办.md)）、持久化与分叉（[第11章](./第11章-会话管理-持久化格式迁移与分叉.md)）。零件齐了，但有一个问题一直在你的视野边缘：**谁来决定一个运行中的 dsh 到底装哪些零件？**

答案只有一句话：**配置**。DSH 里没有一个"偷偷写死的主程序"——没有一份必须被 fork 才能改动的 `main.ts`，没有一个硬编码的插件数组。你启动的每一个 `dsh`，都是一棵**从配置层叠（compose）出来的插件树（plugin tree）**。这也正是本章标题的含义：**配置即组合，一切皆插件**。

学完本章，你应该能回答七个问题：

1. **profile**、**bundle**、**agent preset** 这三个"组合单位"各是什么？分别决定"整个进程装什么"和"每个会话看到什么"？
2. 运行时那棵树是从哪些层、按什么顺序叠出来的？哪一层最后赢？
3. **patch** 方言有哪几种写法？为什么 `config` 是**整体替换**而不是深合并？
4. `!!js` 表达式能写在哪里、不能写在哪里？
5. 什么叫做"**禁用而非删除**"？为什么删行是危险的？
6. 不写一行代码，靠 skill、MCP、hooks 三条路怎么扩展 DSH？
7. `packages/extensions` 的"运行时自改"为什么既强大又危险？

核心源码集中在四组：`packages/boot/`（启动与 profile 管理）、`packages/bundle/`（六个 BFF——bundle 的 patch 层）、`packages/preset/`（会话级能力集）、`packages/extensions/`（运行时自改）。此外 `vendor/include/src/index.ts` 藏着本章最硬的一块干货——patch 的**真实语义**。建议给 3.2、3.3、3.7 三节多留时间。

## 2. 从一个问题出发

设想一个很现实的场景：DSH 团队某天要同时发布两个产品形态——一个是带浏览器界面的网页版，一个是只跑一次任务、打印结果就退出的命令行版。二者共享的东西大概有九成：模型适配器、工具系统、沙箱与审批、会话持久化、上下文压缩……差异只有一成：网页版要 HTTP 服务器与浏览器插件，命令行版只要一个一次性 runner。

没有配置组合的年代，业界通常两种做法。**其一是条件编译**：同一份代码里塞满 `if (mode === 'web')`，构建时打不同的包。**其二是拆两个仓库**：把共享部分抽成库，两个仓库各自组装。前者让代码里长满分支，后者让"共享部分"的每次改动都要在两边同步。

DSH 的答案是第三种：**同一棵插件树，两种组合**。共享能力属于一个叫 `dsh-base` 的 **bundle**（它插入的行就是那九成）；网页版再加一个 `dsh-web-app` bundle，命令行版再加一个 `dsh-headless` bundle。没有任何一个 bundle 需要知道另一个存在，也没有一行 `if` 分支。想发布第三种形态？再加一个 bundle，而不是改 `dsh-base`。

| 传统方案 | DSH 组合 | 差异要点 |
|---|---|---|
| 条件编译，运行期分支 | 分层的 patch，静态组合 | 差异在配置，不在代码 |
| 抽库 + 两个仓库 | 一个 base bundle + 多个 mode bundle | 共享面只维护一次 |
| 改主程序才能换行为 | 用 patch 覆盖任意一行 | 无需 fork，无需重编译 |
| "扩展 = 改源码" | "扩展 = 挂一个插件行" | 增删是配置事实，不是发布事件 |

先把两个反复出现的词钉死。**profile**（档案）是"一个命名的进程组合"，存在 Harness home（`$DSH_HOME/profiles/<name>/`）里。**bundle**（打包层）是"一个 npm 包，它的 `package.json` 声明了一个 patch 文件，把一组配置行作为一层贡献出来"。运行时那棵树就是把若干 bundle 层、再加上你自己的层，按顺序叠起来的结果。

## 3. 正文

### 3.1 三个组合单位：profile、bundle、agent preset

先明确话语体系。DSH 复用了"包"这个载体，但一个包可以扮演三种角色，由它 `package.json` 里的 `dsh` 字段声明（类型定义在 [packages/util/package-manifest/src/types.ts](../../packages/util/package-manifest/src/types.ts)）：

```ts
// packages/util/package-manifest/src/types.ts（L29-L39）
export interface DshManifest {
  manifestVersion?: 1
  bundle?: DshBundleManifest
  profile?: DshProfileManifest
  client?: DshClientManifest
}
// L69-L78
export interface DshBundleManifest {
  /** One patch file path, or an ordered list applied in sequence ... */
  patch: string | string[]
}
export interface DshProfileManifest {
  /** Ordered bundle layer list, using installed package names. */
  bundles?: string[]
}
```

**单位一：profile。** 一个 profile 目录里有两个关键文件：`package.json`（其 `dsh.profile.bundles` 是**有序**的 bundle 清单，`dependencies` 里则装 out-of-tree 插件）与 `cordis.patch.yml`（用户自己的那一层 patch）。首次使用时，DSH 会从模板自动初始化它（[packages/boot/app-boot/src/profile.ts](../../packages/boot/app-boot/src/profile.ts) L254-L273），模板表是 `PROFILE_TEMPLATES`（L179-L195）：

```ts
// packages/boot/app-boot/src/profile.ts（L179-L195）
export const PROFILE_TEMPLATES: Record<string, ProfileTemplate> = {
  acp: { bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-acp-app'] },
  web: { bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app'] },
  headless: { bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-headless'] },
  sdk: { bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-sdk-app'] },
  'sdk-minimal': { bundles: ['@deepseek-ai/dsh-sdk-minimal'] },
}
```

注意 `sdk-minimal` 是唯一的例外：它**不经过 `dsh-base`**，一个 bundle 独自拥有完整的树。这五个模板（另有 `desktop` 由 Electron 独占，CLI 拒绝启动它）就是"发布形态"的全部清单。

初始化后，一个 profile 目录长这样（`initProfile`，profile.ts L254-L273）：

```json
// $DSH_HOME/profiles/web/package.json（initProfile 生成的形态）
{
  "name": "dsh-profile-web",
  "private": true,
  "dependencies": {},
  "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app"] } }
}
```

外加一份空的 `cordis.patch.yml` 模板与一个 `pnpm-workspace.yaml`（`nodeLinker: hoisted`，让 out-of-tree 插件的 peer 复用**安装里那一份** Cordis，而不是各自再装一份）。注意 `dependencies` 一开始是空的——bundle 是从**安装**解析的，不是从 profile 装的；`dependencies` 只装你想额外挂的第三方插件。

**单位二：bundle。** 一个 bundle 只做一件事：贡献一个 patch 文件（或有序的一串，见 `bundlePatchFiles`/`bundlePatchPaths`，profile.ts L58-L75）。六个 shipped bundle 的分工：

| bundle | 作用 | 关键行 |
|---|---|---|
| `dsh-base` | 共享第一层：模型适配器、工具、持久化、沙箱与审批、设置、凭据、遥测 | 一条大 `insert` |
| `dsh-web-app` | 浏览器应用：host 行 + 浏览器 roster，并把 base 的 agent 面行逐 id 禁用后插入 preset 注册表 | [web-app/cordis.patch.yml](../../packages/bundle/web-app/cordis.patch.yml) |
| `dsh-headless` | 一次性 runner：`headless-startup` + `headless-runner`，无 Host/HTTP/浏览器，hmr 禁用 | [headless/cordis.patch.yml](../../packages/bundle/headless/cordis.patch.yml) |
| `dsh-sdk-app` | SDK JSON-RPC 服务器（stdout 归协议） | [sdk-app/cordis.patch.yml](../../packages/bundle/sdk-app/cordis.patch.yml) |
| `dsh-acp-app` | 自动化 ACP：固定 `deepseek-v4-flash` 路由，stdout 归 ACP | [acp-app/cordis.patch.yml](../../packages/bundle/acp-app/cordis.patch.yml) |
| `dsh-sdk-minimal` | 唯一不经 base 的完整独立树（显式最小 agent 内核，压缩 `none`） | [sdk-minimal/cordis.patch.yml](../../packages/bundle/sdk-minimal/cordis.patch.yml) |

`dsh-base` 的第一行注释把它的定位说得很直白（base/cordis.patch.yml L1-L3）：它是"每个 base-backed profile 的共享核心，作为一条 insert 应用在**空的根**之上"。它甚至预告了本章的主线："后面的 bundle patch 与用户的 `cordis.patch.yml` 会**按 id** 寻址这些行，**逐行最后写者胜**（last write winning per row）"。

**单位三：agent preset。** 前面两个决定"**进程**挂什么"，preset 决定"**每个 Agent（会话）看到什么**"。同一个进程里的两个会话，可以挂不同的 preset：一个拿全套工具，一个只拿 persona 加一个持久 shell。这是 3.7 节的主题。

这里用两个单位把一个易混点说清：**profile 决定整栋楼装什么设备，preset 决定每个房间配什么家具。** 这是本章第 2 个、也是最后一个明喻——请把它记住，因为第 5 节的误区四就考这个。

### 3.2 层叠顺序：一棵洋葱

同一棵树的各个组合单位，是靠"层层以 patch 覆盖一个空根"叠出来的。顺序至关重要，因为**后面的层覆盖前面的层**。权威实现是 `readProfilePatches`（[packages/boot/app-boot/src/profile-context.ts](../../packages/boot/app-boot/src/profile-context.ts) L63-L74）：

```ts
// packages/boot/app-boot/src/profile-context.ts（L65-L73，节选）
const patches = structuredClone([
  ...profile.layers.flatMap(layer => layer.patches),      // ① 各 bundle，按 dsh.profile.bundles 顺序
  ...(initialProfile?.patches ?? loadOptionalPatches(binName, context.patchPath) ?? []), // ② profile 自己的
  ...(loadOptionalPatches(binName, join(context.home, PROFILE_PATCH_FILENAME)) ?? []),   // ③ home 层
  ...context.overlays,                                    // ④ --patch 覆盖
])
const telemetryPatch = resolveTelemetryPatch(...)         // ⑤ launcher 的遥测开关
if (telemetryPatch !== undefined) patches.push(telemetryPatch)
```

完整顺序（后者胜）：

```
空根（profile/cordis.yml 就是一行 "[]"）
  │
  ├─ 各 bundle 的 cordis.patch.yml   （按 dsh.profile.bundles 顺序）
  ├─ profile 自己的 cordis.patch.yml （$DSH_HOME/profiles/<name>/）
  ├─ home 层 cordis.patch.yml        （$DSH_HOME/cordis.patch.yml，机器级偏好）
  ├─ --patch overlays                 （argv 顺序，最高优先的用户层）
  └─ launcher 的 telemetry switch patch（DSH_TELEMETRY_DISABLED 非空则禁用遥测行）
  ▼
一棵消解完的插件树
```

把空根写成 `[]` 不是偷懒，而是刻意的设计。profile-boot.ts 的 `PROFILE_ROOT_CONFIG`（[apps/cli/src/profile-boot.ts](../../apps/cli/src/profile-boot.ts) L81-L85）是一份带注释的**空数组**，并且注释直接告诉用户："这棵树是 patch 组合出来的，请编辑 `cordis.patch.yml`，不要编辑这个文件。"为什么根文件必须存在？因为 Loader 需要一个真实的 include 根来把 `baseUrl` 锚在 profile 目录上（L153-L160）。而且它**每次启动都会被重写**：vendored Loader 曾有"插件自销毁时把当前树写回文件"的行为，若不一并重置，下次启动就会把组合出的行当字面数据再插一遍，导致 bundle 层被重复插入。

这五层就是洋葱。注意第 ③ 层的语义：**home 层是机器级偏好，优先级高于每个 profile 自己的层**——你在 `$DSH_HOME/cordis.patch.yml` 里写的覆盖，对该机器上的**每一个** profile 生效，包括你后来新建的。

### 3.3 patch 方言速查表

现在讲本章最硬的一块：patch 到底怎么改写树。真正的实现只有一份，在 [vendor/include/src/index.ts](../../vendor/include/src/index.ts) 的 `applyEntryPatches`（L57-L127）。app-boot 的挂载、`--dump-config` 的离线渲染，调的都是它——注释（L44-L56）特意强调"同一份实现，所以 dump 永远不会和真正 boot 出来的树漂移"。看懂这 70 行，你就看懂了整个组合系统。

一个 patch 是一个 mapping。下面是速查表：

| 写法 | 语义 |
|---|---|
| `insert: [rows]` | 往树尾追加行。若同时给了 `id` 指向一个已存在的 `group: true` 行，则插入该 group 的 `config` 列表内（L79-L91）。 |
| `id: X` + 无 `insert` | **定向**已存在的行 X：提供的字段替换该行对应字段（L109-L123）。 |
| `config: {...}` | **整体替换**该行的 config，**不是深合并**——必须重述你想保留的全部字段。 |
| `name: '<pkg>'` | 是**断言**既有插件名，不是改名。名字不匹配就警告跳过（L115-L118）。 |
| `disabled: <bool\|expr>` | 禁用（而非删除）一行。 |
| `group: true` + `name: cordis:group` | 让该行的 `config` 变成**嵌套的行列表**，可被后续 patch 按 id 插入。 |
| `name: cordis:include` | 从 `config.path` 载入一个字面的 YAML/JSON 行列表。 |
| `isolate: { <service>: true }` | 把服务实例**隔离**进一个 realm（见 3.7）。 |
| `inject` / `intercept` | 行的注入声明 / 拦截声明（与[第3章](./第3章-Cordis内核-服务依赖注入与上下文.md)、[第4章](./第4章-事件驱动-五路派发与三个事件域.md)一致）。 |

行字段类型就是 `PatchOptions`（L130-L141）：`id / insert / name / config / group / disabled / inject / intercept / isolate`。

把核心逻辑摘出来（L76-L123，删去部分注释）：

```ts
// vendor/include/src/index.ts，applyEntryPatches（L76-L123，节选）
for (const patch of patches) {
  const { id, insert, name, ...overrides } = patch
  if (insert) {
    if (id) {
      const target = entryMap.get(id)
      if (!target) { warn('patch insert: entry %C not found', id); continue }
      if (!target.group) { warn('patch insert: entry %C is not a group', id); continue }
      if (!Array.isArray(target.config)) target.config = []
      target.config.push(...insert)              // 插入 group 的 config 内部
    } else {
      data.push(...insert)                        // 追加到树尾
    }
    buildMap(insert)                             // ★ 让同一列表里更靠后的 patch 也能命中刚插入的行
    continue
  }
  if (!id) { warn('patch: id is required for non-insert patches'); continue }
  const target = entryMap.get(id)
  if (!target) { warn('patch: entry %C not found', id); continue }
  if (name && name !== target.name) { warn('patch: name mismatch for %C ...', id); continue }
  for (const [key, value] of Object.entries(overrides)) {
    if (key === 'id') continue
    target[key] = value                           // 逐字段替换；config 是整体替换
  }
}
```

三个细节值得咀嚼。

**其一，"整体替换 config"是刻意的。** DSH 不用深合并（deep merge）。理由藏在 base 文件的开头注释里（base/cordis.patch.yml L6-L10）：深合并会让"这一行到底最终是什么值"变成一次跨多层的历史累加，任何一层都无法独立读懂最终态；整体替换则让每一层都能**完整重述**它要的那一行，"任何一个行条目最多只活在一个 bundle 层加用户层里"。代价是啰嗦（必须重述所有保留字段），收益是**可推理**。这正是 [第3章](./第3章-Cordis内核-服务依赖注入与上下文.md) 讲过的"显式优于隐式"在配置层的投影。

**其二，`name` 是断言不是改名。** 你若写 `id: tools` 加一个错的 `name`，DSH 不会把你的插件改名，而是警告这行**不是你以为什么**并跳过（L115-L118）。这防的是"id 撞车"——同一个 id 在不同 bundle 里指向不同插件时，静默改名会让组合悄悄错位，断言则让它立刻可见。

**其三，插入即建索引。** L100 的 `buildMap(insert)` 让同一 patch 列表里更靠后的 patch 能命中刚插入的行。这条看似微小的规则，是"一层可以配置或禁用前一层插入的行"的前提。

真实例子更直观。`dsh-base` 的 `system-prompt` 行只有一个中性默认（base L504-L507），`dsh-web-app` 用一条同 id patch 覆盖它、并**重述**它要保留的键（web-app L16-L20）：

```yaml
# packages/bundle/web-app/cordis.patch.yml（L16-L20）
- id: system-prompt
  config:
    personaSuffix: Your working directory is {{cwd}}.
    personaPrefix: >-
      You are a coding agent powered by the {{model}} model.
```

### 3.4 `!!js` 与 fails-loud

**`!!js` 是 Loader 的表达式标量**（注意是双叹号，`!js` 是无效的）。它能在两个地方求值，别处一律保持字面：

- **在 `config` 里**：在**该行声明的注入激活之后**，对**该插件自己的 context** 求值，所以 `!!js dshHomePath('sessions')`、`!!js ctx.webStartup.host ?? '127.0.0.1'`、`!!js "!ctx.get('profileContext')"` 都是合法的（base L133、web-app L182）。
- **在 `disabled` 里**：对 **Loader 的 context** 求值，而且在**每次挂载决策**时都求值（base L22、L30）。

其余行元数据（`id / name / group / inject / intercept / isolate`）**必须保持字面**。这不是君子协定：`scripts/verify-cordis-config.ts` 的 `metadataExpressionErrors`（L517-L539）以 `metadataFields`（L41）为清单，会把任何一个埋在元数据里的 `!!js` 报成"`!!js is not interpolated here"（`!!js 在此不会被求值`），并让门禁失败。为什么如此严格？因为元数据里的 `!!js` 会**静默地**被当作 truthy 数据——一旦它真值化，组合就悄悄变了而你毫无察觉。宁可让它在 CI 里炸掉，也不许它沉默地改变树的形状。

`!!js` 的另一半故事是"**fails loud**（失败即报错）"。这是本章的一条原则线，几个代表：

- **存在的 patch 文件必须能应用。** `loadOptionalPatches`（[packages/boot/app-boot/src/index.ts](../../packages/boot/app-boot/src/index.ts) L316-L325）与 `loadOverlayPatches`（L336-L344）的区别只有一句：前者文件不存在视为"无此层"，后者（bundle 的 patch、`--patch`）文件不存在**直接抛错**。注释（L309-L311）说得斩钉截铁："一个存在却无法应用的 patch 文件是 misconfiguration（配置错误），必须在启动时炸掉，绝不能被静默跳过。"
- **空文件或仅注释的 patch 会让 boot 失败。** 顶层必须是一个 YAML 数组；解析出 `undefined` 会以"必须是顶层数组"报错。想禁用一层，写显式的 `[]`，而不是留空。
- **`.env` 引导名被拒绝。** 名为 `PATH`、`DSH_*`、`XDG_*`、TLS、代理等的变量只允许来自继承环境（app-boot L175-L178）。唯一的例外是 home 层的四个代理名（L166），因为"代理决定每个请求走哪条路，跟着仓库一起 clone 下来的 `.env` 不能改它；home 层的文件才是用户自己的"。
- **启动审计。** `auditStartupEntries`（L926）对消解后的树分类：**全局必需 id**（L747-L755：`agent-loop`、`webserver`、`modules`、`connection`、`headless-runner`、`acp`、`sdk-jsonrpc-server`）缺失即 `StartupError`；其余行失败只是警告，成功的兄弟行继续跑。`installFailLoud`（L680-L729）把运行期的 `unhandledRejection`/`uncaughtException` 变成一行诊断加 `exit(1)`。

一句话概括这节：**DSH 把"配错"和"没配"严格区分，并在最早能发现的地方炸掉。**

### 3.5 boot 链：五个包的接力

现在跟着一次 `dsh web` 走完启动。入口链在 `apps/cli`：

1. **`runCli`**（[apps/cli/src/bin.ts](../../apps/cli/src/bin.ts) L26）调用 `parseDshArgs`。
2. **`parseDshArgs`**（[apps/cli/src/args.ts](../../apps/cli/src/args.ts) L146）是 launcher 的**唯一**语法：它只认自己的旗标 `--profile` / `--patch` / `--dump-config*`，其余参数**原样**留给树内插件（L164-L170 的 `.allowUnknownOption().passThroughOptions().enablePositionalOptions()`）。所以 `dsh --profile web --port 8080` 里 `--port` 属于 web 应用，`dsh --profile web -h` 打印的是 web 应用自己的帮助。`--patch` 用 `collect`（L76）实现为可重复单值，注释解释了为什么不设成 variadic——variadic 会吞掉内层参数。
3. **`runProfile`**（[apps/cli/src/profile-boot.ts](../../apps/cli/src/profile-boot.ts) L244）先做一件关键的事：`installProxyFromEnvironment`（L249）**在挂载任何插件之前**把代理装进 Node 的 fetch。它读的是 launcher 的启动环境快照，而不是 `process.env`，所以 `.env` 里声明的代理也能生效。
4. **`composeProfile`**（L197-L209）算出**不可变的 runtime resolution**（`createRuntimeResolution`），并把 `--patch` 覆盖也解析好。
5. **`boot`**（[packages/boot/app-boot/src/index.ts](../../packages/boot/app-boot/src/index.ts) L973）新建 `Context`，`ctx.provide('dshHomePath', dshHomePath)`（L996），挂 `Loader` 插件（L1002），再 `mountRootInclude`（L539）构造根 `cordis:include` 行——它的 `id` 固定为 `'include'`（L576），`config.path` 指向 profile 的空根 `cordis.yml`，`config.patches` 就是那五层 patch。随后 `ctx.get('loader')?.await()` 等整棵树消解，最后 `auditStartupEntries` 审计（L1013）。
6. 回到 `runProfile`：`boot` 的 `prepare` 回调（L296-L312）在**任何配置行挂载之前**提供了 `profileContext`、启动环境快照、`PluginPackages`（runtime resolution）以及 `provideCmdline`（`ctx.cmdlineArgs` / `ctx.appExit` / `ctx.appReady`）。

`packages/boot/` 这一组的五个包，正好覆盖启动链的五个侧面：

| 包 | 职责 | 关键出口 |
|---|---|---|
| `app-boot` | 启动 + 组合 + profile + 配置 dump + schema | `boot`、`mountRootInclude`、`readProfilePatches`、`loadOptionalPatches` |
| `cmdline` | `ctx.cmdlineArgs` 快照、`ctx.appExit`、`ctx.appReady` | README 的 "How flags beat config values" |
| `config-editor` | `ctx.configEditor.edit()`：把配置写回 profile patch 层并立即应用 | 原子替换、保留 YAML 注释与 `!!js` |
| `hmr` | 模块替换 + Include 刷新 + profile 配置变更，进同一串行队列 | `runExclusive()`，拒绝嵌套事务 |
| `plugin-manager` | `ctx.pluginManager` + 模型工具 `plugin_manager` + `dsh plugin` CLI | 共享 `operations.ts` |

顺带把几条行为钉一下。**config-editor** 的 `edit()` 写的是"活动 profile 的 patch"，只对 profile 根 Include 拥有的、可唯一寻址的行生效（README 的 Known Limitations）；home 层与 `--patch` 只参与优先级读取，**不是写入目标**。**hmr** 默认 `root: []`（base L28-L32），也就是"只做配置热重载，不监听模块"；headless/SDK/ACP 直接把 `hmr` 行 `disabled: true`（headless L33-L34）。**plugin-manager** 把注册表按顺序询问，`fallbackRegistries` 默认含 npmmirror（README 配置表），GitHub 仓库在 pnpm 之前先做 `git ls-remote` 预检，版本兼容豁免必须 `acceptRisk: true`（README "Version compatibility and exemptions"）。

当配置在运行中改变（HMR 或 config-editor 写盘），走的不是重启，而是 `reconcileProfilePatches`（[index.ts](../../packages/boot/app-boot/src/index.ts) L274-L303）：它把整份 patch 列表作为**一个完整的一代**重新应用到根 Include，等所有行更新 settle，再与改动前的失败清单逐一对比——**只有新增或变化的失败才抛出**，既有的失败行保持原状、不打断。这正是"配置热重载既可撤销、又不会因为一个一直坏着的可选行而永久卡住"的实现。它更新的就是 `mountRootInclude` 存下的那个固定 id 根 Include（`bootstrapIncludes.get(ctx)`，L277）。

### 3.6 bare 插件名解析与静态门禁

树里的行写的是 `name: '@deepseek-ai/dsh-llm'` 这样的 **bare 插件名**（裸包名）。Node 的解析器不认识它们，因为树在运行期才拼出来。DSH 的做法是**在解析层做拦截**：profile 目录的 `node_modules` 先解析，否则落到安装范围内的"运行时解析表"。`createRuntimeResolution`（profile.ts L441）从一个安装锚点做 BFS，收集 dependencies **和 peerDependencies**（L399-L401 的注释：Service Definition 以 peer 出现，比如 `dsh-subprocess`、`dsh-compaction`，但它们会被 out-of-tree 插件直接 import，所以必须一起收）。产出的 `RuntimeResolution` 是**冻结的**，启动后不再变（L506 的 `Object.freeze(this)`）。

还有一个容易忽略的维度：**Worker 与子进程**。运行时解析的拦截安装在主线程的 Node 解析器上；Worker 由 `profile-resolution/worker-bootstrap.ts` 各自再装一次，保证 worker 里的插件也按同一张解析表加载。

一旦有"手写 bare 名"，就有"手写错名"的风险。`scripts/verify-cordis-config.ts` 用几条**静态门禁**守住这里：

- `validateAppResolution`（L240）与 `bundlePluginDependencyErrors` / `packageTestPluginDependencyErrors`（L391、L310）检查每个 yml 里的 bare 名，必须出现在**正确 manifest** 的 `dependencies` 里。
- `metadataExpressionErrors`（L517）保证 entry 元数据的静态性、`!!js` 的合法位置。
- `validatePresetPlaneSeparation`（L139-L166）防"**平面双挂**"：任何 shipped preset 里的行，若同时还在 host 组合里是 active 的，就报"a row belongs to exactly one plane"（一行只属于一个平面）。这条防的正是 3.7 要讲的 isolate realm 陷阱。
- `validateClientHalvesDeclared`（L106）保证声明了 `dsh.client` 的包必须有 `./client` 出口，反之亦然。

这些门禁不是形式主义，而是"组合的正确性没法只看一个文件"这一事实的补偿：**树的形状是全局的，所以校验也必须全局。**

### 3.7 agent preset：每个会话的能力集

把镜头从进程拉近到会话。Web 版里，同一个 dsh 进程会服务多个会话，它们不该共用一套工具集——一个做代码编写的会话需要 `tool-bash`/`tool-fs`，一个只负责回答的会话可能只需要 persona。这就是 **agent preset**（智能体预设）：**每个 Agent（会话）的能力集**。

实现分三个包。

**声明侧** `packages/preset/agent-preset`：它是一个"声明行"插件（[src/index.ts](../../packages/preset/agent-preset/src/index.ts)）。三个要点：

```ts
// packages/preset/agent-preset/src/index.ts（L12-L29，节选）
export default class AgentPreset {
  static inject = ['agentPresets']
  static readonly [EntryGroup.key] = true          // ← 保留子行的 !!js 到各自 fiber
  static Config = z.object({ id: z.string().required(), /* name/description/order */ plugins: z.array(z.any()).required() })
  async* [Service.init]() {
    yield await this.ctx.agentPresets.register(this.config)   // register 返回 disposer
  }
}
```

`EntryGroup.key` 这个静态标记的含义是：**这一行的 `config` 本身就是 entry 列表**，所以 Loader 的插值要把它的子行 `!!js` 保留下来，留给子行自己的 fiber 去求值——否则 preset 里的 `!!js process.platform === 'win32'` 会在错误的上下文里被提前求值。

**注册侧** `packages/preset/agent-preset-registry`：`class AgentPresetRegistry extends TypertRemoteService`（[src/index.ts](../../packages/preset/agent-preset-registry/src/index.ts) L52），服务名 `ctx.agentPresets`。它的 `register()`（L81）**急切地** activate 一次：`createScope` + `mountPreset`（L103-L122）。它用一套 **Generation（代）** 管理版本：每个 preset 定义对应若干"代"，Agent 绑定到某一代；`revision` 被保留，所以**会话记录里的 preset id 在重启后能按 id 取到当前定义**（会话日志只存 id，不存整棵 preset 树）。`Config` 里有 `default` 与 `selectedDefault: Volatile`（L54-L57）——后者是"最近选过"的易失选择。

**挂载侧** [src/mount.ts](../../packages/preset/agent-preset-registry/src/mount.ts)：`PresetTree extends EntryTree` 是一棵**内存树**（`write()` 被覆写为空，L23——preset 从不写回磁盘，只有配置编辑器会持久化定义）。`mountPreset`（L204-L216）的准入流程是：`prepareProfileEntries` 准入 → `tree.root.update()` → `auditRows` 审计 → `leakedServices` 检查。

其中最关键的是 **isolate realm（隔离区）强制**（L204-L215）：

```ts
// packages/preset/agent-preset-registry/src/mount.ts（L204-L215，节选）
export async function mountPreset(ctx, id, plugins): Promise<PresetMount> {
  const tree = new PresetTree(ctx)
  ctx.effect(() => () => { tree.root.stop() }, 'agent-preset.tree')
  await tree.root.update(prepareProfileEntries(ctx, plugins as EntryOptions[], ctx.baseUrl))
  const audit = await auditRows(tree)
  const leaked = leakedServices(ctx, ctx.fiber)
  if (audit.failed.length > 0) throw new Error(audit.failed.join('\n'))
  if (leaked.length > 0) throw new Error(`Preset services require isolate realms: ${leaked.join(', ')}`)
  return { presetId: id, fiber: ctx.fiber, tree, key: scopeOf(ctx) }
}
```

`leakedServices`（L69-L83）扫描"本 subtree 发布进 **root realm** 的服务"：一个没有 `isolate` 的 provider 会把实现存在 root 的符号下，那正是泄漏；而一个在 `isolate` realm 里的 provider 存在 realm 私有的符号下，正确地**不**出现在这里。规则于是很清晰：**preset 里任何提供服务（provide a service）的行，必须用 `cordis:group` + `isolate:{<service>: true}`，把 provider 和它的全部消费者放进同一个 realm。** 否则两个会话各挂一个同名服务，第二个就撞车；或者 preset 局部 provider 遮蔽了 host 的路由，host 的贡献者反而够不着。

这正是 3.6 的 `validatePresetPlaneSeparation` 在防的同一件事，只不过门禁在**静态**侧、`leakedServices` 在**运行**侧。**Host/preset 平面判据**也由此而来：**一个被 realm 外行读取的服务留在 host 平面**（例如 jobs registry、subagent registry、skill registry、token meter——它们被跨会话读取或是进程单例）；而**会话级的工具、命令、压缩后端、计划模式移入 preset**。web-app 的 patch 用大段注释记下了这条判据（web-app L448-L563），并把 base 的 agent 面行逐 id `disabled: true`——注意是**禁用**，不是删除（见 3.8 与第 5 节误区二）。

`packages/bundle/web-app/presets/` 下随包发布四个 preset：`standard`（全能力）、`ptc`（`run_code` 形态）、`minimal`（仅 persona + 一个 `persistent-shell` group，`isolate: { terminals: true }`）、`cordis`（面向插件开发）。`standard.patch.yml` 里能看到正是这套 isolate 写法（L46-L92）：`planning` group `isolate: { planMode: true }`、`compaction` group `isolate: { compaction: true, toolResultPruner: true }`、`delegation` group `isolate: { workflowEngine: true }`。

### 3.8 运行时自改：extensions 与信任声明

DSH 最激进的一块在 `packages/extensions/`：**让 Agent 在运行中定义、运行、停止一个 Cordis 插件**，甚至带浏览器半。三个包分工：`tool-cordis`（只读发现）、`cordis-host-runner`（Host 半与生命周期）、`cordis-client-runner`（浏览器半），外加 `ui-cordis`（浏览器面板）。

**只读发现** [packages/extensions/tool-cordis/src/index.ts](../../packages/extensions/tool-cordis/src/index.ts)：注册两个工具 `cordis_inspect_list` 与 `cordis_inspect_query`（L23、L42），注入 `['tools', 'cordisInspect']`（L10）。Host provider 由独立行 `@deepseek-ai/dsh-tool-cordis/host` 注册一次（web-app L163-L164），registry 拒绝重复 id。

**生命周期** `DynamicCordisRunnerService`（[src/index.ts](../../packages/extensions/cordis-host-runner/src/index.ts) L131）拥有定义注册表、`node:vm` 沙箱、host-half fiber 生命周期与 invoke 处理表。动词是 `define → run → stop → undefine`：`define`（L159）预检语法但不执行、铸造 plugin/package id；`run`（L256）分 `mode: 'run'` / `'update'`；`stop`（L464）撤销 live 效果但**保留定义**；`undefine`（L218）连定义一起忘掉。带浏览器半的包会 emit `cordis/request-run`（L299）并**挂起等人批准**。

它对外广播四个前向事件（都在 client-safe 的 `./types` 子路径声明，由 `dsh-api-remotes` 允许投递到浏览器）：`cordis/request-run`（一个带浏览器半的激活在等页面）、`cordis/request-run-resolved`（该请求离开可应答状态）、`cordis/dynamic-package`（某个精确的 Plugin/Package 激活已上线）、`cordis/dynamic-retract`（某次激活被撤回）。它们与[第4章](./第4章-事件驱动-五路派发与三个事件域.md)的 `emit` 模式一致——只作通知，不改变已提交的状态。

**信任声明**是本节的落点。README 的 "Trust stance"（[README.md](../../packages/extensions/cordis-host-runner/README.md) L60-L62）写得毫不含糊：

> The sandbox isolates globals but is not a security boundary: ... Treat a dynamic package like bash access.

（沙箱隔离全局对象，但**不是安全边界**——请把动态包当作 bash 访问来对待。）具体约束有几条必须记住：

- **定义是 session-scoped 加进程本地**：别的会话读不到，重启清空，历史日志只留参数与回执（README L56-L58）。
- **没有任何模型工具能创建动态定义**（README L119）。模型侧只有 `tool-cordis` 的只读发现；持久安装一律走 Plugin Manager。
- **挂起的浏览器请求没有超时**：它等人，直到发起的那一轮被取消（Known Limitations）。

把 `vm` 沙箱不是安全边界这一点想透：它挡的是**意外**（误触全局、误用模块），不是**恶意**。所以凡是"能跑代码"的口子，DSH 给的定性都是"等价于给你一个 shell"。这种诚实比虚假的安全感更专业。

### 3.9 三条"不写代码的扩展"：skill、MCP、hooks

不是每个扩展都要写 Cordis 插件。DSH 留了三条"不写代码"的路。它们接的都是[第4章](./第4章-事件驱动-五路派发与三个事件域.md)、[第5章](./第5章-Agent-Loop-让模型转动起来的引擎.md)的既有扩展点。

**其一，skill（技能）。** 一个 skill 是一个目录束 `<name>/SKILL.md` 或平铺文件 `<name>.md`（[packages/skill/skill-filesystem/README.md](../../packages/skill/skill-filesystem/README.md)）。YAML frontmatter 必需 `name` + `description`，可选 `whenToUse`、`metadata`、`disable-model-invocation`、`user-invocable`。根目录按 **rank 优先级**扫描（README 的 "Roots and priority"）：

| Rank | 来源 | 路径 |
|---|---|---|
| 100 | `project-dsh` | `<projectRoot>/.dsh/skills` |
| 200 | `project-agents` | `<projectRoot>/.agents/skills` |
| 300 | `custom` | `Config.customSkillDirs` |
| 400 | `user-dsh` | `<dshHome>/skills` |
| 500 | `user-agents` | `<agentsHome>/skills` |
| 600 | `bundled` | `Config.bundledSkillDir` |

本仓库自己的 `.agents/skills/` 里就有十几个 `dsh-*` 维护者技能；`packages/preset/agent-preset/skills/` 里则有面向产品会话的 creator skills——`cordis-plugin-development`（含模板）、`cordis-composition-reference`（**Loader patch 方言参考**，本章 3.3 的速查表就是它的浓缩版）、`editing-cordis-compositions`。注意"加速方式"：skill 的正文按需加载，目录与正文**生命周期分离**（发现时只解析 frontmatter，每次 load 重新读文件），所以改正文不需要版本号或缓存失效。

**其二，MCP（Model Context Protocol）。** 每个 MCP 服务器一个行条目，配置 `serverName` + `transport: stdio | streamable-http`（[packages/mcp/mcp-client/README.md](../../packages/mcp/mcp-client/README.md)）。工具以**稳定限定名** `mcp__<serverName>__<tool>` 注册进 `ctx.tools`（L75）——同一命名形态与 Claude Code、Codex 相同。注意限定名是**公开契约**：`serverName` 是本地配置命名空间，**绝不用远端不可信的 `serverInfo.name`**，这样会话历史与权限规则能在重连、重同步、HMR 之后存活。服务器 instructions 以**字面文本**并入已记录的 system prompt（呼应[第8章](./第8章-消息系统-会话日志即模型记忆.md)"模型可见即已记录"）。重连退避从 500ms 翻倍到 30s、最多 10 次；`failOnStartupError` 可以把它从"启动后报错"升级为"激活失败"。base 已挂 `mcp-resources`（base L492-L493），跨连接共享资源发现与读取。

**其三，hooks。** [packages/hooks/](../../packages/hooks/) 是 Claude Code / Codex 的桥，复用你**现有的 `hooks.json`**。共享引擎 `hook-protocol` 的规则：**只有 command hook 会运行**（`http`/`mcp_tool`/`prompt`/`agent` 跳过并警告）；**exit 2 表示阻断并把 stderr 展示为原因**；hook 可以附加模型可见的上下文；`{"continue": false}` **只记录、不停止运行**（因为拦截点没有"硬停机"原语）；其余任何 exit code 都是非阻断失败。hook 挂的是[第4章](./第4章-事件驱动-五路派发与三个事件域.md)、[第5章](./第5章-Agent-Loop-让模型转动起来的引擎.md)的 typed-Decision 扩展点，并把自己的过程记录成仅日志的 `hook/invoked` / `hook/result` 事件。

### 3.10 用户态四件套：settings、credentials、identity

配置不只是开发者的事，终端用户也能在 UI 里改。四件套（都在 base 层）：

- **settings**（`ctx.settings`）：从每个插件的 Config schema **派生活配置表单**；编辑持久化到活动 profile 的 patch 并立即应用；`volatile` 字段的更新不触发 remount。
- **credentials**（`ctx.credentials`）：用**命名引用**而非内嵌值；本机存在 `$DSH_HOME/.credentials.yaml`，环境变量覆盖优先。
- **identity**：`$DSH_HOME/.anonymous-user-id`，每个 harness home 一个匿名 UUID，删掉即重置。

它们合起来说明了配置系统的一个尺度：**同一套 patch 层，既服务开发者（手写 `cordis.patch.yml`）、也服务终端用户（在 UI 里点选）**，只是 UI 写回的是活动 profile 的那一层。

## 5. 常见误区

**误区一："两个 patch 给的 `config` 会深合并。"** 不会。patch 对 `config` 是**整体替换**（vendor/include L120-L123）。你必须重述想保留的每个键，否则没重述的键就丢了。base 与 web-app 的开头注释都在反复提醒这一点（base L6-L10、web-app L5-L6）。误以为深合并，是读这套配置最常见的错误。

**误区二："`disabled: true` 就是把行删了。"** 不。它是**禁用**——行还在，只是不激活。为什么共享 base 之上的层从不"删行"？web-app 的注释给了答案（L455-L457）："base 是共享的，一行若不在某个 surface 覆盖里出现，就等着**哪天有人重排组合时静默复活**。" 删除是"现在没有"，禁用是"这一层明确说不要"。前者会在未来某次重排里失效，后者不会。

**误区三："`!!js` 哪里都能写。"** 错。它只对 `config`（对该插件自己的 context 求值）和 `disabled`（对 Loader context、每次挂载决策）生效；其余元数据必须是字面值，`scripts/verify-cordis-config.ts` 的 `metadataExpressionErrors`（L517）会让任何埋在 `id`/`name`/`group`/`inject`/`intercept`/`isolate` 里的 `!!js` 门禁失败。

**误区四："preset 和 profile 是一回事。"** 不是。**profile 决定整个进程挂什么，preset 决定每个会话看到什么。** 同一个 profile（比如 web）下的不同会话可以挂不同的 preset；profile 是进程级、存在磁盘的组合，preset 是会话级、声明在 patch 里的能力集。两者都用 patch 行与 Cordis 服务，但作用域与生命周期完全不同。

**误区五："动态插件是一种持久安装。"** 不是。`packages/extensions` 的定义是 **session-scoped + 进程本地**：别的会话读不到，重启清空，历史日志只留参数与回执。真正的**持久**安装走 Plugin Manager（`dsh plugin` / `plugin_manager` 工具），因为它会把依赖写进 profile 的 `package.json` 与 `node_modules`。把两者混为一谈，会以为重启后动态插件还在——它不在。

**误区六："MCP 工具名就是服务器给的原始名。"** 不是。模型看到的是稳定限定名 `mcp__<serverName>__<rawName>`（如 `mcp__github__create_issue`）。原始名只在 `tools/call` 的**线路上**使用，从不暴露给模型、也从不从公开名反推。这个命名是**钉死的契约**，改动会破坏会话历史与权限规则。

**误区七（送一条）："配置写错了会安静地忽略。"** 恰恰相反。存在的 patch 文件不可应用就直接抛错（`loadOverlayPatches`）；空文件会失败（必须显式 `[]`）；必需 id 缺失是 `StartupError`；`.env` 里写引导名会被拒绝。DSH 的原则是 **fails loud，越早越好**。学会用 `dsh --profile <name> --dump-config` 看组合出的树，是排查配置问题的第一步。

## 6. 动手环节

四个练习，由浅入深。前两个可以直接在命令行上做，后两个更适合纸面加小组讨论。

**练习一：看一次真实的组合。** 在仓库里跑：

```sh
pnpm dsh --profile web --dump-config
```

观察输出：每一段行前面都有 `# ==` 注释，标出这组行来自哪个文件、又被哪些层 patch 过（实现见 app-boot 的 `renderConfigDump`，L431-L494）。再跑一次 `--dump-default-config`，对比它少了 profile 自己的层与 `--patch` 覆盖。想一想：为什么 dump 与真正 boot 出来的树用的是**同一个** patch 算法（`applyEntryPatches`）？

**练习二：读两个 patch 文件。** 打开 [packages/bundle/base/cordis.patch.yml](../../packages/bundle/base/cordis.patch.yml) 与 [packages/bundle/web-app/cordis.patch.yml](../../packages/bundle/web-app/cordis.patch.yml)。回答：(a) base 里有几行用了 `!!js`？分别在哪两个字段上？(b) web-app 里哪些 base 行被 `disabled: true` 关掉了？它们为什么在 base 里存在而在 Web 里禁用？(c) `system-prompt` 这一行，base 给的是什么 config，web-app 又重述了什么？

**练习三：用 Grep 找 isolate。** 在 `packages/bundle/web-app/presets/` 下搜索 `isolate:`。数一数 `standard` preset 里有几个隔离组、各自隔离了哪些服务。然后对照 `packages/preset/agent-preset-registry/src/mount.ts` 的 `leakedServices`，回答：如果 `compaction` 组没有 `isolate: { compaction: true, toolResultPruner: true }`，两个会话同时挂 `standard` 时会发生什么？（提示：第二个会话的服务注册会撞在第一个上，或者 preset 局部 provider 遮蔽 host 路由。）

**练习四：设计一个新发布形态（纸面作业）。** 假设 DSH 要加一个"只读审查"形态：不给任何写工具，只允许读文件、搜索、跑只读命令，并把结果汇总。不要写代码，回答四个问题并到源码里验证答案：

1. 它应该是一个新的 **bundle** 还是一个新的 **preset**？（提示：它需要共享 base 的持久化与模型适配器吗？它是"整进程形态"还是"每会话能力集"？）
2. 如果做成 bundle，它的 `package.json` 里 `dsh.bundle.patch` 指向什么？它用 `insert` 加行，还是用 `id` 覆盖 base 的行来禁用写工具？
3. 为什么"禁用 base 的写工具行"比"在 base 里删掉它们"更安全？（回到误区二。）
4. 若它还要给每个会话一个不同的只读范围，这个范围该落在 bundle / preset / 还是 profile 的 `cordis.patch.yml`？

这道题的目的是让你走一遍 DSH 的决策路径：**先问"进程级还是会话级"，再问"用哪一层"，最后才问"写哪几行 patch"。**

## 7. 本章小结

1. 运行中的 dsh 是一棵**从有序层组合出的插件树**；没有特权主程序，扩展 = 挂一个插件行，而不是改源码。
2. 三个组合单位：**profile**（命名的进程组合，`$DSH_HOME/profiles/<name>/`，`dsh.profile.bundles` 有序清单 + 用户 patch）、**bundle**（声明 `dsh.bundle.patch` 的 npm 包，贡献一层配置行）、**agent preset**（每个 Agent/会话的能力集）。
3. 层叠顺序（后者胜）：空根 `[]` → 各 bundle 的 patch（`dsh.profile.bundles` 顺序）→ profile 自己的 `cordis.patch.yml` → home 层 `$DSH_HOME/cordis.patch.yml` → `--patch` 覆盖 → launcher 的遥测开关 patch；权威实现在 `readProfilePatches`。
4. patch 方言：`insert` 追加（有 `id` 且指向 `group: true` 则插入其 `config` 内）；`id` 定向既有行，逐字段替换，**`config` 整体替换不深合并**；truthy `name` 是断言而非改名；无 id / 无目标的 patch 警告跳过。
5. `!!js` 只对 `config`（对该插件 context 求值）与 `disabled`（对 Loader context、每次挂载决策）生效；其余元数据必须字面，`verify-cordis-config` 会拒绝。
6. **禁用而非删除**：共享 base 之上的层用 `disabled: true` 关行，因为删除的行会在未来重排组合时静默复活。
7. boot 链五个包：`app-boot`（组合/启动/dump）、`cmdline`（`ctx.cmdlineArgs`/`appExit`/`appReady`）、`config-editor`（写回 patch 层并即时应用）、`hmr`（模块与配置进同一串行队列）、`plugin-manager`（注册表、GitHub 预检、版本豁免）。
8. bare 插件名靠解析拦截层 + 冻结的 `createRuntimeResolution`（含 peerDependencies）供给；静态门禁 `verify-cordis-config` 校验依赖声明、元数据静态性、预设平面分离、client halves。
9. fails loud：存在却不可应用的 patch 必须抛错；空 patch 失败（显式 `[]` 才是禁用层）；必需 id 缺失即 `StartupError`；`.env` 引导名被拒（home 层豁免四个代理名）。
10. agent preset 与 profile 的区别在**作用域**：进程级 vs 会话级。`AgentPresetRegistry` 用 Generation 保留版本，会话只存 preset id，重启后按 id 取当前定义。
11. **isolate realm 强制**：preset 内任何提供服务者必须 `cordis:group` + `isolate`，把 provider 与全部消费者放进同一 realm；`leakedServices` 扫描发布进 root realm 的服务，任何泄漏都拒绝挂载。
12. Host/preset 平面判据：被 realm 外行读取的服务（jobs/subagent/skill registry、token meter）留 host 平面；会话级工具、命令、压缩后端、计划模式移入 preset。
13. `packages/extensions` 的运行时自改（`define`/`run`/`stop`/`undefine`）是 session-scoped + 进程本地；**vm 沙箱不是安全边界**，定义不持久、模型工具不能创建定义，持久安装走 Plugin Manager。
14. 三条"不写代码的扩展"：**skill**（目录束/平铺 + frontmatter，根按 rank 100..600 扫描）、**MCP**（`mcp__server__tool` 稳定限定名、退避重连）、**hooks**（exit 2 阻断并展示 stderr，`continue:false` 只记录）。
15. 用户态四件套（settings 派生表单写回活动 profile patch、credentials 命名引用、anonymous identity）说明同一套 patch 层既服务开发者，也服务终端用户。

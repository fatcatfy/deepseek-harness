# 第11章 会话管理：持久化格式、迁移与分叉

## 1. 本章导读

第 8 章告诉你：会话日志（session log）就是模型的记忆，`SessionEvent` 的只追加序列是真源。第 10 章告诉你：对话太长时，上下文压缩（compaction）通过"表面替换"（surface replacement）在模型可见历史上覆盖一段范围，而原始事件永久留在日志里。

这两章都站在"一个正在运行的 `Session` 对象"的视角。可现实问题是：进程会退出，机器会重启，用户第二天打开客户端，看到的是昨天的那条会话。于是日志必须**落盘**，落盘就必须回答一个第 8 章没有回答的问题——**文件格式会不会变，变了怎么办？**

本章要讲的，是 DSH 在"日志落盘"这一侧的完整工程：

- **`SessionPersistence` 接缝（capability seam）**：持久化的服务定义、`SessionHandle` 句柄契约、`append` 与 `flush` 的语义差别。
- **JSONL 后端的物理布局**：一个会话目录里长什么样，文件名如何编码"格式代"。
- **`SESSION_FORMAT_VERSION` 机制**：为什么版本是一个单调整数，由写者而非读者决定。
- **相邻迁移链（adjacent migration chain）**：为什么 v0→v1→v2→v3→v4 是五个包、四条边，一包一步。
- **代数选择与独占发布（exclusive publication）**：已提交的格式代永不移动、永不覆盖、永不删除。
- **恢复（restore）流程**：一个旧格式文件如何一步步流过整条链，变成一个当前 `Session`。
- **分叉（fork）与崩溃恢复（crash recovery）**：如何从一条既有历史派生出新会话，以及如何把一次崩溃的尾部配平。
- **SQLite 的对照**：为什么非会话数据用"原地重建"，而会话日志刻意反其道而行。

学完本章你应该能回答一句话：**"用户机器上已经有几百万个旧格式会话文件，你要改格式，怎么办？"**

本章与第 8 章（日志即记忆）、第 10 章（表面机制，迁移必须重排引用）、第 12 章（插件与配置组合，会话格式的静态目录不依赖插件挂载）紧密相连，建议先读第 8 章再回来。

## 2. 从一个问题出发

假设你的产品已经发布了一个会话格式，我们叫它 **v0**。用户机器上散落着几百万个 v0 会话文件。现在你发现 v0 的结构有问题，必须改成 v1。你有两条直觉上都想走的路，但两条都通向灾难：

- **原地迁移（in-place migration）**：读到旧文件就覆盖成新格式。问题在于，覆盖不是原子操作。如果进程在写入一半时崩溃，用户就得到一个既不是 v0 也不是 v1 的半截文件——**丢数据**。而且旧格式的读方再也拿不到原文，无法回滚。
- **不迁移**：新版本只读新格式。用户升级后打开旧会话，直接报错——**读不了**。

DSH 的答案是第三条路，也是本章全部内容的浓缩：

> **只读时，在内存中流式迁移；写入时，独占发布一个"新代"文件；旧代文件永不删除。**

请注意三个关键词。**内存中**：读一个旧文件不需要先把它写回磁盘，`open(id, 'read')` 直接消费迁移结果。**新代**：v1 写到 `session.v1.jsonl`，v0 的 `session.jsonl` 原封不动躺在旁边。**独占**：发布新代时用内核级原语保证"文件已存在就失败"，绝不覆盖。

这条规则的正式表述，写在 `.agents/notes/implemented/architecture/2026-08-31-released-session-format-migrations.md` 里：

> Migration never moves, replaces, or deletes a committed generation and writes only the final current target; intermediate versions exist only as stage state.

翻译过来：迁移从不移动、替换或删除一个**已提交的格式代**（committed generation），只写最终的当前目标；中间版本只作为迁移阶段（stage）的内存状态存在。

同一个"复用既有历史"的问题还有第二种形态：不是复用一条**旧格式**的历史，而是复用一条**同格式、别人的**历史。这就是**分叉（fork）**——从会话 A 的某个位置切一刀，派生出一个子会话 B，B 继承 A 的前缀作为自己的起点。它和迁移共享同一个约束来源：**已提交的事件永不重写**，所以 B 只能是 A 前缀的副本加自己的新事件。

本章用"代（generation）"来统一理解这两件事：文件有格式代，事件位置有继承切割（inherited cut）。理解了"不可变"，你就理解了整章。

## 3. 正文

### 3.1 会话组包地图

先把 `packages/session/`（会话组）和 `packages/session-query/`（检索组）的包逐个对号入座。这是本章的主干，后面每一节都在细化其中一行。

**格式抽象层（与后端无关）**

- `packages/session/session-format`：逻辑格式类型与迁移接口。这里定义了 `SessionFormatHeader`、`SessionFormatEvent`、`SessionFormatArtifact`，迁移接口 `SessionFormatMigration` / `SessionFormatMigrationStage` / `SessionFormatChain` / `SessionFormatCatalog`，文件名规范 `sessionFormatLogFilename`，以及编译迁移链的 `createSessionFormatChain`。它不关心文件，只关心"逻辑事件如何从一代变成下一代"。
- `packages/session/session-format-catalog`：**生成**出来的静态目录。核心文件 `src/generated.ts` 由 `scripts/gen-session-format-catalog.ts` 生成，把 v0..v4 五个编解码器（codec）和四条迁移边装配成一个 `sessionFormatCatalog`。它的注释说得非常清楚：直接 import 使"历史可读性不依赖已挂载的插件"。
- `packages/session/session-format-v0-to-v1` … `session-format-v3-to-v4`：每个包**恰好拥有一条相邻边**（adjacent edge）vN→vN+1。这就是"一包一步"。

**持久化层**

- `packages/session/session-persistence`：服务定义（Service Definition）。`src/index.ts` 里的抽象类 `SessionPersistence`（约 L135）暴露 `create`/`open`/`stat`/`list`/`flush`；`src/handle.ts` 定义 `SessionHandle`；`src/storage-contract.ts` 是所有后端共享的校验；`src/errors.ts` 是错误分类。**这一层没有任何物理格式知识。**
- `packages/session/session-persistence-jsonl`：交付的 JSONL 后端实现。物理布局、文件名、zstd 编码、写租约、代发布、Worker 验证全在这里。这是本章物理细节的主战场。

**周边（本章只带过，第 8 章已讲）**

- `session-projection` / `session-projection-cache`（第 8 章的派生读模型），`session-title` / `session-title-llm`（标题），`session-stats`，`session-telemetry` / `session-telemetry-otel`，`session-log-deepseek`（官方上报），`session-checkpoint-policy`（第 8 章）。

**检索组（第 8 章衔接）** `packages/session-query/`：`session-query`（`ctx.sessionQuery`，`SessionQueryEngine`）、`session-query-sqlite`（FTS5 派生索引）、`tool-session-query`（模型侧工具）、`session-log-export`（ZIP 归档）。

一句话总结分工：**抽象层定义"怎么变"，catalog 提供"现成的变体"，后端负责"什么时候写、写到哪个文件"。**

### 3.2 `SessionPersistence` 接缝：句柄、`append` 与 `flush`

第 7 章讲"能力接缝"时说过：一个接缝由服务定义、服务提供方、消费方三种角色组成。持久化接缝的服务定义在 `packages/session/session-persistence/src/index.ts`：

```ts
export abstract class SessionPersistence extends Service {
  abstract create(header: SessionHeader, options?: SessionPersistenceCreateOptions): Promise<SessionHandle>
  abstract open(id: SessionId, access: SessionAccess, options?: SessionPersistenceOpenOptions): Promise<SessionHandle>
  abstract flush(): Promise<void>
  abstract stat(id: SessionId, options?: SessionPersistenceStatOptions): Promise<SessionPersistenceSnapshot | undefined>
  abstract list(options?: SessionPersistenceListOptions): Promise<readonly SessionPersistenceSnapshot[]>
}
```

注意一个设计取舍：**所有日志读写都不经过按 id 寻址的服务方法，只经过逐会话的句柄**。句柄类型在 `src/handle.ts`（`SessionHandle`，约 L59）里定义，它有几个你必须记住的性质：

- `access: SessionAccess`，取值 `'read' | 'write'`。一种句柄类型同时服务两种访问；在 `read` 句柄上调用 `append` 是运行时的 `SessionReadOnlyError`，而不是类型层面的分裂。
- **单写者（single writer）**：进程内第二次 `open(id, 'write')` 会以 `SessionAlreadyOwnedError` 拒绝。
- `inheritedEventCount: SessionLogOffset`：**继承切割长度是存储元数据，和 header 一起走，绝不进入可回放的事件日志**。这是本章反复出现的模式——带正文的存储操作需要"header + cut"两件套，即 `SessionStorageMetadata`。

最关键的语义差别在 `append` 与 `flush`：

- `append` 是 **best-effort（尽力而为）**：一旦 resolve，这批事件已"被接受、有序、本实例可见"，但**不承诺崩溃存活**——后端可以把物理写缓冲起来。
- `flush` 才是**持久性屏障（durability barrier）**：一旦 resolve，所有已确认的 append 都durable了，且会话对其他进程materialize（实体化）可见。

还有一个你可能没注意到的可见性规则：`create` 返回的那一刻，会话在本进程内就可被 `stat`/`list`/`open` 观察到，哪怕后端把物理实体化推迟了（纯优化）；其他进程只有在实体化后才能看到；**一个在崩溃前从未实体化的会话等于从未存在**。

错误分类都收敛在 `src/errors.ts`。其中 `SessionFormatUnsupportedError` 和 `SessionPersistenceCorruptionError` 的区别值得单独记：前者表示"日志完好，但本构建无法忠实解读"（提示升级 harness），后者表示"数据真的坏了"。方向的措辞由 `sessionFormatVersionRefusal(id, version)`（L133）统一生产：未来版本 → "upgrade the harness"；比支持版本旧又无升级路径 → "no upgrade path"。

### 3.3 物理布局：项目目录、会话目录、格式代文件名

JSONL 后端的物理布局全在 `packages/session/session-persistence-jsonl/src/format.ts`。它的形态是：

```
<root>/<projectKey(cwd)>/<encodeSegment(sessionId)>/session[.vN].jsonl[.zstd]
```

**`root` 是必填配置，没有默认值。** 后端 `Config`（`src/index.ts` 约 L90-101）明确注释：默认 `process.cwd()` 会随着进程 cwd 变化（bash 调用、子进程）把会话文件撒得到处都是，所以必须由部署显式指定。

从内往外看三个**安全 / 可读性编码**：

- **会话目录名** `encodeSegment(sessionId)`（L199）：`SessionId` 是一个**未校验的 branded string**，可以是任意 JS 字符串，所以必须先做**单射（injective）路径段编码**再进文件系统。安全字符（`A-Za-z0-9._-`）保持原样，其余代码单元（包括 `~` 本身）转成 `~XXXX`；`.` 和 `..` 特别处理成 `~002E` / `~002E~002E`，防止一个"看起来安全"的整段造成目录穿越。它操作的是 UTF-16 代码单元，因此孤立代理项也能被保留。
- **项目目录名** `projectKey(cwd)`（L225）：把 cwd 变成人类可读、可导航的目录名。分隔符（`/`、`\`、`:`）折叠成 `-`，不安全代码单元同样用 `~XXXX`，最后包成 `--<slug>--` 并截断到 251 字符。注意注释原话：**分隔符替换与截断是有意有损的**——它服务的是"人能看懂"，不是"能还原"。没有 cwd 的会话归入 `_no-cwd`（L255）。
- **代文件名**：`sessionFormatLogFilename(version)` 在 `session-format/src/filename.ts`（L14）。v0 保留最初的 `session.jsonl`；**v1 及以后在 `.jsonl` 前带小写数字 `.vN`**，即 `session.v1.jsonl`、`session.v4.jsonl`。压缩后缀由后端决定：默认 `zstd`，得到 `session.v4.jsonl.zstd`。解析函数 `parseSessionFormatLogFilename` 只承认规范名：临时名、大写、前导零、`.v0`、带压缩后缀的名字都不是一个已提交的格式代。

**首行是 header。** `format.ts` 内部的 `HeaderLine`（约 L83-94）字段为：`type:'session'`、`version`、`id`、`createdAt`、`cwd?`、`parentSession?`、`isSeeded`、`origin?:'subagent'`、`delegationDepth`、`agentPreset?`。这里要划一条重点：

> **继承切割长度不在 header 里。** 物理 header 只带 `isSeeded` 这一个谱系 bit；精确的切割长度由**最后一个带 `inherited:true` 的 `session/end-seed` 事件**承载，只有读正文之后才能确定。

原因回到 3.2 的取舍：切割是"带正文的存储操作"要用的元数据，而事件日志是**可回放**的；把一个纯存储事实塞进 header，会让"header 能不能单独表达一个会话"和"日志能不能独立回放"两件事纠缠不清。所以物理 header 只做无正文的元数据，切割留在正文里的标记事件。

一行事件长这样（形态取自 v0 历史样本）：`{"type":"user/message","seq":1,"time":3,"data":{...},"surfaceOp":"append"}`。仓库里有一份真实形状的历史 fixture：`packages/session/session-persistence-jsonl/tests/fixtures/released-v0-real-shapes.jsonl`，它的首行是 `{"type":"session","version":0,...}`，注意它**没有 `isSeeded`**——它属于 v0 编解码器，不是当前 `HeaderLine`，这正是"历史物理 header 在进入 `SessionHeader` 接口前会被翻译"的样例。

### 3.4 `SESSION_FORMAT_VERSION`：版本由写者决定

版本常量只有一个手工维护处，位于 `packages/core/session/src/types.ts`（L89）：

```ts
export const SESSION_FORMAT_VERSION = 4
```

它的 JSDoc 值得逐句读，因为这里藏着整套机制的设计意图：

- **单个单调整数，没有 major/minor 拆分。**
- **"是否需要 bump 由写者产出什么决定，绝不由新读者能接受什么决定。"** 换句话说，判据是"一个旧 runtime 还能不能**语义正确地**处理新日志"，而不是"新 runtime 能不能解析旧日志"。JSDoc 特意强调："parses without error" 不是 correctness——静默跳过一段影响重建的内容就是一次**错误读取**。
- **只有结构性变化才 bump**：header 形状、`SessionEvent` envelope、核心事件语义、或表面机制（`SurfaceEventType` 集合与 `SurfaceOp` 变体）。**新增一个普通事件类型不 bump**——它用每个事件上的 `ignorable: true` 守卫来吸收词汇增长（衔接第 8 章）。
- 拿不准就 bump：一个近乎恒等的升级步几乎免费，而漏掉一次 bump 会让旧 runtime 静默读错新日志。

存储侧如何执行这条常量？有两个入口。第一，JSONL 后端在解析 header 时先跑 `refuseForeignFormatVersion`（`format.ts` L340）：版本不是当前值就立刻抛 `SessionFormatUnsupportedError`，**在验证当前 header 形状、解码任何事件行之前**。注释解释了原因：未来格式未必满足本构建的结构校验，用户必须看到"升级 harness"，绝不能看到"损坏"。第二，共享的 `assertVersion`（`session-persistence/src/storage-contract.ts` L46）在任何后端入口统一执行同一判断。

`session-format-catalog/src/generated.ts` 顶部的注释点明了另一条纪律：生成的目录里有一个 `currentVersion: 4` 和 `sessionFormatCatalogOptions`，装配出 `sessionFormatCatalog`。**catalog 的当前版本必须和 `SESSION_FORMAT_VERSION` 一致**——`session-persistence-jsonl` 的构造函数里就有一处启动断言（`src/index.ts` 约 L273）在检查这一点。

### 3.5 相邻迁移链：为什么一包一步

现在到本章的灵魂。先看迁移接口本身，`session-format/src/types.ts`：

```ts
export interface SessionFormatMigration {
  readonly name: string
  readonly fromVersion: number
  readonly toVersion: number
  migrateHeader(header: SessionFormatHeader): SessionFormatHeader
  createStage(input: SessionFormatMigrationStageInput): SessionFormatMigrationStage
  validateTargetHeader(header: SessionFormatHeader): void
}
```

`createSessionFormatChain`（`chain.ts` L41）编译时做两件硬性检查：每条边必须**相邻**（`defineSessionFormatMigration` 里 `to !== from + 1` 直接抛错），且从 0 到 `currentVersion` 的每一段都必须存在、不重复、不越界。任何缺口都会在编译期变成 `SessionFormatUnsupportedMigrationError`。

**为什么一包恰好一条边？** 因为每条迁移边是有状态、可独立维护、可独立冻结的转换器。把它们拆成独立包，带来三个具体好处：

1. **已发布语义可冻结**。v0→v1 的 `codec.ts` 一旦发布就是"released v0 codec"，v1→v2 复用它而不是复制它（`session-format-v1-to-v2/src/index.ts` 直接 re-export `releasedV1SessionFormatCodec`，而 v1 codec 又来自 v0 包）。链上每一环的输入输出语义固定在它自己的包 README 里。
2. **历史可读性与插件无关**。`generated.ts` 直接 import 五个 codec 和四条边，所以**在 feature 插件挂载之前**，历史格式就能被恢复。这就是决策记录里 Alternatives 那条被否决的方案——"Let mounted plugins register migrations"——被拒的原因：那会让历史可读性变成部署相关的。
3. **拒绝策略归**入**边，而不是归入当前校验**。内容准入（content admission）属于**进入的那条边**：保留一段不认识的 block 但不懂它的字段，无法证明迁移保持了它的含义。所以 v2→v3 用一套历史 kind 集合审查它自己负责的位置，不认识的 JSON 保持不解释。收窄当前接受度或改冻结的前驱校验器都会改变独立的承诺，而不是确立安全的转换。

**每条边是一个有状态的阶段（Stage）。** 决策记录说得直白："迁移是有状态的，尽管 API 曾把它呈现成一次性函数。"v0→v1 要追踪消息身份与重试身份，v1→v2 要缓冲一个未结算的 Assistant attempt、追踪它后面被阻塞的事件、维护新旧序列引用。所以协议被改成了：

```ts
export interface SessionFormatMigrationStage {
  transformEvent(event, context): void
  transformRun(run, context): void
  finish(context): number
}
export interface SessionFormatMigrationContext {
  emitEvent(event): void
  emitRun(run): void
}
```

`emitEvent`/`emitRun` 是**同步**的。生产者自己声明"我发的是标量事件还是一条紧凑 run"，热路径永远不用从解析出的文件对象上猜测类别。调用方持有调度权，并把 context 传给每次操作，而不是往 stage 构造函数里注入回调——这样 stage 的构建与下游接线解耦。一次输入可以发出零个、一个或多个输出，**不需要分配临时返回数组，也不需要内部输出队列**。

链路的样子（决策记录原文）：

```
JSONL record
  → released physical row decoder
  → v0-to-v1 stage
  → v1-to-v2 stage
  → v2-to-v3 stage
  → v3-to-v4 stage
  → current event collector
```

链路里**没有 `flatMap`、没有展开复制、没有中间版本事件数组物化**。`SessionFormatEventRun` 是这里的明星：它是"一个编解码器拥有的紧凑 run"，带 `runType`、`firstSeq`、`eventCount` 和一个 `expand()`。v0 与 v1 的打包 Assistant chunk 是一整条 run；v0→v1 与 v1→v2 都实现了 `transformRun`，所以打包 chunk 可以**不先展开成几百万个普通事件**就抵达折叠边。决策记录记下了一个具体数字：一份真实 v0 日志的 914 万展开事件，被折叠成 72,784 个当前事件，全程无需让两种表示同时存在。v2→v3 与 v3→v4 没有 `transformRun` 的专门处理，就回退到 `run.expand()`。

编译期如何接线？`CompiledSessionFormatMigrationStream`（`chain.ts` L208）在构造时**逆序**把 stage 串成一个 context 链（下游先建、上游指向下游），这样 `emitEvent` 从链头流到链尾。`finish()` 则**按源到目标顺序**结算每个 stage，让每个 stage 有机会在下游关闭前吐出自己的尾部事件。`finish` 返回的是目标的精确继承切割；如果一个 stage 事先声明了 `headerInheritedEventCount` 却最终算出不同值，会直接抛错。

### 3.6 代数选择与独占发布

一个会话目录里可能同时躺着 `session.jsonl.zstd`（v0）和 `session.v4.jsonl.zstd`（当前）。**选哪一代？** 后端 `resolveGenerationInDirectory`（`session-persistence-jsonl/src/index.ts` L1447）的规则是：读目录、用 `parseGenerationLogFilename` 筛出规范名、**取数字最高的 canonical generation**作为唯一权威源（`sourcePath`/`sourceVersion`），并同时算出 `currentPath`。

两条入口路径对"选择"的后续处理不同，这是本章必须分清的一对：

- **只读 `open(id, 'read')`**：`requireStoredLog`（L514）解析源。若源就是当前版本，直接稳定读取；若源是历史版本，**解码并组合相邻迁移链一次**，得到当前逻辑事件，但**不发布**——读句柄直接消费内存中的迁移结果（`PreparedStoredLog.status === 'prepared'`，作为 `primed` 状态交给句柄）。
- **只写 `open(id, 'write')`**：Claim 单写者 → 获取租约 → `requireStoredLog` → 若结果是 `prepared`，调用 `publishStoredMigration`（L692）执行**独占发布**，发布成功后才返回可写句柄。若结果是 `current`，直接用。

因此 `stat`/`list` 的规则是：**header-only，只翻译受支持的历史 header，不读 body、不发布后继**（`readGenerationHeader` L1087）。它们让"列一下有哪些会话"不会退化成一次全量正文扫描。

**独占发布**的实现在 `generation.ts` 的 `prepareJsonlMigration` / `publishPreparedMigration`。流程是：

1. **准备（prepare）**：`readStableSnapshot`（L262）稳定读取源文件——stat → read → 再 stat，两次 identity 一致才接受；若持续有 append 重叠，第二次读取后返回已提交前缀而不是无限饥饿。然后 `decodeStreamingMigration` 流式解压、逐行送进迁移链，产出当前 artifact。
2. **编码到临时文件**：`writeSyncedTemp`（L715）在**同目录**用 `wx` 独占创建 `session.migration.<token><suffix>.tmp`，逐块写、`fsync`，记录 sha256 与字节数。编码在 ~1MiB 的明文切片间 `await scheduler.yield()`，压缩输出按 4MiB 批量落盘（`MIGRATION_WORK_CHUNK_BYTES=1024*1024`、`MIGRATION_WRITE_CHUNK_BYTES=4*1024*1024`，L50-51）。
3. **Worker 验证**：`verifyCurrentFile` 默认是 `verifyCurrentGenerationInWorker`（`migration-verifier.ts`），在新 Worker Thread 里以**严格解析 + 完整当前恢复**独立读一遍暂存文件，核对 id、事件数、字节数与 digest。进程级调度器 `MAX_CONCURRENT_VERIFIERS = 2`（L21）把完整代验证的 CPU 限制在最多两个 Worker。
4. **源未变 + 独占发布**：发布前再 `stat` 源文件，identity 变了就抛 `JsonlGenerationSourceChangedError`。发布本体的 `publishCurrentExclusive`（L817）**POSIX 用硬链接（`link`）+ 目录 `fsync`**：`link` 在目标已存在时以 `EEXIST` 失败，所以两个进程并发迁移同一 id 不会互相覆盖（`rename` 会静默覆盖，被明确弃用）。**Windows 用 `publishNewFileWin32`**（`win32.ts` L134），即 `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)`，不替换、不跨卷复制。
5. **目标冲突处理**：若发布返回"已存在"（`published === false`），说明赢家是别人；此时 `inspectExpectedCurrent` 会验证**已有目标的迁移前缀**是否等于本次暂存字节，相等才接受，否则抛 `JsonlGenerationTargetConflictError`。追加尾部留给当前代阅读，不参与迁移赢家验证。

这里就是决策记录的硬规则落地处：**只写最终 current 目标，中间版本仅存在于流式 stage 状态**。因为 `PrepareJsonlMigration` 只编码一次 `currentPath` 对应的文件名，v1/v2/v3 从不落盘。

**不承诺降级。** 决策记录 Consequences 明确写着：更低代保留下来是给操作者检查用的；保留不承诺降级兼容、不承诺自动回退、也不承诺旧 runtime 能安全解读新代。

**父目录补全（parent catalog completion）：一条边为什么需要额外证据。** v3→v4 与前面三条边有个本质区别：它不只是逐事件转换，还要在父会话日志的尾部补上"它有哪些子代理"的目录事实。这份事实的来源**不在父日志里**，而在每个子会话自己的日志里。所以：

- `session-format-v3-to-v4` 原始声明的 `createStage()` **直接抛** `SessionFormatUnsupportedMigrationError`（`migration.ts` L23-27）——"V3 catalog migration requires explicit historical child facts, including an empty array for a parent without children"。**一个未绑定子证据的历史正文恢复会拒绝，而不是假定子集为空。**
- 要跑这条边，必须用 `createSessionFormatV3ToV4(children)` 生成一个闭包了该父会话子证据的迁移，由 `session-format-catalog/src/children.ts` 的 `createSessionFormatCatalogWithChildren(children)` 替换掉静态目录里的那一条边。
- 子证据的收集在 `session-persistence-jsonl/src/catalog-migration.ts`：`prepareCatalogFacts(parentId, sources, ...)` 对每个直接子会话调用 `readDecodedJsonlSource`，再用 `historicalChildCatalogSource`（`facts.ts` L12）把子会话压缩成 `{childId, childCreatedAt, descriptorCount, descriptor, sourcePath}` 这样一份紧凑身份。
- **子会话失败被隔离**：某个子会话解不开时，`failures` 记下它、`facts` 里放一份 `unavailable`（`descriptorCount: 0, descriptor: null`），父会话历史照常完成。这正是决策记录里"unreadable children do not block healthy parent history"的落地。
- 发布前后都要复核成员与修订号：`validateRelatedSources` 既比较"子集合成员有没有变"，也调用 `related.validate()` 核对每个子文件的 `dev/ino/size/mtimeNs/ctimeNs`，任一处漂移就抛 `JsonlGenerationSourceChangedError`。

这也解释了 3.4 里那句"历史公共修订号把父会话物理修订与全部子路径指纹组合起来"的原因：父会话的历史逻辑值取决于整个子目录集合，父子任一变动都会被同一变更令牌捕获。

这里需要一个比喻来记住"代"的性质（**比喻一**）：把它想成**数据库的 WAL 段文件**——写新工作时追加新段，旧段只读不删，谁也不原地改写一个已落盘的文件。区别是 DSH 的"段"恰好是一整个文件格式版本，而不是时间窗口。

### 3.7 恢复流程：一次单遍扫描

恢复的读侧实现在 `format.ts` 的 `SessionLogScanner`（L386）。"扫描"这个词是刻意的：它**逐块物理扫描**，在 buffer 上找换行、只对完整记录解码 UTF-8，因此永不因为一个撕裂的尾帧而把整个日志判死。它的失败策略是一次性选定的 `SessionFormatRecovery`：

- `'strict'`：任何不可解析的已提交事件立即抛错。
- `'recoverable'`（生产默认）：容忍一个撕裂的尾帧，返回可安全追加的截断偏移 `committedBytes`，并保留前面的合法连续前缀。

扫描过程还负责"当前代接受度"：`consumeEventLine` 对每一行先跑 `assertV4RowAdmission`，把结构性拒绝**放在可恢复尾部抑制之前**——也就是说"这个当前格式的已知行不合法"必须先于"尾部可容忍"被拒绝。`finish()` 会再做一次 `assertReleasedV4Relationships`。

真正的管线由 catalog 组装。`createRestore`（`session-format/src/catalog.ts` L124）这样做：

1. 用 `artifactCodec` 按 header 版本选 codec，若版本高于 current 立刻抛 `SessionFormatUnsupportedMigrationError`。
2. 创建物理行解码器 `codec.createDecoder(headerValue, recovery)`。
3. 若源就是当前版本：走 `CurrentSessionFormatRestore`，逐行解码进 collector，`finish` 时施以当前验证。
4. 若源是历史版本：建一个 `SessionFormatEventCollector`，用 `chain.createStream(header, cut, collector)` 编译整条 v0..v4 链，解码器的每一行/run 流经链路，最后进入 `MigratingSessionFormatRestore`。它按 `validation` 策略选择 `restoreCurrent`（完整当前验证）或 `restoreTransformedCurrent`（只对转换结果施以已发布的当前验证）。

注意 `session-format/src/types.ts` 里 `SessionFormatRestoreOptions` 的 `validation: 'transformed' | 'current'`：生产历史读取用 `'transformed'`——迁**移后**的当前结果要验证，而输入本身已经是当前格式的行只接受 codec 验证。这个策略在 Worker / fixture 验证里换成严格解析 + 完整当前恢复。三种调用者（生产、Worker、fixture）共用同一个 `createRestore`，这是决策记录强调过的"生产与 fixture 迁移不再走不同入口"。

在 JSONL 后端，恢复流程的入口是 `decodeStoredLog`（`index.ts` L760，明文路径用 `scanLog`，zstd 路径用 `readZstdPrefix`）。`readZstdPrefix` 会扫描拼接的 zstd 帧：完整帧全部解码；如果有一个 `tornStart` 的**不完整尾帧**，它会尽力 `decompressZstdPrefix` 恢复其中已完整写入的 JSONL 记录，返回 `tornTruncateTo` 与 `recoveredTail`——前者是写路径要截断的字节偏移，后者是"从撕裂尾里救回来的完整事件"，由写句柄的**第一次新 append 之前**持久重写。`JsonlSessionHandle.persistContiguous`（`storage.ts` L319）先提交撕裂修复、再写新批次。

恢复出的当前 artifact 如何变成 `Session`？通过当前验证器 `restoreReleasedV4Artifact` + `assertReleasedV4Relationships` + `restoreReleasedV4Artifact`，最终调用 `Session.fromRestore(id, seed, header, inheritedEventCount, eventState, projections)`（`core/session/src/index.ts` L528）。`eventState` 表明 seed 事件是"独占对象（`detached`）"还是"只有深冻后的共享对象（`shared-frozen`）"——**恢复路径对独占/已深冻的值免拷贝、免冻结**。构造函数本身会校验：envelope 合法、`seq` 从 0 连续、surface 转换与 seed 相同的不变量。最后 `deriveMessages()` 从 surface 折叠出模型可见消息（第 8 章）。

### 3.8 分叉：从一条历史派生新会话

分叉的入口是 `SessionStore.fork`（`core/session/src/index.ts` L1251）：

```ts
fork(source: SessionForkSource, boundary?: SessionSeq, childSessionId?: SessionId): Session
```

- `SessionForkSource = Session | SessionId`，源可以是活的 `Session` 对象或它的 store id。
- `boundary` 是一个**闭区间（inclusive）的源事件 seq**；省略表示"源的最后一个事件"；**空源省略 boundary 分叉出空子会话**。
- 失败码在 `SessionForkErrorCode`（L900）：`SESSION_NOT_FOUND` / `SESSION_NOT_LIVE` / `SESSION_ALREADY_EXISTS` / `INVALID_BOUNDARY`，对应错误类 `SessionForkError`（L907）。

种子构造是 `buildForkSeed(events, boundary)`（`core/session/src/fork.ts` L21），三步：

```ts
export function buildForkSeed(events: readonly SessionEvent[], boundary: SessionSeqType): SessionEvent[] {
  const prefix = events.slice(0, boundary + 1)          // ① 复制 inclusive 前缀
  prefix.push({
    type: 'session/end-seed', seq: SessionSeq(boundary + 1),
    time: events[boundary]!.time,
    data: { inherited: true },                          // ② 追加带标记的切割点
  })
  return prefix.concat(openTurnClosers(prefix, { kind: 'forked' }))  // ③ 合成未闭合 turn 的关闭器
}
```

第 ② 步有个容易被忽略的细节：**一个新鲜 fork 出的子会话恒有一个带标记的切割点，即使复制的前缀已经以祖先的标记结束**。构造函数（L601-618）的注释确认了这一点：它保留"最终 inherited 标记"的唯一性——子会话不能有多个 `inherited:true` 标记，且 `inheritedEventCount` 必须指向最后那一个。

第 ③ 步是本章最反直觉的地方。如果 `boundary` 切在一个**未闭合的 turn 中间**，前缀里可能有一个 assistant 已经发出 `tool-call`、却还没有 `tool/result` 的位置。直接把这样的前缀当历史交给模型，provider 会拒绝"悬空的工具调用"。所以 `openTurnClosers(prefix, { kind: 'forked' })`（`repair.ts` L53）会为边界处未闭合的 turn **合成缺失的工具结果 + `step/end` + `turn/end`**。

`TurnEndReason` 的 `{kind: 'forked'}` **只由 fork 种子携带，agent-loop 从不发出**；`{kind: 'interrupted'}` 同理（见 3.9）。关闭器里的合成错误工具结果有差别化的措辞：`TOOL_NOT_STARTED` 与 `TOOL_OUTCOME_UNKNOWN` 两个错误码都被两种 cause 共用，但文字不同——fork 版本会告诉模型"父会话可能在分叉点之后完成了它"，并提示只在只读或幂等时才重试。

**边界之前的源事件在子会话里保持原样**，包括那些本来就缺结果的失败工具调用。关闭器只补边界处**未闭合**的尾巴。

然后是继承计数，这是最需要记牢的一条：

> **`inheritedEventCount = boundary + 1`——只计复制的源事件，不含合成的关闭器。**

看 `fork` 的返回（L1260-1267）：`inheritedEventCount: SessionLogOffset(resolved === undefined ? 0 : resolved + 1)`。`resolved` 是边界 seq，加一得到"复制了 0..boundary 共 boundary+1 个源事件"；关闭器的 seq 从 `boundary + 2` 开始（`openTurnClosers` 里 `seq = last.seq + closers.length + 1` 的推算），落在继承前缀之外，因此属于子会话自己。

子会话的 header 由 `fork` 构造：`cwd`（继承源）、`parentSession: source.id`、`isSeeded: true`。构造函数随后校验：seeded 会话必须有 seed 与继承计数、切割处必须有标记、`firstLifecycleSeq = inheritedEventCount`。运行时用 `Session.isOwnSeq(seq)`（L672，`seq >= inheritedEventCount && seq < this.seq`）与 `ownEvents()` 判断一个事件属于本会话还是父级。

**子代理（subagent）走的是同一套血统机制**，只是入口不同：`CreateSessionOptions.meta.origin: 'subagent'` 加上 `delegationDepth`。`delegationDepth` 会被持久化，注释解释得很清楚——"一个只存在于 runtime 的深度会让一个被恢复的子会话重置成顶层"，递归预算必须在重启后存活。

**官方 fork 入口**在 `docs/architecture.md`（约 L162）记着：`ctx.agents.create({ sessionId, seed, meta: { parentSession, seedLength } })`。这里要再强调一次持久化边界：**只有经 agent-loop 发布的会话才持久化**——`Session` 在别处构造出来，不会自动获得写句柄。

### 3.9 崩溃恢复：没有专门的"恢复模式"

一个在 turn 中途崩溃的日志，以打开的 `turn/start` 结束而没有 `turn/end`。持久化**不会**截断或原地修复它：长周期任务里单个 turn 可能极其庞大（很多 step、大量工具输出），这些事件在崩溃前已被持久追加，它们是真源的一部分。后端只丢弃**撕裂物理尾部**中不完整的碎片，并把从中恢复的完整记录交给写路径重写（见 3.7）。

修复是**读方的职责**。`interruptedTurnClosers(persisted)`（`repair.ts` L209）就是 `openTurnClosers(events, { kind: 'interrupted' })` 的封装。resume 流程（第 5 章 agent-loop）通过写句柄读已存储日志，计算缺失工具错误、未闭合的 `step/end`、以及合成的 `turn/end { reason: { kind: 'interrupted' } }`，然后**作为普通批次通过同一个句柄 `append`**。

**所以恢复不需要一个专门的"恢复模式"。** 修复只是又一批 append，走的是平时那条"每 handle 变更串行化在 promise 链上"的路。这也是为什么修复只在写所有权之下发生：并发 `open(id, 'write')` 会以 `SessionAlreadyOwnedError` 拒绝，而不是让修复与活跃轮次竞速。只读观察方（session-query）只在内存里用同样的闭合事件配平冷日志，不回写。

`repair.ts` 顶部的注释把两种 cause 归纳得很干净：`interrupted` 是崩溃恢复；`forked` 是 fork 种子切在源的开 turn 中。两者选择合成的 `turn/end` reason、对模型可见的错误工具结果措辞、以及确定性合成 message-id 前缀。

### 3.10 对照：SQLite 为什么刻意相反

会话日志之外，DSH 还有别的持久化。它们的策略**刻意与 JSONL 相反**：

- `packages/storage/storage-sqlite/src/schema.ts`：非会话 KV 数据的物理布局版本 `STORAGE_SQLITE_SCHEMA_VERSION = 1`，存在 `PRAGMA user_version`。注释：**只有表布局的破坏性变化才 bump；任何其他已标记版本都直接拒绝——这个未发布格式没有迁移。**
- `packages/session-query/session-query-sqlite/src/schema.ts`：会话全文检索的派生索引 `SESSION_QUERY_SQLITE_SCHEMA_VERSION = 8`，并用 `PRAGMA application_id = 0x44534851` 保护，防止误重置无关数据库。版本不匹配时 `resetDerivedSchema` **原地 `DROP TABLE` 重建**。

为什么两者相反？

- **派生索引可以丢弃重建**：FTS5 索引的全部内容都能从源日志重新生成，所以"不匹配就重建"是最便宜、最不可能出错的策略——重建的代价是 CPU，不是数据。
- **会话日志不能丢弃**：它是用户的原始数据，无法从别处重建。所以它必须**相邻迁移**、必须**保留旧代**、必须**独占发布**。你不能对用户的原始日志说"版本不匹配，我删了重建"。

再看两个 SQLite 包之间的差异：`storage-sqlite` 的注释强调两套 open 序列是**故意镜像、故意不共享 helper 的**——因为各自拥有独立的数据库身份和 schema，共享一个 helper 会把本可独立的存储提供方耦合到一起。

### 3.11 检索组与归档（第 8 章衔接）

`packages/session-query/` 这一组在会话历史之上提供检索能力，本章只做定位，细节归第 8 章与各包 README：

- `session-query`（`ctx.sessionQuery`，`SessionQueryEngine`）：`observeSession` 原子观察、`searchSessions` / `searchEvents` / `listSessions` / `readSession`（完整重放验证）。它的类型词汇包括 `SessionRecord`、`SessionSurfaceSnapshot`（带 `capturedThroughSeq`）、`SessionLineageTrace`（fork 血统树）、`SessionEventTrace`（`replacedBy` / `replacementChain` / `sourceEventSeqs` / `derivedEventSeqs`）。
- `session-query-sqlite`：FTS5 派生索引，就是上面那个"可丢弃重建"的库。
- `tool-session-query`：模型侧工具 `session_search` / `session_event_search` / `session_trace` / `session_event_trace` / `session_event_read`。
- `session-log-export`：ZIP 归档。根用 log 规范名，子代理放 `subagents/<id>/`，图片走内容寻址 `media/`，通用文件走 `files/<prefix>/<digest>/`，用 fflate 流式压缩，**导出前对 live 会话过一遍 flush 屏障**——这最后一点正是 3.2 那条"`flush` 才承诺崩溃存活"的直接应用。

### 3.12 写路径：串行链、write-behind 缓冲与租约

前面讲的是"格式"和"代"，现在把"一个正在运行的会话如何把事件写下去"补全。实现在 `session-persistence-jsonl/src/storage.ts` 的 `JsonlSessionHandle`（L85）。

**变更串行化（mutation chain）。** 句柄持有一条 promise 链 `chain`。每个公开的修改操作（`append`/`flush`）都经 `run()`（L364）排到链尾；`enqueueChain`（L357）把 `this.chain = next.catch(() => {})`，因此一次操作失败不会毒化后续操作——调用方仍能从自己那次调用的 promise 上看到失败。`append` 的契约里那句"已接受、有序"就来自这里：**批次在入链之前就被 `materializeAppendBatch` 校验并深快照**，所以"被检查的值"和"被持久化的值"是同一个值，而不是先检查后复制。

**live 路由与 write-behind 缓冲。** 后端 `JsonlBackendTracker.install(ctx)`（L534）安装三个监听器：

- `session/event`（同步通知）：把事件按会话 id 路由进活跃写句柄的缓冲。`enqueueLive`（L274）push 一份 `structuredClone` 的持久化自有副本，并在空闲时武装一个有界批处理窗口 `LIVE_WRITE_BATCH_MAX_DELAY_MS = 200`（L36）。**第一个待处理事件开启固定窗口，后续事件加入但不重置截止时间**——这正是决策记录描述的顺序保证来源。
- `session/flush`：取消等待、排空到完全停稳，返回一个 promise，让 agent-loop 在领取下一个普通轮次前有一个顺序与错误观察点。
- `session/disposed`：做最终排空并关闭句柄。

`drainLive`（L288）是单飞的：并发调用者加入同一次 drain；`drainBuffered`（L294）用 while 循环反复拼批次并入链，抓到失败时把批次**按序拼回缓冲**并置 `drainPaused = true`，让自动定时器安静下来，下一次显式 flush 重试并向调用方响亮拒绝。窗**只限制有意的批处理等待，不限制事件循环调度或后端完成持久化的延迟**。

**撕裂尾修复的顺序。** `persistContiguous`（L319）先确认写访问、确保租约、`assertContiguous` 校验 seq 连续，然后按两步提交待修复状态：先 `truncateTornTail` 截断撕裂字节，再 `persistBatch` 把 `recoveredTail` 里的完整事件持久重写。每一步**只有落盘成功才清空对应状态**，所以中途失败会在下一次变更时重试，而不会留下"状态说已修、磁盘没修"的裂缝。

**跨进程写租约（SessionWriteLease）。** `lease.ts` 的 `SessionWriteLease`（L58）是会话目录内的一把内核级写锁，整个写句柄生命周期持有：

- 仲裁者是内核。POSIX 在日志旁的 `session.lock` 上做非阻塞 `flock(2)`（经 native `tryLockExclusive`）；Windows 持有一个以该路径派生的**命名内核信号量**——**从不是文件锁或文件句柄**，所以读者、搜索、目录删除在锁被持有时照常进行。争用映射成 `SessionAlreadyOwnedError`。
- 内核在持有者的描述符或最后一个对象句柄关闭时释放锁，**包括任何进程死亡**，所以崩溃的持有者永远不会阻塞后继者。
- **没有过期时间**：一个活着但卡死的持有者会一直持锁，直到它的进程退出。注释给的道理是——任何能让卡住的写者被"征收"的过期机制，都会让它恢复后的 append 撕裂日志。
- POSIX 锁认的是 inode 而不是路径，所以加锁后持有者要核对"锁住的 inode 仍是锁路径上的那个文件"，否则重试：一个被 unlink 又重建的锁文件带新 inode，锁在孤儿 inode 上什么也证明不了。所以**释放从不删除 POSIX 锁文件**——每个已获取的锁都属于一个已实体化或正在实体化的会话，留下文件是为了保住后续加锁者要核对的稳定 inode。
- 锁的获取时机：打开既有工件做写 open 时获取；对一个**新建**会话，只在它第一次实体化写入之前获取——一个未实体化的会话在文件系统上没有任何足迹。

**句柄生命周期。** `close()`（L223）是唯一的拆解口，幂等且不可取消（`Symbol.asyncDispose` 委托给它）。一个写句柄先通过仍然打开的存储排空已路由缓冲——**无论哪个 fiber 先卸载，后端拆解都不丢数据**；随后释放内核锁、释放进程内 claim。排空失败与锁释放失败会被聚合为一个 `AggregateError`，但**无论锁释放成败，进程内 claim 都会被释放**——否则一个 id 会被一把内核可能已经放掉的锁卡死在本进程里。

## 5. 常见误区

**误区一：以为迁移会原地覆盖旧文件。**
不会。迁移**从不移动、替换或删除一个已提交的格式代**，只写最终的 current 目标（`session.v4.jsonl.zstd`）。中间版本（v1/v2/v3）只作为 stage 内存状态存在，从不落盘。发布用 POSIX 硬链接（目标已存在则 `EEXIST`）或 Windows 的 no-overwrite `MoveFileExW`，`rename` 因会静默覆盖而被明确弃用。旧代文件保留下来供操作者检查；保留不等于承诺降级。

**误区二：以为 fork 会复制全部工具调用配对。**
不会。fork 只复制 inclusive 的源前缀，然后为**边界处未闭合的 turn** 合成工具结果与 `step/turn` 关闭器（`openTurnClosers(prefix, {kind:'forked'})`）。边界之前的源事件保持原样，**包括本来就缺结果的失败工具调用**。合成关闭器只是为了满足 provider "不能有悬空工具调用"的约束，不让子会话继承一个无法投喂的尾巴。

**误区三：以为 fork 的 `inheritedEventCount` 包含合成关闭器。**
不包含。`inheritedEventCount = boundary + 1`，**只计复制的源事件**；关闭器从 `boundary + 2` 起，属于子会话自己的事件。混淆这一点会导致 `isOwnSeq` / `ownEvents` 把关闭器误判为父级事件。

**误区四：以为 SQLite 和 JSONL 用同一套升级策略。**
刻意相反。SQLite 的 `SCHEMA_VERSION`（storage 的 1、session-query 的 8）不匹配就**原地 `DROP` 重建**，因为那是可丢弃的派生索引；会话日志则**必须相邻迁移 + 保留旧代 + 独占发布**，因为它是用户无法从别处重建的原始数据。判据是"这块数据能否丢弃重建"，不是"哪个策略更时髦"。

**误区五：以为 resume 有一个专门的"恢复模式"。**
没有。`interruptedTurnClosers` 合成的闭合事件**作为普通批次通过同一个写句柄 `append`**，和平时写事件走同一条串行化 promise 链。修复之所以安全，是因为它只在写所有权（单写者 + 跨进程租约）之下发生，而不是因为它是一个特殊模式。

**误区六：以为新增一个事件类型就要 bump `SESSION_FORMAT_VERSION`。**
不用。只有**结构性**变化（header 形状、`SessionEvent` envelope、核心事件语义、surface 机制）才 bump；新增普通事件类型用 `ignorable: true` 守卫吸收词汇增长。反过来，拿不准时应该 bump——一个近乎恒等的升级步几乎免费，漏 bump 会让旧 runtime 静默读错。

**误区七：以为 `open(id, 'read')` 会把迁移结果写回磁盘。**
不会。只读 open 在内存中消费迁移结果后就返回读句柄（`PreparedStoredLog` 作为 `primed` 状态），**不发布**。只有 `open(id, 'write')` 才会在持有写所有权时独占发布后继代。这保证了"用户只是翻看一条旧会话"绝不会改动他的磁盘。

**误区八：以为撕裂的尾帧会被永久丢弃。**
不完全是。撕裂物理尾部里**已经完整写入的 JSONL 记录**会被恢复出来（`readZstdPrefix` 的 `recoveredTail`），并由写路径在句柄第一次新 append 之前持久重写；只有真的不完整的字节（`tornTruncateTo` 之后的碎片）才会被丢弃。而一个**语义上**未闭合的 turn（有 `turn/start` 无 `turn/end`）根本不算撕裂——它是有效前缀，由 resume 用 `interruptedTurnClosers` 配平，绝不截断。

## 7. 本章小结

1. `SessionPersistence` 是持久化能力接缝的服务定义，暴露 `create`/`open`/`stat`/`list`/`flush`；所有日志读写经逐会话句柄 `SessionHandle`，不经按 id 寻址的服务方法。
2. `append` 是 best-effort（接受、有序、本实例可见）；只有 `flush` 承诺崩溃存活与跨进程实体化。
3. `SessionAccess = 'read' | 'write'`；进程内单写者，`read` 句柄上的修改是运行时的 `SessionReadOnlyError`。
4. 物理布局是 `<root>/<projectKey(cwd)>/<encodeSegment(id)>/session[.vN].jsonl[.zstd]`；`SessionId` 是未校验字符串，必须先做单射路径段编码防穿越；`root` 必填无默认。
5. 格式代文件名：v0 = `session.jsonl[.zstd]`，v1+ = `session.vN.jsonl[.zstd]`；只有规范名才是一个已提交的格式代。
6. 继承切割长度不在物理 header 里，由最后一个 `inherited:true` 的 `session/end-seed` 事件承载，只有读正文后才知道。
7. `SESSION_FORMAT_VERSION` 是单个单调整数（当前 4），由**写者产出**决定，只有结构性变化才 bump；新增普通事件类型靠 `ignorable: true`。
8. 未来版本在解码任何行之前就被 `refuseForeignFormatVersion` 转成 `SessionFormatUnsupportedError`，提示"升级 harness"而非"损坏"。
9. 迁移是"一包一条相邻边"：`session-format-v0-to-v1` … `session-format-v3-to-v4`，由生成的 `session-format-catalog` 静态装配，历史可读性不依赖插件挂载。
10. 每条边是有状态 `SessionFormatMigrationStage`（`transformEvent` / `transformRun` / `finish`），经同步 `emitEvent`/`emitRun` 串联；无中间版本事件数组物化；紧凑 run 可被下游直接消费。
11. 代数选择：`stat`/`list` 只翻译 header、不读 body、不发布；只读 `open` 在内存中消费迁移结果；只写 `open` 才独占发布后继。
12. 独占发布：临时文件 → 最多 2 个 Worker 全代验证 → 源 identity 复核 → POSIX `link`+目录 `fsync` / Windows `MoveFileExW` write-through；已提交代永不移动、覆盖、删除；不承诺降级。
13. 恢复是单遍流式扫描（`strict`/`recoverable`），容忍撕裂尾帧并返回安全截断偏移；撕裂尾中完整的记录由写路径在第一次新 append 前重写。
14. `fork(source, boundary?, childSessionId?)`：`boundary` 是闭区间源 seq；`buildForkSeed` 复制前缀、追加带标记切割点、为未闭合 turn 合成 `forked` 关闭器；`inheritedEventCount = boundary + 1` 只计复制源事件。
15. 崩溃恢复没有专门模式：`interruptedTurnClosers` 合成的闭合事件作为普通批次 `append`，只在写所有权之下发生；`forked` 与 `interrupted` 是只有这两条路径携带的 `TurnEndReason`。

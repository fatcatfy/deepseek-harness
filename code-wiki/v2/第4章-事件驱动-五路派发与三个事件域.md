# 第4章 事件驱动：五路派发与三个事件域

## 1. 本章导读

上一章（[第3章](./第3章-Cordis内核-服务依赖注入与上下文.md)）我们拆开了 Cordis 内核：Context 是服务仓库，fiber（纤程）管生命周期，`ctx.effect()` 让每个注册都可逆。本章我们沿着骨架往前走一步，看 Cordis 的另一个核心部分——**事件（event）**：一个插件如何在不修改任何主干代码的前提下，观察、拦截、包装这台机器的每一步。

学完本章，你应该能回答三个问题：

1. 同样叫"派发一个事件"，`emit`、`parallel`、`serial`、`bail`、`waterfall` 五种派发模式（dispatch mode）到底差在哪？为什么 DSH 规定"派发模式是事件公开契约的一部分"？
2. 为什么 waterfall（瀑布）监听器**必须**调用 `next()`？不调会发生什么？
3. DSH 把几十个事件分成 session（会话）、agent（代理）、capability（能力）三个事件域，新需求来了该往哪个域放？

本章的地图：先从一个真实问题出发（第 2 节）；正文讲五种派发模式、waterfall 语义、注册机制、声明方式（第 3 节）；然后逐行走读两份核心源码（第 4 节）；再列出四个常见误区（第 5 节）；最后是动手环节与小结（第 6-8 节）。

## 2. 从一个问题出发

设想你要写三个插件，需求都很朴素：

- **压缩插件**：每步（step）开始前检查 token 压力，快爆了就把旧消息摘要掉——参见真实插件 `dsh-compaction-basic`；
- **重试插件**：模型请求失败时接管恢复，按策略决定要不要重试——参见真实插件 `dsh-llm-retry`；
- **审批插件**：模型想执行 `rm -rf` 这类危险工具时，先拦下来问用户——参见真实的 `tools/pre-execute` 监听器家族。

三个需求的共同点：它们都想在 agent-loop（代理循环）的固定节奏里**插入自己的逻辑**。而 agent-loop 是整个 harness 最核心、最不该被随手修改的代码。你可以想象直接改源码的后果：三个插件三处补丁，每升级一次 agent-loop 就要重新缝一次，而且 vendor 里的 Cordis 是钉死版本的上游拷贝，根本不该动。

DSH 的答案你已经猜到了：**事件**。agent-loop 在固定位置"敲钟"——派发（dispatch）一个具名事件；你的插件在 `apply(ctx)` 里用 `ctx.on('agent/pre-step', ...)` 注册监听器（listener），告诉框架"这个钟响的时候叫上我"。压缩插件听 `agent/pre-step`，重试插件听 `agent/request-error`，审批插件听 `tools/pre-execute`。agent-loop 一行代码都不用改。

但这里有个容易被初学者忽略的关键点：**"敲钟"有好几种敲法**。同样是通知监听器，有的敲法是"广播一下就完事"，有的敲法是"每人投一票，第一个反对的说了算"，还有的敲法是"你们层层把我的工作包起来"。选错敲法，插件之间会互相冲突。这五种敲法，就是本章前半部分的主角。

## 3. 正文

### 3.1 事件系统的解剖：一个总线，五种派发

Cordis 的事件系统全部实现于 [vendor/cordis/src/events.ts](../../vendor/cordis/src/events.ts)，核心是 `EventsService` 类（约 L131）——它就是我们说的**事件总线（event bus）**。它的核心存储是一个字典：

```ts
// vendor/cordis/src/events.ts（节选，L131-L132）
export class EventsService {
  _hooks: Record<keyof any, Hook[]> = {}
```

每个事件名对应一个监听器记录数组（`Hook`），记录里除了回调，还存着注册它的 Context（L120-L123）。你在插件里调用的 `ctx.on()`，最终走的就是 `EventsService.on()`（L288）；`ctx.emit` / `ctx.parallel` / `ctx.serial` / `ctx.bail` / `ctx.waterfall` 则是混入 Context 的五个派发方法。

注意一个初学时最容易误解的事实：**一个事件只有一种派发模式**。事件的声明者用 JSDoc 的 `@mode` 标签把模式写死，生产者必须用对应的方法派发，消费者的语义依赖它。这不是"你可以任选的五种调用风格"，而是事件的公开契约（后面 3.5 节展开）。

### 3.2 五种派发模式：同一件事的五种做法

先看总表，来自 [docs/cordis-primer.md](../../docs/cordis-primer.md) 的"Dispatch Modes"一节（L19-L25）：

| 模式 | Awaited? | 顺序 | 有返回值? | 一句话语义 |
|---|---|---|---|---|
| `emit` | 否 | 注册序 | 无 | 通知所有监听器，不关心结果 |
| `waterfall` | 否 | 注册序 | 有 | 监听器层层包装内建行为 |
| `parallel` | 是 | 并发 | 无 | 所有监听器同时跑，全部 settle 才继续 |
| `serial` | 是 | 注册序 | 有 | 依次 await，第一个 bail 值胜出 |
| `bail` | 否 | 注册序直到 bail | 有 | 同步依次，第一个 bail 值胜出 |

表里的"bail 值"指 `isBailed()` 判定为有效的返回值（L13-L15）：**除了 `null`、`false`、`undefined`，都算 bail**。注意这个怪癖：`0` 和空字符串 `''` 也是 bail 值——你以为返回了一个"空"值表示没意见，链条却停在你的监听器这里。serial/bail 的监听器表达"没意见"时，请显式返回 `undefined`。

下面用一个对照实验建立直觉。假设有个教学虚构事件 `demo/step`，注册了三个监听器：

```ts
// 教学虚构，非仓库事件
ctx.on('demo/step', (info) => { log('A 看到了') })              // A：观察者
ctx.on('demo/step', async (info) => { await saveToDisk(info) }) // B：要刷盘
ctx.on('demo/step', (info) => info.force ? 'veto' : undefined)  // C：决策者
```

把 `demo/step` 分别放进五种模式，行为差异如下。

**emit（L194-L196）：喊一嗓子就散场。**

```ts
emit(...args: any[]) {
  this.dispatch('emit', args).map(cb => cb(...args))
}
```

A、B、C 依次被同步调用一次，谁也不等谁：B 返回的 promise 无人 `await`，C 的返回值直接丢弃。emit 适合**纯通知**：UI 刷新、计数上报。真实的 `agent/status`（代理状态翻转）就是 emit——听的人只管画画进度条，没有任何投票权。还要注意原生 `ctx.emit` 用 `Array.map` 执行回调：某个监听器同步抛错会让后面的监听器一个都收不到（3.7 节会讲 DSH 如何在 agent 域修掉这一点）。

**parallel（L183-L187）：并发，全员 settle 才返回。**

```ts
async parallel(...args: any[]) {
  const results = await Promise.allSettled(this.dispatch('emit', args).map(async cb => cb(...args)))
  const errors = results.filter((result): result is PromiseRejectedResult => result.status === 'rejected')
  if (errors.length) throw new AggregateError(errors.map(error => error.reason))
}
```

A、B、C 同时启动；`await ctx.parallel(...)` 会等它们全部落定；谁失败了错误也被聚合成 `AggregateError` 一起抛。适合"多个互不相干的副作用"，典型是会话的**持久化检查点**：`session/flush`（[packages/core/session/src/index.ts](../../packages/core/session/src/index.ts) L82，`@mode parallel`）——JSONL 落盘插件和遥测插件必须都跑完，这次 flush 才算完成，谁也不否决谁。

**serial（L204-L209）：按序 await，第一个 bail 值短路。**

```ts
async serial(...args: any[]) {
  for (const cb of this.dispatch('serial', args)) {
    const result = await cb(...args)
    if (isBailed(result)) return result
  }
}
```

依次 await A、B、C；C 排最后，轮到它时 A、B 已经跑过；C 返回 `'veto'`（bail 值），链条停止，`ctx.serial` 的返回值就是 `'veto'`。返回 `undefined` 则继续下一个。适合"有序且异步的多方决策"。真实例子是 `agent/created`（[packages/core/agent/src/runtime-types.ts](../../packages/core/agent/src/runtime-types.ts) L261，`@mode serial`）：AgentLoop **await 完所有**初始化监听器才开始处理排队输入，任何一个抛错就回滚整个创建（[docs/architecture.md](../../docs/architecture.md) L80）。事件矩阵显示它有整整 12 个消费者包，从 hooks 桥接到 goal 驱动器，全都靠"创建时排队初始化"这一个语义。

**bail（L217-L222）：serial 的同步版。**

```ts
bail(...args: any[]) {
  for (const cb of this.dispatch('bail', args)) {
    const result = cb(...args)
    if (isBailed(result)) return result
  }
}
```

行为同 serial，但不 await、纯同步。Cordis 自己拿它实现内部钩子：`ctx.on()` 注册监听器前会先 `bail('internal/listener', ...)`（L296），给特殊事件一个"替换注册"的机会。

**waterfall（L234-L243）：层层包装，下一节专门讲。**

五个方法共用的准备工作在 `dispatch()`（L165-L175）里：取出过滤后的监听器回调列表，并把它们绑定到派发时的 `this`。这个 `this` 上可能挂着**上下文过滤器（context filter）**——3.7 节 scope 过滤的全部魔法都从 L171-L173 这三行出发。

### 3.3 waterfall 与 next()：最容易出事的一环

waterfall 是**环绕中间件（around-middleware）**。想象一颗洋葱：最外层是第一个注册的监听器，往里一层层是后来的监听器，洋葱芯是框架的内建行为。每个监听器收到 `(...args, next)`：调 `next()` 就进入下一层，`next()` 的返回值是从芯里冒出来的结果；不调 `next()`，整颗洋葱从你这层往里全部不存在。

先看实现，只有十行（L234-L243）：

```ts
waterfall(...args: any[]) {
  const cbs = this.dispatch('waterfall', args)
  const inner = args.pop()        // 最后一个参数是最内层的 next（内建行为）
  const next = () => {
    const cb = cbs.shift() ?? inner  // 弹出下一个监听器；耗尽后落到内建行为
    return cb(...args)
  }
  args.push(next)
  return next()
}
```

派发者调用 `ctx.waterfall(name, payload, builtinNext)`：`builtinNext` 是内建行为。`waterfall()` 先把 `next` 追加为最后一个参数，再发起第一次调用：`next()` 弹出第一个注册的监听器，于是每个监听器收到的最后一个参数，就是进入下一层的 `next`。链条耗尽后落到 `builtinNext`。整条链的返回值**只经由 `next()` 传播**：`waterfall()` 返回最外层监听器的返回值，而最外层监听器想传递内层结果，就必须 `return next()`。

现在看本章最重要的一段代码——**忘记 `next()` 的最小错误**。你给 `tools/execute`（工具执行，waterfall）写了个指标插件：

```ts
// ❌ 错误：记完指标就自己返回了
ctx.on('tools/execute', async (exec) => {
  metrics.count(exec.name)
  return { kind: 'ok', content: [] }   // 没有调 next()！
})
```

编译通过，运行不报错。但从你注册的那一刻起，这个事件上排在你的监听器之后的所有包装层——超时控制、重试、指标——以及洋葱芯里**真正的工具执行体，永远不会运行**。工具静默失效：模型请求执行 `bash`，拿到一个假结果，没有任何异常。这是本章（也是整个事件系统）最危险的坑，所以 [AGENTS.md](../../AGENTS.md) 把它写成硬规则："Waterfall listeners MUST call `next()` to delegate; returning without it short-circuits the chain"。

修复只需一行：

```ts
// ✅ 正确：观察之后把执行权交还链条
ctx.on('tools/execute', async (exec, next) => {
  metrics.count(exec.name)
  return next()
})
```

两个进阶细节：

- 想加工结果，就先 `const result = await next()`，修改后再返回——下游只见你替换后的值；
- `next()` 之后**不能反悔**：执行已经发生。

那什么时候**有权**不调 `next()`？当事件把决策权交给了你。这叫**短路即设计（short-circuiting is the design）**（[docs/cordis-primer.md](../../docs/cordis-primer.md) L35）：拥有决策的策略监听器可以返回自己的决定而不委托；只注解、只观察的监听器必须委托。真实范例是 [packages/llm/llm-retry/src/index.ts](../../packages/llm/llm-retry/src/index.ts)：它监听 `agent/request-error`（waterfall，runtime-types.ts L353），决定重试时直接 `return { kind: 'retry' }`（L191），不调 `next()`——它**拥有**这个恢复决策；重试耗尽或不想管时才 `return next()` 把决定权留给内建行为（默认 `undefined`，即失败终局）。

配套的注册选项 `prepend: true`（[events.ts](../../vendor/cordis/src/events.ts) L112-L117 的 `EventOptions`）把你的监听器插到队列最前面——成为洋葱最外层。只在"必须先于普通注册运行"时才用它（primer L33），比如审计插件要看到未经下游篡改的原始输入。

### 3.4 注册即效应：监听器的生命周期

第 3 章讲过"Registrations are effects"（注册即效应），事件监听器是最好的例子。`ctx.on()` 最终调用 `EventsService.register()`（L254-L260）：

```ts
register(label: string, hooks: Hook[], callback: any, options: EventOptions): () => void {
  const method = options.prepend ? 'unshift' : 'push'
  return this.ctx.fiber.effect(() => {
    hooks[method]({ ctx: this.ctx, callback, ...options })
    return () => this.unregister(hooks, callback)
  }, label)
}
```

看清楚：注册监听器这件事本身就是一个 `ctx.fiber.effect()`。效果是——你的插件 fiber 卸载（配置删除、热重载）时，监听器**自动注销**，不需要你手写清理代码。这也解释了为什么 `ctx.on()` 必须在活跃的 fiber 里调用：fiber 已销毁时会抛 `INACTIVE_EFFECT`。`once()`（L312-L318）则是在 `on()` 外再包一层"触发即注销"。

`EventOptions` 还有一个字段 `global: true`：无视派发者的 context filter，强行收到事件。它是给框架内部诊断用的逃生门，插件开发几乎用不到，但读源码时见到要知道它绕过了 scope 过滤。

### 3.5 事件怎么声明：declaration merging 与 @mode

事件不是字符串约定，而是**类型化事件（typed events）**，通过 TypeScript 的声明合并（declaration merging）进入 `Events` 接口。真实样本一，会话域的生命周期事件（[packages/core/session/src/index.ts](../../packages/core/session/src/index.ts) L38-L84，节选）：

```ts
declare module '@deepseek-ai/cordis' {
  interface Events {
    /**
     * @param session - the session just entered and announced.
     * @mode emit
     */
    'session/created'(this: Scoped<Session>, session: Session): void
    // …
    /**
     * Awaited parallel durability checkpoint: every listener runs and the
     * caller awaits all of them, with no waterfall veto.
     * @param session - the session whose buffered events must reach durable storage.
     * @mode parallel
     */
    'session/flush'(this: Scoped<Session>, session: Session): Promise<void> | void
  }
}
```

真实样本二，vendor loader 的一个 waterfall（[vendor/loader/src/index.ts](../../vendor/loader/src/index.ts) L29-L41）：

```ts
declare module '@deepseek-ai/cordis' {
  interface Events {
    /**
     * Refresh entry context before applying config.
     * @param entry - entry containing the new raw config and optional current fiber.
     * @param next - continue context refresh and Loader's config update.
     * @mode waterfall
     */
    'loader/patch-context'(entry: Entry, next: () => void): void
  }
}
```

仓库规约（[AGENTS.md](../../AGENTS.md)）要求每个事件的 JSDoc 必须有 `@mode` 和载荷（payload）每个字段的 `@param`。这不只是文档洁癖：类型目录生成器会机械校验——声明标了 `@mode waterfall` 却没有尾随的 `next` 参数会直接报错（[packages/typert/generator/src/cordis-catalog.ts](../../packages/typert/generator/src/cordis-catalog.ts) L210），声明与实际派发方法不一致也会被矩阵生成流程揪出来。**派发模式是事件公开契约的一部分**（[docs/cordis-primer.md](../../docs/cordis-primer.md) L27）：消费者依赖它，就像调用方依赖函数签名。

`this: Scoped<Session>` 这个 `this` 类型标注是 3.7 节 scope 过滤的声明面。

### 3.6 三个事件域：扩展点选型的第一决策

DSH 自己的事件有几十个，[docs/architecture.md](../../docs/architecture.md) 的 Events 一节（L72-L82）把它们组织成三个**事件域（event domain）**。选对域，是大多数改动的第一个决策。

**域一：Session 事件（durable，持久事实）。**

判据一句话：**这个事实必须活过重载（survive a reload）吗？** 用户说过什么、模型答过什么、工具返回过什么——进程重启后还得在，下次请求还要喂给模型。这些事实不是广播出来的，而是**追加（append）进会话日志**——一张类型化的 `SessionEventMap`（[packages/core/session/src/types.ts](../../packages/core/session/src/types.ts) L281 起），成员如 `turn/start`（L288）、`step/start`（L299）、`user/message`（L309）、`assistant/message`（L341）、`tool/call`（L361）、`tool/result`（L375）等。日志追加之后，再通过 `session/event`（emit，session/src/index.ts L74）向全进程广播"日志刚长了一条"。想观察会话历史，监听 `session/event` 就够了。

配套的生命周期事件：`session/created`（L54，emit）、`session/disposed`（L63，emit）、`session/flush`（L82，parallel）。生成矩阵显示 `session/event` 的消费者足足有 25 个包——从持久化、投影缓存到 token 统计，全都在消费这份持久事实流。Session 域是**模型记忆**的基础，第 8 章会用整章展开。

**域二：Agent 事件（live，活的机器）。**

`agent/*` 事件携带一个**活动中的 Agent 对象**——它有 inbox（收件箱）、有运行状态、有取消信号，进程一死就没了，**不能重放**。它们全部声明于 [packages/core/agent/src/runtime-types.ts](../../packages/core/agent/src/runtime-types.ts) L245-L394，模式分布值得整表细看：

| 事件 | 行号 | 模式 | 用途 |
|---|---|---|---|
| `agent/created` | L261 | serial | 代理初始化，全部 await 完才开始排队工作 |
| `agent/disposed` | L270 | emit | 代理离开注册表 |
| `agent/status` | L280 | emit | `idle` ⇄ `running` 状态翻转 |
| `agent/inbox/inserted` / `claimed` / `discarded` | L288 / L299 / L307 | emit | 收件箱增减的三个观察点 |
| `agent/pre-step` | L320 | waterfall | 拒绝或改写进入本步的消息 |
| `agent/request` | L337 | waterfall | 替换冻结的模型调用配置 |
| `agent/request-error` | L353 | waterfall | 接管失败请求的恢复决策 |
| `agent/assistant-stream` | L363 | emit | 流式输出的 start/chunk/end 帧 |
| `agent/turn-stopping` | L381 | serial | turn 关闭前的最后确认 |
| `agent/error` | L393 | emit | 步/turn 出错的通知 |

两个教学点。其一，`agent/turn-stopping` 虽是 serial，但声明返回 `void`、**没有 `next()`**：监听器有异议不是靠返回值否决，而是调用 `agent.steer(...)` 往收件箱里塞新消息——机器随后重读 inbox，有新活就再跑一步，没活才关 turn。**数据决定结果，监听器顺序改变不了它**（runtime-types.ts L364-L374 的 JSDoc 写得非常清楚）。这示范了同一模式在不同事件里可以有完全不同的否决通道。其二，`agent/pre-step` 是压缩插件的挂点：矩阵显示它的监听器多达 16 个包，`compaction-basic`、`time-context`（注入当前时间）、`agent-instructions`（注入指令）全在这一层排队改写消息。

**域三：Capability 事件（能力接缝上的策略）。**

第 1 章讲过能力接缝（capability seam）：Service Definition / Provider / Consumer 三角色。Capability 事件就挂在接缝上，让策略插件不必 import 循环就能介入能力内部。最典型的是工具管线家族（[packages/core/tools/src/index.ts](../../packages/core/tools/src/index.ts)）：

| 事件 | 行号 | 模式 | 决策词汇 |
|---|---|---|---|
| `tools/pre-execute` | L153 | waterfall | `PreToolDecision`（L607）：`allow` / `deny` / `cancel` / `ask` |
| `tools/execute` | L164 | waterfall | around-dispatch：超时、重试、指标 |
| `tools/post-execute` | L176 | waterfall | `PostToolDecision`（L617）：`accept` / `block` |
| `tools/ptc-dispatch-log` | L190 | waterfall | 改写日志副本的 content blocks |
| `tools/result` | L198 | emit | 观察冻结的最终结果 |
| `tools/change` | L208 | emit | 工具集变化（**故意不做** scope 过滤） |

审批插件该挂哪一层？挂 `tools/pre-execute`——因为它的决策词汇（allow/deny/ask）就是为审批设计的；`tools/execute` 的 `next()` 直接返回工具结果，没有 deny 可言。**选事件就是选决策词汇**，这个原则贯穿 capability 域。其他接缝同理：`fs/write-intent`、`fs/edit-intent`（[packages/fs/fs/src/index.ts](../../packages/fs/fs/src/index.ts) L57 / L65，均 waterfall）让观察策略拦截文件写入；`llm/stream`（[packages/llm/llm/src/index.ts](../../packages/llm/llm/src/index.ts) L73，waterfall）包装模型流本身；`session-telemetry/record`（[packages/session/session-telemetry/src/index.ts](../../packages/session/session-telemetry/src/index.ts) L42，waterfall）给遥测记录再加工。工具管线在第 7 章整章展开。

三域之下还有一个纪律性事实：`turn/*`、`step/*`、`user/message`、`tool/call`、`tool/result` 这些**模型可见（model-visible）的事实必须走 Session 域**——AGENTS.md 的规则"Model-visible ⟺ logged"：凡是会进入模型请求的内容，都必须能从会话日志重建。你新发明一个 agent/* 事件把用户消息偷偷塞进请求？重放会话时模型记忆就缺一块。这正是三域分立的根本原因：**持久事实与瞬态观察的边界，就是日志的边界**。

顺带一提：想知道某个事件谁生产、谁消费、什么模式，不要背，查生成的矩阵 [docs/event-producer-consumer.md](../../docs/event-producer-consumer.md)——"Events are many-to-many"，矩阵把每行关系的声明位置、派发包、监听包都列成了表。

### 3.7 scope 过滤分发：一个进程里多个 Agent 互不串扰

最后一个问题：一个 DSH 进程里可能同时跑着主 Agent 和若干子代理（subagent，第 5、11 章会大量出现）。如果所有 `agent/*` 事件对所有监听器广播，子代理的 `agent/pre-step` 监听器就会收到主 Agent 的消息——彻底乱套。

机制起点在 Cordis 自己的 `dispatch()`（[events.ts](../../vendor/cordis/src/events.ts) L165-L175）：

```ts
dispatch(type: string, args: any[]) {
  const thisArg = typeof args[0] === 'object' || typeof args[0] === 'function' ? args.shift() : null
  const name: string = args.shift()
  // …
  const filter = thisArg?.[Context.filter]
  return (this._hooks[name] || [])
    .filter(hook => hook.global || !filter || filter.call(thisArg, hook.ctx))
    .map(hook => hook.callback.bind(thisArg))
}
```

派发时第一个参数若是对象，会被当作 `thisArg`；它身上若挂着 `Context.filter` 函数，就由这个函数逐个裁决"这个监听器的 Context 配不配收本次事件"。**框架只提供过滤机制，过滤策略由派发者定义。**

DSH 的 `dsh-scope` 包在策略层构造这个 filter。[packages/core/scope/src/index.ts](../../packages/core/scope/src/index.ts) 的 `scopeTarget()`（L170-L185）造出一个 carrier（载体对象），其 filter 逻辑是（L173-L181）：无 scope 标签的监听器一律放行；带标签的监听器，只有标签等于本次派发的 scope key、**或等于 key 的某个祖先**才放行。L158-L169 的 JSDoc 点明方向："events flow up the chain, never down"——事件沿 scope 链向上流动：子代理的事件，父 scope 链上的监听器看得见（这样一套插件组装能观察到它组装的每个后代代理），但父 scope 的事件，子代理的监听器看不见。

[packages/core/agent/src/dispatch.ts](../../packages/core/agent/src/dispatch.ts) 把这套机制与 agent 事件的派发组合到一起。三个关键函数：

- `agentCarrier(agent)`（L94-L96）：`return scopeTarget(agent, agent)`——以 Agent 自身为 scope key 造一次性载体；
- `agentEvents(ctx, agent, carrier)`（L107-L149）：构造**融合派发器**。`serial` 与 `waterfall` 直接转发 Cordis 原语（L138-L147）；`emit` 则**绕开原生实现自己收集回调**（L120-L137），原因是 JSDoc 写明的：原生 emit 用 `map` 执行回调，一个同步 throw 会让后续监听器全部收不到事件、返回的 promise 被丢弃——而 agent 域的通知是"非否决"的，所以它逐个 `try/catch` 包含同步抛错、`Promise.resolve(...).catch` 包含异步拒绝（L127-L136），只 `warn` 一条日志，绝不让一个观察者拖垮其他观察者或生命周期本身；
- 载荷融合函数（L113-L118）：`({ ...payload, agent })`——**先展开调用方字段，再注入 `agent` 主体**，调用方即使碰巧传了 `agent` 字段也覆盖不了真实主体，保证"事件的 agent"与"scope 路由的 agent"永不分裂。

类型层还有一道约束：`AgentSubjectEvent` 映射类型（L28-L34）——从 `Events` 接口里筛出"第一个参数携带 `agent` 字段**且** `this` 声明为 `Scoped<Agent>`"的事件，只有这些事件能走融合派发器，防止碰巧带 Agent 字段的普通事件误入。

至此本章目标全部闭环：五种模式给了"敲钟的敲法"，三个事件域给了"钟的种类"，scope 过滤给了"谁听得见"。第 5 章你将看到 AgentLoop 如何在循环的每个阶段敲响这些钟。

## 5. 常见误区

**误区一：把 `session/event` 和 `agent/*` 混为一谈——"不都是事件吗？"**

两者的根本差异是持久性。`session/event` 是**日志追加后**的广播，载荷 `SessionEvent` 是落盘的持久事实，重放会话时按序重演；`agent/*` 携带活动 Agent 对象与取消信号，是瞬态的现场观察，进程重启即消失、不能重放。判据就一句话：**事实必须活过重载，进 Session 域；只观察进行中的工作，进 Agent 域**。把用户消息写进 `agent/*` 就塞给模型，违反"Model-visible ⟺ logged"，重放时模型记忆会缺一块。

**误区二：以为 waterfall 的返回值会"自动"传回。**

waterfall 的返回值**只经 `next()` 传播**。`return await next()` 是透传，`return myValue` 是**短路整条链**（含内建行为），`next()` 之后不 `return` 它的结果同样丢。三个变体里两个是事故。同理，想改共享请求对象，改完必须接着委托——否则你的改写成为终局，下游全部收不到你的修改。

**误区三：以为监听器抛错"无非报个错"。**

三种结局，取决于事件与派发器。结局一：agent 域的 `agentEvents.emit` **逐个包容**——同步 throw 被捕获、返回的 promise rejection 被捕获，各记一条 warn，其余监听器照常收到事件（dispatch.ts L127-L136）。结局二：原生 `ctx.emit` 用 `Array.map` 跑回调，一个同步 throw **让后面所有监听器都收不到事件**（events.ts L194-L195），异常直接上抛给派发方。结局三：waterfall 里抛错，**整条链当场断裂**——内建行为也不会运行，异常抛给派发方善后。写监听器前先确认自己面对的是哪种结局；观察型监听器永远该自己兜住异常。

**误区四：把派发模式当实现细节，"我想用哪种就用哪种"。**

模式是事件契约的一部分：`@mode` 写进 JSDoc，目录生成器校验声明与派发一致（连 waterfall 忘写尾随 `next` 参数都会硬报错）。消费者的正确性依赖模式语义——你敢在 `agent/pre-step` 改写消息，正是因为它是 waterfall，上游改写你能接着改；换成 emit，你连"结果"都拿不到。同理，给已有事件新增监听器时先查矩阵确认模式，再决定自己是"投票者"还是"包装者"。

## 7. 本章小结

1. 事件是 DSH 的扩展点机制：插件用 `ctx.on()` 注册监听器，主干在固定位置派发事件，**一行主干代码不改**即可接入压缩、重试、审批等横切行为。
2. 五种派发模式：`emit`（通知，忽略返回值）、`parallel`（并发，全 settle 后聚合错误）、`serial`（按序 await，首个 bail 值胜出）、`bail`（serial 的同步版）、`waterfall`（环绕中间件，层层包装内建行为）。
3. bail 值的判定：非 `null` / `false` / `undefined` 即有效——`0` 和 `''` 也会短路；"没意见"就返回 `undefined`。
4. waterfall 的返回值**只经 `next()` 传播**；不调 `next()` 即否决剩余整条链（含内建行为），且**静默**——AGENTS.md 把"必须 `next()`"定为硬规则。
5. 短路即设计：拥有决策的监听器（如 llm-retry 对 `agent/request-error`）可不委托；只观察/注解的监听器必须委托。
6. `prepend: true` 插到队列最前成为洋葱最外层，仅"必须先跑"时使用；`global: true` 无视 scope 过滤，是诊断逃生门。
7. 注册即效应：`ctx.on()` 就是 `EventsService.register()`，监听器注册本身是 `ctx.fiber.effect()`，fiber 卸载自动注销。
8. 派发模式是事件公开契约：`@mode` JSDoc + 目录生成器机械校验（waterfall 必须有尾随 `next` 参数），声明与派发不一致会被抓。
9. 三个事件域：Session 事件（持久事实，追加进 `SessionEventMap` 日志后经 `session/event` 广播）；Agent 事件（live，携带活动 Agent，观察/拦截进行中的工作）；Capability 事件（挂在 fs / tools / llm 等接缝上，策略不 import 循环）。
10. 域的判据："事实必须活过重载"→ Session 域；观察/拦截进行中的 Agent → Agent 域；给能力加策略 → Capability 域。**模型可见的内容必须来自日志**（Model-visible ⟺ logged）。
11. `agent/turn-stopping` 示范了 serial 事件的另一种否决通道：没有 `next()`、返回 `void`，有异议调 `agent.steer(...)` 塞数据——数据决定结果，顺序无关。
12. scope 过滤：Cordis 的 `Context.filter` 提供机制，`dsh-scope` 的 `scopeTarget` 提供策略——子代理只见自己的事件，父 scope 链看得见后代；`agentEvents` 融合派发器把 agent 主体注入载荷，且 emit 对监听器异常逐个包容。
13. 选扩展点先查生成的矩阵 [docs/event-producer-consumer.md](../../docs/event-producer-consumer.md)，事件多对多，不要背。

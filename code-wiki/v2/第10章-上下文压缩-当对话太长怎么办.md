# 第10章 上下文压缩：当对话太长怎么办

## 1. 本章导读

上一章我们看清了"一次请求里到底塞了什么"（[第9章](./第9章-上下文工程-一次请求里塞了什么.md)）：system prompt、工具 schema、历史消息、注入的上下文，一样不少。但每样东西都要花 token，而模型窗口是有限的。于是迟早会遇到那个瞬间——**这次请求装不下了**。

本章回答：DSH 如何让一场已经用满窗口的长对话继续下去，而且**不破坏[第8章](./第8章-消息系统-会话日志即模型记忆.md)建立的仅追加日志（append-only log）与可重放性（replayability）**。

四个核心问题：

1. `ctx.compaction` 这条能力接缝（capability seam）长什么样？为什么压缩被设计成"接缝"而不是循环里的一段代码？
2. `packages/compaction/` 下的五个包分别解决什么成因？什么时候触发？
3. 一次压缩究竟往日志里写了什么？为什么"旧消息没有消失"，模型却"忘掉了"它们？
4. 模型总结（summarization）为什么能复用上一次请求的 KV cache 前缀？

主干源码在 [packages/compaction/](../../packages/compaction/)，核心事务在 `compaction-basic/src/region.ts`。本章是全书理念核心章之二，请给 3.7 节（压缩如何落进日志）多留时间——那是本章的灵魂，也是第 8 章 surface 机制的第一次真实开工。

## 2. 从一个问题出发

设想一场长对话进行到第 80 轮。你在第 3 轮贴过一段 300 行的报错栈，在第 12 轮读过整整两个文件的源码，在第 40 轮让模型跑了十几次命令——历史消息加起来远超窗口。现在用户问了一句"继续修那个 bug"。你有两个朴素选项，但它们都是死的：

**选项 A：删掉旧消息。** 直接把最早的 60 条 `user/message` / `tool/result` 从日志里抹掉。代价是灾难性的：日志不再仅追加，"可重放"这条贯穿全系统的地基塌了；fork（[第11章](./第11章-会话管理-持久化格式迁移与分叉.md)）失去切割点；人类 transcript 里用户已经看过的对话凭空消失。而且删到哪里为止？删多删少都没有第二条信息能校准。

**选项 B：什么都不删。** 请求继续超限，provider 直接拒绝（`CONTEXT_WINDOW_EXCEEDED`），这一轮 Agent 卡死。

DSH 的答案是一条**分层策略**：不删除任何日志事实，而是在 surface 投影上做三件事——把冗余的工具输出**剪短**、把超出图片预算的旧图片**卸载**成文本、把最老的一段历史**概括**成一条摘要。前两件完全不需要模型调用，第三件只用一次。三条路径全部只写"替换"事件，原始事件原封不动留在日志里。

先把这三种朴素方案与 DSH 的对照摆出来：

| 方案 | 日志可否重放 | 人类是否还能看到旧对话 | 需要模型调用 | DSH 是否采用 |
|---|---|---|---|---|
| 删掉旧消息 | 不可（违反 append-only） | 不能（用户历史被抹） | 否 | ✗ |
| 什么都不做 | 可 | 能 | 否 | ✗（会溢出） |
| 在 surface 上遮蔽 + 替换 | 可（原始事件仍在） | 能（读追加来源事件） | 仅摘要一次 | ✓ |

关键在于理解一件事：**模型需要省 token，用户需要完整历史，两者的正确性标准根本不同**。第 8 章的两层视图（模型视图 vs 人类视图）正是为这个分歧准备的。本章全部工作都踩在那块地板上。

## 3. 正文

### 3.1 压缩家族：一条接缝与四个角色

打开 [packages/compaction/README.md](../../packages/compaction/README.md)，第一张表就把五个包的分工说清了。压缩是一条标准的**能力接缝**，与第 6 章的 `ctx.llm`、第 7 章的工具能力同构，分成 Service Definition / Service Provider / Consumer 三种角色：

| 包 | 角色 | 注册的服务键 | 解决的成因 |
|---|---|---|---|
| [compaction](../../packages/compaction/compaction/) | Service Definition | `ctx.compaction` | 定义共享词汇：三个操作、结果类型、`compaction/*` 事件 |
| [compaction-basic](../../packages/compaction/compaction-basic/) | Service Provider | 注册 `ctx.compaction` | 普通对话太长：模型总结旧历史 |
| [compaction-tool-result-pruner](../../packages/compaction/compaction-tool-result-pruner/) | Consumer/工具 | `ctx.toolResultPruner` | 历史被超大工具输出占据：无模型剪枝 |
| [compaction-image-offload](../../packages/compaction/compaction-image-offload/) | Consumer（监听错误） | — | 图片预算超限：旧图片卸载为文本 |
| [command-compact](../../packages/compaction/command-compact/) | Consumer（命令） | 注册到 `ctx.commands` | 用户想立刻压缩，不等压力触发 |

一句话记住分工：**接缝定义"压缩是什么"，basic 决定"何时压、怎么压、压哪段"，另外三个包各管一种具体成因或入口**。压缩是一件可选能力，不属于 agent-loop 主干，因此它的词汇定义在 `compaction` 包里，而不是 core。

### 3.2 `ctx.compaction`：抽象类与三个操作

Service Definition 的核心是一个抽象类 `CompactionEngine`（[compaction/src/index.ts](../../packages/compaction/compaction/src/index.ts) L119），它通过声明合并把 `compaction` 挂到 Cordis 的 `Context` 上（L88-L90）。它有三个抽象方法，正好对应三种触发方式（L136 / L162 / L187）：

```ts
abstract compactIfNeeded(agent, trigger, signal): Promise<CompactionResult | null>  // 自动：pressure / context-overflow
abstract compactNow(agent, signal, sourceCommandId?): Promise<CompactionResult | null>  // 手动：即使低于阈值也压
abstract compactRegion(start, end, agent, signal?): Promise<CompactionResult>  // 强制：显式区间
```

三个方法共同的不变量是：**成功的压缩把一个 surface 区间替换成一条摘要节点，并阻止同一会话的并发压缩**。注意 `compactRegion` 的 `start` / `end` 按 **surface 位置（surface position）** 命名，不是数值 seq 区间——因为前一次替换可能把一条新高 seq 摘要节点放进旧区间的位置，导致 `start` 在数值上大于 `end`。权威集合是 `shadowedSeqs`（当前 surface 顺序），不是数值范围。这个反直觉的细节在 `CompactionResult` 的 JSDoc 里写得很清楚（[compaction/src/types.ts](../../packages/compaction/compaction/src/types.ts) L107-L114）。

`CompactionTrigger` 是封闭联合 `'pressure' | 'context-overflow'`（index.ts L32）。`ManualCompactionError` 携带一个封闭的失败码集合（index.ts L35-L41）：`busy` / `cancelled` / `changed` / `summary` / `commit` / `persistence`，`command-compact` 把它们逐一翻译成人类可读文案（[command-compact/src/index.ts](../../packages/compaction/command-compact/src/index.ts) L24-L56）。

一次成功压缩返回的 `CompactionResult`（[compaction/src/types.ts](../../packages/compaction/compaction/src/types.ts) L94-L119）字段如下：

| 字段 | 含义 |
|---|---|
| `compactionId` | 本次压缩整个 durable 生命周期的稳定身份（`Branded<'CompactionId'>`，[brand.ts](../../packages/compaction/compaction/src/brand.ts) L4） |
| `sourceCommandId?` | 发起本次压缩的人类命令身份，仅手动时存在 |
| `startSeq` / `summarySeq` / `endSeq` | 追加的三条记账事件 seq（start / summary / end） |
| `summary` | 后端产出的摘要内容块 `ContentBlock[]` |
| `shadowedRange` | 被遮蔽的 surface 边界对 `{ start, end }`（位置跨度，`start` 可能大于 `end`） |
| `shadowedSeqs` | 全部被遮蔽节点的 seq，按 surface 顺序——**权威集合** |
| `shadowedTokenCount` | 被遮蔽内容的估算 token 数 |

注意 `CompactionResult` 只报告"发生了什么"，它不携带任何可变状态——调用方拿到的是一份 detached 的只读事实，与日志里刚追加的那几条事件一一对应。

接缝还导出了两个工具配对（tool-pairing）断言：`toolPairingBalancedBefore(session, seq)` 与 `toolPairingBalancedAfter(session, seq)`（[compaction/src/tool-pairing.ts](../../packages/compaction/compaction/src/tool-pairing.ts) L112 / L124）。它们判断"某个切点两侧有没有未配对的 assistant 工具调用"。实现上按 surface 顺序维护一个每切点的平衡缓存（`balanceCache` L72），`assistant/message` 里的 `tool-call` 块计数 +1、`tool/result` 计数 −1（`eventDelta` L29-L38）；一次 replace 会让 `replaceGeneration` 增长并触发缓存重建（L78）。这两个函数是后面 3.8 节区间选择的裁判。

### 3.3 压缩落进日志的词汇：四个仅日志事件

压缩向 `SessionEventMap` 合并了四个事件（[compaction/src/types.ts](../../packages/compaction/compaction/src/types.ts) L17-L90）。**它们全部是仅日志（log-only）事件，绝不进入 surface**——这一点和 `SurfaceEventType` 的封闭设计一致（[session/src/types.ts](../../packages/core/session/src/types.ts) L439）：只有能产生消息的五类事件才允许带 `surfaceOp`，`compaction/*` 没有资格上 surface。

| 事件 | 载荷要点 | 作用 |
|---|---|---|
| `compaction/start` | `{ compactionId, sourceCommandId?, turn: number \| null }` | 获取日志记录的锁；`turn` 数字表示自动轮次，`null` 表示独立手动事务 |
| `compaction/summary` | `{ summary, shadowedRange, shadowedSeqs, shadowedTokenCount, provider, model, maxTokens?, usage?, rawOutput?, llmStreamCall? }` | 记录摘要内容、被遮蔽的区间与 seq、以及"哪个 provider/model 写了它" |
| `compaction/end` | `{ compactionId, sourceCommandId?, turn, error? }` | 释放锁；`error` 记录失败尝试 |
| `compaction/prune` | `{ shadowedRange, shadowedSeqs, shadowedTokenCount }` | 无模型剪枝的**影子价格（shadow price）**事件 |

这里有一个贯穿全章的关键协议：**影子价格（shadow price），即"一条 surface replace 事件，由紧挨在它前一条的计量事件标价"**。`compaction/summary` 的 JSDoc 明确说这个相邻关系是契约性的（"That adjacency is contractual"，types.ts L30）：被遮蔽的定价字段就是替换节点的影子价格，消费方可以直接把一条替换和它前一条计量事件配对，而不必自行维护"每个节点多少钱"的状态。`compaction/prune` 复用同一协议（types.ts L76-L81）。

摘要本身呢？它不在这些事件里上 surface。真正改变模型视图的是一次 `user/message` 替换事件，它携带 `surfaceOp: { op: 'replace', startSeq, endSeq }`。也就是说：**`compaction/summary` 只是审计记录，摘要内容由紧随其后的一条 `user/message` 承载**。为什么复用 `user/message` 而不是新造 surface 事件类型？这是有意的决策——只有产生消息的事件才该到达模型，摘要就是给模型看的一条用户消息。

### 3.4 分层策略：从零模型调用到一次模型调用

压缩家族解决的不是一个成因，而是一组成因。按"代价从廉价到昂贵"排开：

| 层 | 机制 | 模型调用 | 落盘事件 | 触发时机 |
|---|---|---|---|---|
| 1 | 工具结果剪枝（tool-result pruning，`compaction-tool-result-pruner`） | 零 | `compaction/prune` + 一条 replace 的 `tool/result` | 压力/溢出确认后，选择摘要区间**之前** |
| 2 | 图片卸载（image offload，`compaction-image-offload`） | 零 | `image/offload` | 请求因 `IMAGE_OFFLOAD_REQUIRED` 失败后 |
| 3 | 输出外溢（output spill，[packages/spill/](../../packages/spill/)，属相邻的 spill seam） | 零 | spill 策略拥有 | 单条输出过大、需要在工具执行侧外置时 |
| 4 | 模型总结（model summarization，`compaction-basic`） | 一次 `ctx.llm.stream()` | `compaction/summary` + 一条 replace 的 `user/message` | 压力触发 / 溢出恢复 / 手动 |

设计意图写在 compaction-basic 的 README 里：剪枝和卸载都可能**直接免除**那次摘要调用——如果剪完之后压力已经降到阈值以下，`compaction-basic` 就地返回，不再总结（[compaction-basic/README.md](../../packages/compaction/compaction-basic/README.md) L90）。所以"分层"不是修辞，而是真实的短路路径：先用最便宜的手段，只有它不够时才付模型调用的钱。

注意三者的共同点：**它们都不删除旧事件**。剪枝替换的 `tool/result` 只在 `content` 上缩水（surface.ts 的 `assertToolResultRewrite` 强制"只许改 content"，[session/src/surface.ts](../../packages/core/session/src/surface.ts) L456-L485）；图片卸载不改消息成员与身份，只把图片块标记为已卸载；摘要替换只是遮蔽。原始事件永远在日志里。

### 3.5 触发时机汇总：压力、溢出、手动

DSH 明确区分三种触发，前两种由 `compaction-basic` 以纯消费者身份挂到 agent-loop 的既有事件点上（这一点 3.10 节展开）。

**① 压力触发（step pressure）。** 监听 `agent/pre-step` waterfall（[compaction-basic/src/index.ts](../../packages/compaction/compaction-basic/src/index.ts) L158-L176），在请求推导之前运行，trigger 为 `'pressure'`。它先用 `ctx.tokenMeter.measure(session)` 测量当前会话（`session` 由最新持久日志重放而来），再解析路由模型容量，算出阈值，比较 `totalTokens >= thresholdTokens`。这是"温和的预防性压缩"。

**② 溢出恢复触发（context-overflow recovery）。** 监听 `agent/request-error`（index.ts L190-L234），只有当失败码为 `CONTEXT_WINDOW_EXCEEDED_CODE` 时才介入，trigger 为 `'context-overflow'`。它**绕过正常阈值与保留尾部策略**：`selectCompactableRange(session, measurement, 0)` 传 `retainTokens = 0`（index.ts L299），即强制做一次"最大化的、平衡的头部缩减"。成功推进了 surface 后返回 `{ kind: 'retry' }` 让循环重试这次请求（index.ts L233）。重试次数受 `maxOverflowRetries` 限制（默认 1，`0` 表示禁用恢复）。有一处精细的处理：如果无模型剪枝已经落地、而后面的摘要阶段才失败，这次 durable 的缩减**仍算有效缩减证据**，依然允许重试（index.ts L204-L227 的注释），取消则始终优先。

**③ 手动触发（manual）。** `/compact` 命令调用 `compactNow`（[command-compact/src/index.ts](../../packages/compaction/command-compact/src/index.ts) L67）。它作用于**空闲（idle）会话**，经 `agent.runMaintenance`（[compaction-basic/src/index.ts](../../packages/compaction/compaction-basic/src/index.ts) L390）与 driver turn 串行化：压缩运行期间到达的新提示词按 FIFO 排队，等这次维护操作结算后才开始。它**低于阈值也能压缩**（清除有价值的历史），先同步启动一个 idle 任务，选择有用区间（无操作则不写日志），再追加独立的 `turn: null` 的 `compaction/start` 作为 durable 锁，最后 flush（L383-L435）。

手动失败被 `ManualCompactionError` 归类，`command-compact` 逐码翻译（[command-compact/src/index.ts](../../packages/compaction/command-compact/src/index.ts) L24-L56）：

| 失败码 | 含义 | 是否已写入日志 |
|---|---|---|
| `busy` | 已有活动压缩，或 agent 非空闲 | 否（pre-start 拒绝，无记录） |
| `cancelled` | 请求被取消，保留原始 abort 原因 | 视阶段而定，最多一次闭合 |
| `changed` | 选中的历史在压缩期间变了 | 是（闭合并持久化，不写摘要替换） |
| `summary` | 无法产出一个更小的摘要 | 是（同上） |
| `commit` | 提交阶段未干净完成，可能已有部分变更 | 可能部分落地 |
| `persistence` | 内存 marker 对已闭合，但 flush 失败 | 标记已闭合 |

三条规则值得记住：`changed` 与 `summary` 会**闭合并持久化失败尝试**（日志里看得到，但没有摘要替换）；`commit` 可能发生在部分变更之后，所以命令文案提示用户"压缩未干净完成，重试前先检查会话状态"；取消独立于这些失败码，做完必要清理后抛出原始 abort 原因。忙碌时报 `busy`，命令译为"compaction 不可用"。

**阈值公式与每一项的来源**（`resolveCompactSpec`，[compaction-basic/src/config.ts](../../packages/compaction/compaction-basic/src/config.ts) L153-L217）：

设：

| 符号 | 含义 | 来源 |
|---|---|---|
| `W` | 路由模型的完整上下文窗口 `contextWindow` | adapter 声明，经 `ctx.llm.resolveModelInfo(provider, model, signal).context.contextWindow` 读取（basic index.ts L304-L313） |
| `O` | 本次请求预留给输出的 token `reservedCompletionTokens` | 最新请求信封的 `maxTokens`；缺省时取 adapter 的每请求默认 `defaultMaxTokens`；再没有则为 0（basic index.ts L65-L68） |
| `B` | 额外压力余量 `headroomTokens` | 配置项，默认 `65536`（config.ts L75） |

则：

```txt
messageBudgetTokens  = W − O
pressureBudgetTokens = messageBudgetTokens − B
thresholdTokens      = floor( min( W × thresholdRatio, pressureBudgetTokens ) )
```

`thresholdRatio` 默认 0.8（config.ts L20）。保留尾部预算：

```txt
retainTokens = 显式 retainTokens，否则 floor( messageBudgetTokens × retainRatio )
```

`retainRatio` 默认 0.16（config.ts L23）。约束：`W − O − B` 必须为正，且 `retainTokens < thresholdTokens`，否则加载或首次使用该路由时抛 `TargetPressureConfigError`（config.ts L159-L204）。这套"上下文窗口 × 比例"的双重上限，既限制了窗口占比，也保证了扣掉输出预留与余量后仍有余地。

### 3.6 模型总结：复用 KV cache 前缀的亮点

`compaction-basic` 的 `summarize()` 是**子类唯一可覆写的钩子**（basic index.ts L247）；默认实现 `summarizeWithLlm` 在 [summarizer.ts](../../packages/compaction/compaction-basic/src/summarizer.ts) L120。

它只发一次 `ctx.llm.stream()` 调用，输入是**"重放的对话前缀"**，而不是一段独立的总结 prompt。具体由 `buildSummarizationInput`（region.ts L544-L563）装配：

- 取 surface 节点 0 的 `system/message` 派生成的消息（即这场对话**自己**的 system prompt）；
- 取最新请求头的工具 schema `header.tools`；
- 按 surface 顺序派生被遮蔽区间里每条消息（`shadowedSeqs`）；
- 最后追加 `COMPACTION_INSTRUCTION` 作为**最后一条 user 消息**（summarizer.ts L145-L151）。

为什么这样拼？因为这样一来，这次辅助调用就是"上一次路由请求"的**真前缀（genuine prefix）**：system prompt、tools、前导消息与那次请求逐字节一致，于是 provider 的 **KV cache**（键值缓存）可以复用，只有末尾那条指令和摘要输出是未缓存的。`COMPACTION_INSTRUCTION` 的注释把动机写得很直白（summarizer.ts L25-L31）：把指令作为**最后一条 user 消息**、而不是另造一个 summarizer system prompt，正是为了保住这个前缀。这是本章最值得品味的一个设计——一个纯粹的工程优化，却是"压缩机如何组织 prompt"这个核心决策的动机。

那次调用的其他要点：

- `GenerateOptions` 携带 `purpose: 'compaction'`（summarizer.ts L160）；只把返回的**文本**收进摘要，图片输出直接以 `UNSUPPORTED_CONTENT` 失败（`summaryText` L214-L221）；`max-tokens` 截断会被 `finishError` 当成错误（L197-L211），不留半截 checkpoint。
- 目标 provider/model 的解析顺序是：显式 `summarizationProvider/Model` → 最新路由请求目标 → `AgentOptions` 对（L127-L142）。
- 指令要求固定结构的 Markdown checkpoint：`## Primary Request and Intent` / `Key Technical Concepts` / `Files and Code` / `Errors and Fixes` / `Pending Jobs` / `Current Work` / `Next Step` / `Critical Context`（L37-L60）。若输入里已有 `<compacted-summary>` 块，要求**合并**而不是逐字拷贝（L66）。
- 落地的替换节点由 `CHECKPOINT_PREAMBLE` 定框（L70-L71），告诉模型"这是自动生成的 checkpoint，当作既有背景（established background），别复述、别确认"，随后是 `<compacted-summary>` 开闭标签（`frameSummary` L188-L194）。

为什么把指令放最后、而不是换一段 summarizer system prompt？除了缓存，还有职责上的原因：这场辅助请求就是"同一场对话的续写"，只是末尾多了一句元指令。若改成独立的系统提示，前缀就不再匹配，KV cache 失效，而且摘要器看到的历史也与原始请求不同了。代价同样明确（README 的 Known Limitations）：一旦把摘要器路由到另一个 provider/model，或压缩的不是头部区间，这份前缀复用就放弃了——你会为每次摘要多付一次冷启动的输入 token。

有了 `summarize()` 这一个钩子，压缩的其余部分（压力、保留、引用来源、收缩校验、token 计价）全部留在 token-meter 上，子类无法改动。

### 3.7 压缩是日志内事务（本章灵魂）

现在到了全章最核心的部分。一次压缩究竟往日志里写了什么？全部逻辑在 `compactSurfaceRegion`（[region.ts](../../packages/compaction/compaction-basic/src/region.ts) L173-L276）。它按固定次序产出五步：

```
① compaction/start      { compactionId, sourceCommandId?, turn }        ← durable 锁
② （await 摘要生成；期间 surface 可能被校验/重算）
③ compaction/summary    { summary, shadowedRange, shadowedSeqs,
                          shadowedTokenCount, provider, model,
                          maxTokens?, usage?, rawOutput?/llmStreamCall? } ← 仅日志
④ user/message          （定框后的摘要，source: compact-checkpoint，
                          surfaceOp: { op: 'replace', startSeq, endSeq },
                          sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs]）  ← 唯一的 surface 变更
⑤ compaction/end        { compactionId, turn, error? }                  ← 释放锁
```

逐步看契约：

**① `compaction/start` 是锁，且必须"同步相邻"于校验。** 事务在 `await` 任何异步工作之前，就先追加这条 marker（region.ts L210）。注释说得很明确：先计划（`validateSurfaceRegion`）后写锁，两者同步相邻，因此"durable 的开锁 marker 在任何 yield 之前就已经是锁了"（L157-L163）。这意味着崩溃只会留下**可检测的孤儿锁**——有 `compaction/start` 而无匹配的 `compaction/end`——而不会留下一条虚假宣称"压缩已完成"的 `compaction/end`。锁的活性判定还考虑 `session/end-seed` 边界：位于最新 seed 边界之前的未匹配 start 属于上一生命周期，是陈旧证据，忽略即可（`assertCompactionInactive` L308-L320）。

**② 摘要与稳定性校验。** `summarizeCompaction`（L387-L428）调用钩子；失败时经 `compaction/summary-error` waterfall 请求"记录一次 durable 的输入变更后重试"（`recover`，basic index.ts L442-L447）。生成摘要后必须通过稳定性检查：自动/显式区间用 `assertWholeSurfaceUnchanged`（整 surface 深比较，L431-L440），手动用 `assertSelectedSpanStable`（只要求选中区间不变，L447-L468）——因为手动压缩期间允许 idle 注入的无关上下文落在区间之外。还有一个硬性收缩判据：定框后的摘要触发计价若**不小于**被遮蔽区间的路由价格，就抛错，拒绝一个"没让它更小"的替换（L418-L422）。

**③ `compaction/summary` 记录"哪个模型写了这份摘要"。** `commitCompactionBody`（L471-L522）写入 `summary`、`shadowedRange`、`shadowedSeqs`、`shadowedTokenCount`、`provider`、`model`，以及可选的 `maxTokens` / `usage` / `rawOutput`。`llmStreamCall: true` 标记"这次摘要恰好通过本上下文的 `ctx.llm.stream()` 发起了一次调用"，并把完整 `rawOutput` 一并记录（types.ts L54-L67）。

**④ 紧随其后的 `user/message` 是唯一的 surface 变更。** 它是摘要真正"上 surface"的地方（L506-L509）。注意 `sourceEventSeqs` 里包含了 `startEvent.seq` 与 `summaryEvent.seq`，再加上全部 `shadowedSeqs`——即这次替换同时引用它的锁、它的审计记录、以及它遮蔽的所有节点。为什么 summary 事件和替换必须**紧挨着**？因为这就是 3.3 节讲的**影子价格协议**：summary 里的定价字段就是这条替换的影子价格，相邻是契约。第 8 章的 `foldSurface` 会校验 `sourceEventSeqs` 必须完整覆盖被遮蔽节点（[session/src/surface.ts](../../packages/core/session/src/surface.ts) L330-L365），缺一即拒。

**⑤ `compaction/end` 释放锁，且只尝试一次。** 每个失败路径都恰好做一次关闭尝试（L240-L251）；关闭失败会故意留下阻塞性的孤儿锁。手动路径还有一个额外的持久化检查点：`flush` 失败抛 `persistence` 失败码（L266-L272）。旧锁与 `turn/start` / `turn/end` 不能互相穿越。

把这五步写成一段日志形态（seq 与时间为示意，字段结构照抄源码）：

```jsonl
{"type":"compaction/start","seq":41,"time":1760002000000,"data":{"compactionId":"c-7f…","turn":1}}
{"type":"compaction/summary","seq":42,"time":1760002100000,"data":{"compactionId":"c-7f…","summary":[{"type":"text","text":"## Primary Request and Intent…"}],"rawOutput":[…],"llmStreamCall":true,"shadowedRange":{"start":4,"end":25},"shadowedSeqs":[4,5,7,8,…,25],"shadowedTokenCount":18322,"provider":"deepseek","model":"deepseek-chat","maxTokens":65536,"usage":{"inputTokens":…,"outputTokens":…}}}
{"type":"user/message","seq":43,"time":1760002100001,"data":{"role":"user","id":"u-9","source":{"kind":"compact-checkpoint","compactionId":"c-7f…"},"content":[{"type":"text","text":"This is an automatically generated checkpoint…"},{"type":"text","text":"<compacted-summary>"},…]},"surfaceOp":{"op":"replace","startSeq":4,"endSeq":25},"sourceEventSeqs":[41,42,4,5,7,8,…,25]}
{"type":"compaction/end","seq":44,"time":1760002100010,"data":{"compactionId":"c-7f…","turn":1}}
```

三条可自检的规律：`compaction/start` 与 `compaction/summary` 在日志里是连续相邻的（锁先于任何 yield 落下）；`compaction/summary` 的 seq 紧挨着替换 `user/message`（影子价格相邻）；`sourceEventSeqs` 里既有被遮蔽节点，也有 `41`、`42` 这两条本次事务自己的记账事件。`foldSurface` 重放到 seq 43 时会把 surface 上 `4`–`25` 的节点整段换成 `43` 一项，`replaceGeneration` 加一。

现在回答本章导读里的那个问题：**旧消息去哪了？** 哪也没去。日志是 append-only 的，`replace` 只在 surface 投影上**遮蔽（shadow）**被替换的节点：`deriveMessages()`（[session/src/index.ts](../../packages/core/session/src/index.ts) L856）沿当前 surface 节点派生的消息自然变短，模型"忘掉了"细节；但被遮蔽的原始事件一动不动地留在日志里，人类 transcript 用 `isAppendSurfaceEvent`（surface.ts L89-L93）只读追加来源事件，所以用户看过的对话一个字都没少。用一句话概括这个机制：**在索引上划掉旧条目，但原始记录保留**——翻当前结论的人顺着索引走，查完整流水的人仍能翻到每一条原始记录。

这就是"压缩落进不可变日志"的全部答案：**它不是删除操作，而是一次带双侧审计（锁 + 摘要）的 surface 替换事务**。可重放性因此毫发无损——重放整份日志，同一个 surface 折叠结果必然重现。

### 3.8 区间选择：system 节点 0 与工具配对平衡

压缩选哪一段？`selectCompactableRange`（region.ts L117-L155）的规则值得逐条记住：

1. **从第一个非 system 的 surface 节点开始。** 若 surface 节点 0 是 `system/message`，则 `firstIdx = 1`；否则从 0 开始（L131）。这意味着**surface 节点 0 的 system prompt 永不入选**。为什么？因为它是"根"，压缩它等于丢失整场对话的系统提示词。第 8 章讲过 surface.ts 的 `assertSystemHeadRewrite`（L493-L507）从折叠侧保护节点 0——只允许一条恰好覆盖它单节点的 `system/message` 改写它。这里是从选择侧再保护一次。
2. **保留一段近期尾部（retain）。** 从尾部往前累加各个节点的 token，直到累计 ≥ `retainTokens` 时停下（L133-L140），把切点定在那里。近期上下文以"原样保留（verbatim）"为原则。
3. **绝不拆开工具调用/结果对。** 确定切点后，向前回退（`keepFromIdx -= 1`）直到 `toolPairingBalancedBefore` 为真（L143-L147）。这样 assistant 的 `tool-call` 块不会和它的 `tool/result` 被切到两侧。
4. 如果最终切点退到了 `firstIdx` 之前，说明没有安全可压的区间，返回 `null`（L141 / L148）。

同样的平衡要求也由 `validateSurfaceRegion`（L337-L358）在事务入口强制：`start` 必须平衡前切、`end` 必须平衡后切，否则抛错，错误文案直说"would split a step's tool-call/result pair"。

一个常被忽视的细节：区间**不保持整个轮次**，只保持工具配对。因此一个过大的轮次里较早关闭的步骤是可以被压缩的（docs/subsystems/compaction.zh.md 的说明）。"安全切点"由内容（工具调用/结果配对）推导，而不是由 step 边界推导——所以 `tool-pairing.ts` 的文件头注释才说"safe cuts are derived from ... current surface order rather than step markers"。

### 3.9 无模型的两种缩减：剪枝与图片卸载

**工具结果剪枝。** `ToolResultPruner`（[pruner/src/index.ts](../../packages/compaction/compaction-tool-result-pruner/src/index.ts) L44，`ctx.toolResultPruner`）做确定性的**头/中/尾剪枝**：按 Unicode 码点（code point）测量，超过 `thresholdChars`（默认 8192）就保留前 `headChars`（4096）与后 `tailChars`（1024），中间换成固定 marker `[... tool result middle pruned ...]`（[config.ts](../../packages/compaction/compaction-tool-result-pruner/src/config.ts) L7-L14）。按码点而非 UTF-16 码元切分，保证不会劈开代理对（surrogate pair），但字形簇（grapheme cluster）仍可能被切断。`pruneSession`（L136-L182）遍历当前 surface 的 `tool/result`，每条超预算的替换为一条新 `tool/result`——只改 `content`，其余 event data 原样保留，并通过 `sourceEventSeqs` 引用被遮蔽节点。**每条替换前紧挨着一条 `compaction/prune` 影子价格事件**（L160-L164），价格由注入的 token-meter 给出。

举个具体例子：一条 `tool/result` 的文本是 20000 个码点，默认 `thresholdChars=8192`、`headChars=4096`、`tailChars=1024`。剪枝后它变成「前 4096 码点 + `[... tool result middle pruned ...]` + 后 1024 码点」，约 5100 余码点，且严格小于原长（`pruneContent` 会断言"必须更小且在阈值内"，L118-L120）。若这条结果里夹着 rich block（图片、结构化块），它们保持原有相对顺序原样保留——剪枝只对 `text` 块动刀。注意剪枝是**同步、无异步等待**的确定性操作，所以它不需要 `compaction/start` 锁；它只靠"影子价格事件 + 替换事件同步相邻"这一条协议保证可重放。这就是"纯消费方能不维护每节点状态就减去被遮蔽价格"的协议。

**图片卸载。** `compaction-image-offload`（[src/index.ts](../../packages/compaction/compaction-image-offload/src/index.ts) L25-L41）同时监听两个错误面：`agent/request-error` 与 `compaction/summary-error`。当失败码是 `IMAGE_OFFLOAD_REQUIRED_CODE` 且携带 `offloadImages` 数量时，`offloadOldestImages`（[image-offload.ts](../../packages/compaction/compaction-image-offload/src/image-offload.ts) L16-L46）按模型请求顺序遍历 surface，跳过 assistant 节点和已卸载的图片，选出最老的若干个"当前输入图片出现位置"，追加一条 `image/offload` 事件（record 每条目标消息的 seq 与按深度优先计数的图片索引），然后返回 `true` 让上层重试。重试**不消耗 provider 重试预算**，也不写 `llm/retry` 事件——它是一次 durable 的 surface 修复，不是 provider 重试。

关键语义：**卸载是永久的**。后续请求对选中的出现位置一律发送占位文本（`offloadedImageText`，[llm/src/content.ts](../../packages/llm/llm/src/content.ts) L108-L117），内容形如"image omitted to fit request image limits; <附件名>. <可用只读路径>"。实现方式是消息投影（`SessionMessageProjection`，[projection.ts](../../packages/compaction/compaction-image-offload/src/projection.ts) L40）——它**不改消息成员、不改消息身份，只把选中的图片块标记为 `offloaded: true`**。这正是第 8 章对比过的：`replace` 换掉节点，projection 改写节点内容。`image/offload` 是当前唯一的消息投影事件类型，加载日志时必须装好它的解释器，否则折叠直接拒绝。

### 3.10 与 agent-loop 的关系：纯消费者，不改循环一行

一个容易被误解的点：`compaction-basic` 不是循环的一部分，而是循环**已有事件点**的纯消费者。它：

- 监听 `agent/pre-step`（basic index.ts L158）——循环每步开始前的水位；
- 监听 `agent/request-error`（L190）——循环请求失败后的裁决点；
- 以 `ManualCompactAgentContext` 的 `runMaintenance`（[compaction/src/index.ts](../../packages/compaction/compaction/src/index.ts) L77-L86）实现手动入口。

它**没有改动 agent-loop 的任何一行代码**。这正好落实仓库约定里那条"Plugins, not loop changes"：新行为挂在文档化的扩展点上，而不是塞进循环。压缩造成的效果是间接的——替换让下一次 `deriveMessages()` 自然变短，循环根本不需要知道"发生过压缩"。触发与执行因此完全解耦：循环提供压力点与错误点，压缩包决定在那些点上做什么。具体挂点是 `agent/pre-step` 与 `agent/request-error`，都是[第4章](./第4章-事件驱动-五路派发与三个事件域.md)讲过的文档化扩展点。`compaction-basic` 只在它们上注册监听器，因此它能在"不编进循环"的前提下获得"每步开始前"和"请求失败后"两个时机的裁决权——这也是能力接缝的另一重价值：循环只管提供事件点，接缝的实现可以整个换掉，而循环一行不动。

### 3.11 可重建性：从日志 + 代码重建那次一次性请求

最后回扣[第8章](./第8章-消息系统-会话日志即模型记忆.md)的灵魂不变量"Model-visible means logged"。压缩的摘要调用是一次模型请求，因此它也必须可重建。`compaction/summary` 的载荷正好承担这件事：它记录 `provider`、`model`、`maxTokens`、`usage`，以及 `llmStreamCall: true` 标记与完整的 `rawOutput`。于是一个消费方只要拿到日志加代码，就能回答"这份摘要是哪台模型、用什么 envelope 写的、它原始输出了什么"。

`usage` 是 provider 报告的 token 计量，`shadowedTokenCount` 则是由 token-meter 的固定启发式（fixed heuristic）给出的被遮蔽内容估算。二者一起，让"这次压缩省了多少 token"有据可查。而触发这一切的测量数据源是 `ctx.tokenMeter`（[token-meter/src/index.ts](../../packages/llm/token-meter/src/index.ts) L101）——它从持久日志重放测量（确定性、零模型调用），并注册了 `tokenUsage` / `contextPressure` / `contextBreakdown` 三个 session projection（L114-L116）。它正是[第6章](./第6章-模型调用-llm能力接缝与适配器.md)埋下的伏笔：压缩触发器读的每一个数字，都来自同一个重放式计量服务。

### 3.12 一次完整的溢出恢复时序

把 3.5 节的第 ② 条展开成端到端时序，看清"循环提供点、压缩包裁决"的分工：

1. 循环派发请求，provider 拒绝：finish 为 `error`，失败码归一化为 `CONTEXT_WINDOW_EXCEEDED_CODE`。
2. 循环把这次失败记入 `assistant/attempt`（[agent.ts](../../packages/core/agent-loop/src/agent.ts) L490-L493），**不伪造模型可见历史**——模型下次看到的对话里不会多出半截 assistant 消息，但失败证据完整留存。
3. 循环派发 `agent/request-error` waterfall，默认动作返回 `undefined`（即不重试，[agent.ts](../../packages/core/agent-loop/src/agent.ts) L494-L508）。
4. `compaction-basic` 的监听器介入：确认失败码、`overflowAgents.set(session, agent)`、解析最新路由目标、检查 `overflowRetries` 是否已达 `maxOverflowRetries`（basic index.ts L190-L201）。
5. 调用 `compactIfNeeded(agent, 'context-overflow', signal)`（L205）：
   - 若有 pruner，先 `pruneSession` 并重测（L294-L298）；
   - `selectCompactableRange(session, measurement, 0)`——`retainTokens = 0`，不保留尾部（L299）；
   - 若无可压区间返回 `null`；否则走 `compactRegion` 的五步事务。
6. 监听器比较 `surface.replaceGeneration` 是否前进（L202 / L228-L233）：
   - 前进（或摘要失败但剪枝已落地）→ 返回 `{ kind: 'retry' }`，循环 `continue` 重新派发；
   - 未前进 → `next()`，交回普通错误处理结束这轮。
7. 重试预算的复位：`agent/status` 变 `idle`（L178-L180）或产出新的 `assistant/message`（L184-L188）时清空 `overflowRetries`——一次成功的响应开启新的溢出恢复序列，即使工具调用让同一轮继续到下一次请求。

三个应试要点：`trigger` 是 `'context-overflow'`；`retainTokens` 是 `0`；默认 `maxOverflowRetries = 1`，即第一次恢复后若仍溢出最多再试一次，之后交回普通错误处理。还要记住 `auto` 的作用域——它同时控制压力监听器与溢出恢复监听器（构造函数 L140），所以 `auto: false` 是"两种自动触发一起关"。

### 3.13 为什么这么设计：收益清点

把压缩设计成"接缝 + 分层 + 日志内事务"，代价是本章这些机制；收益贯穿系统：

1. **循环零改动（Plugins, not loop changes）。** 压缩是 `agent/pre-step` / `agent/request-error` 的纯消费者与 `runMaintenance` 的实现者，agent-loop 一行未改。换一个后端（模板、远端总结器）也只需覆写 `summarize()`。
2. **完整可重放。** 压缩不删除任何日志事实，`replace` 只遮蔽；重放整份日志必然重现同一个 surface 折叠结果，快照测试与离线重建都因此成立。
3. **用户历史完整。** 人类 transcript 走 `isAppendSurfaceEvent`，压缩对用户"什么都还在"，对模型"只留摘要"——两个正确性标准各得其所。
4. **成本分层。** 先做零模型的剪枝与图片卸载，只有它们不够时才付一次模型调用；剪枝甚至可能直接免除摘要。真实的一大类长对话根本用不上最贵那层。
5. **可重建、可审计。** `compaction/summary` 记录 provider/model/maxTokens/usage/`rawOutput`，那次一次性摘要请求可被日志 + 代码重建；影子价格协议让"省了多少 token"有据可查。
6. **可组合、可替换。** 能力接缝把"压缩是什么"与"何时压、怎么压"分开，`ctx.compaction` 一次只装一个实现；剪枝（`ctx.toolResultPruner`）与图片卸载是可选兄弟包，缺了它们压缩依然独立可用。

如果用一句话收拢：**为"把压缩建模成日志内事务"多写的每一条事件与每一处校验，都在可重放、用户历史、成本控制、可审计这四处各还了一次**。

## 5. 常见误区

**误区一："压缩把旧消息删了。"** 不。日志 append-only，`replace` 只在 surface 投影上遮蔽旧节点；原始事件原封不动。人类 transcript 读 `isAppendSurfaceEvent`，用户看过的对话一字不少。把"模型视角的遗忘"当成"数据被删除"，是读第 8、10 章最常犯的错。

**误区二："压缩可以拆开工具调用/结果对。"** 绝对不行。`selectCompactableRange` 会向前回退直至切点平衡，`validateSurfaceRegion` 会拒绝任何不平衡的 `start` / `end`，`toolPairingBalancedBefore/After` 是唯一的裁判。拆开它们会给模型一个"孤儿工具结果"或"没有结果的工具调用"，直接破坏请求合法性。

**误区三："溢出恢复也走正常阈值。"** 恰恰相反。`context-overflow` 分支绕过阈值与保留尾部策略，`retainTokens = 0`，做一次最大化的平衡头部缩减，成功才返回 `{ kind: 'retry' }`。压力触发（`pressure`）才是那个"温和、留尾部"的路径。两条路径的激进程度不同，是有意为之。

**误区四："总结调用是另起一段独立对话。"** 不是。它重放这场对话自己的 system prompt、tools、前导消息，把压缩指令作为最后一条 user 消息附上——是**上一次路由请求的真前缀**，因此能复用 provider 的 KV cache。把摘要器路由到另一个 provider/model，或压缩一个非头部区间，都会放弃这份复用。

**误区五："system prompt 也会被压缩。"** 不会。区间从第一个非 system 节点开始，surface 节点 0 的 system prompt 永不入选；折叠侧还有 `assertSystemHeadRewrite` 双重保护。压缩只缩减派生历史，绝不能碰系统提示词、工具 schema 或会话前缀——README 里明说这三者不在 surface 压缩的合同内。

**误区六："`/compact` 能指定压缩哪段，忙碌时可以排队。"** 都不能。命令是无参数的（`Usage: /compact (no arguments)`），忙碌时报 `busy` 而非排队；显式区间是程序化的 `compactRegion()` 路径。命令的成功结果通过 `sourceEventSeq` 关联到 `compaction/summary`，但命令生命周期本身（`command/run` / `command/done`）从不进入模型历史。

**误区七："图片卸载是临时的，换个更大预算的路由就回来了。"** 不会。`image/offload` 是一条永久决策，标记过的出现位置在所有后续请求、路由切换、resume、replay 里都不会自动恢复；恢复手段是占位文本里给出的只读路径。

## 7. 本章小结

1. 长对话的朴素解法（删旧消息 / 硬扛）要么破坏 append-only 与可重放性，要么溢出；DSH 用"surface 遮蔽 + 替换"在不删日志事实的前提下缩减派生历史。
2. 压缩是可选的**能力接缝**：`compaction`（Definition，`ctx.compaction`）+ `compaction-basic`（Provider）+ `command-compact` / 剪枝 / 图片卸载（Consumer）。
3. `CompactionEngine` 三个抽象方法：`compactIfNeeded`（自动）、`compactNow`（手动，低于阈值也可压）、`compactRegion`（显式区间）；区间按 surface 位置而非数值 seq 命名。
4. 四种 `compaction/*` 事件全部仅日志；`compaction/start`（锁）、`compaction/summary`（摘要与模型调用事实）、`compaction/end`（释放）、`compaction/prune`（剪枝影子价格）。
5. 影子价格协议：surface `replace` 由紧挨其前的计量事件定价，相邻是契约；正因为相邻，消费方无需维护每节点价格。
6. 三种触发：压力（`agent/pre-step`，温和、留尾部）、溢出恢复（`agent/request-error` 且 `CONTEXT_WINDOW_EXCEEDED`，绕过阈值、`retainTokens=0`、成功返回 `retry`）、手动（`/compact`，经 `runMaintenance` 串行化、`turn: null` 独立锁）。
7. 阈值公式 `floor(min(W × thresholdRatio, W − O − B))`，保留 `floor((W − O) × retainRatio)`；`W` 来自 adapter、`O` 来自请求信封 maxTokens 或 adapter 默认、`B` 来自配置（默认 65536）。
8. `summarize()` 是唯一子类钩子；默认 `summarizeWithLlm` 重放对话自身前缀、把压缩指令作为最后一条 user 消息，因而复用 provider 的 KV cache。
9. 一次压缩是日志内事务：`start`（锁）→ 摘要 → `summary`（审计）→ `user/message`（唯一 surface 变更）→ `end`（释放）；失败恰好一次关闭尝试，孤儿锁可检测。
10. 旧消息不删除：`replace` 只遮蔽，`deriveMessages()` 不再派生它们（模型遗忘），`isAppendSurfaceEvent` 仍读到原文（用户全存）。
11. 区间选择：从第一个非 system 节点开始（节点 0 的 system prompt 永不入选），保留 `retainTokens` 近期尾部，绝不拆开工具调用/结果对（`toolPairingBalancedBefore/After` 断言）。
12. 无模型两层：剪枝按 Unicode 码点做确定性头/中/尾裁剪（每条带 `compaction/prune` 影子价）；图片卸载经消息投影永久标记旧图片为 `offloaded`，占位文本给出附件名与只读路径。
13. `compaction-basic` 是 `agent/pre-step` / `agent/request-error` 的纯消费者与 `runMaintenance` 的实现者，不改循环一行代码（"Plugins, not loop changes"）。
14. 可重建性：`compaction/summary` 记录 provider/model/maxTokens/usage/`llmStreamCall`/`rawOutput`，那次一次性摘要请求可由日志 + 代码重建。
15. 触发数据源是 `ctx.tokenMeter`（从日志重放测量、零模型调用，注册 `tokenUsage` / `contextPressure` / `contextBreakdown` 三个 projection），与第 6 章接续。

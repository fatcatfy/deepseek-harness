# 第7章 工具系统：能力接缝与执行管线

## 本章导读

上一章（[第6章](第6章-模型调用-llm能力接缝与适配器.md)）我们讲了模型调用：请求怎么发出去、流式响应怎么回来。但一个只会说话的模型帮不了你干活——它还得能读文件、跑命令、搜代码。本章讲的就是 DSH 的**工具系统**（tools）：从模型吐出一段 JSON 指令，到磁盘真的发生变化、结果真的写回会话历史，中间这条完整的、被治理的执行管线。

你会学到四件核心的事：

1. **scoped 工具注册表**：工具怎么注册、怎么按 agent 作用域遮蔽、schema 怎么进入模型请求；
2. **三道事件闸门**：`tools/pre-execute` → `tools/execute` → `tools/post-execute` 这三个 waterfall 事件如何串成一条五阶段管线，审批、守卫、超时、结果改写各自挂在哪一级；
3. **能力接缝**（capability seam）：为什么"工具"只是一层薄薄的模型面 Consumer，真正的系统访问住在 provider 里——这是 DSH 全仓库最重要的一组架构决策；
4. **为什么工具不直接调系统 API**：沙箱、审批、接缝三层治理换来什么。

前置知识：第3章的 Cordis 服务注入（`ctx.get` / `Service`）、第4章的事件派发（waterfall 必须调 `next()`）、第5章的 agent loop。核心源码在 [`packages/core/tools/src/`](../../packages/core/tools/src/)，全程带着源码读。

## 从一个问题出发

假设你对 agent 说："把 `/tmp/draft.txt` 删了。"模型经过一轮推理，输出一个 tool call：

```json
{ "name": "bash", "arguments": "{\"command\": \"rm /tmp/draft.txt\", \"description\": \"Delete draft file\"}" }
```

一个课程作业级别的实现会在 `execute` 里直接 `child_process.exec(command)`——五行代码，跑通收工。但如果你要把这东西部署到一万台机器上、让陌生人往里输任务，这五行代码每一个字符都在问你：

- **参数可信吗？** `command` 是不是空串？`timeoutMs` 是不是负数？模型幻觉出来的参数长什么样？
- **允许吗？** 这台部署允许模型跑 `rm` 吗？这个 agent 的工作范围里有没有 `bash` 这个工具？要不要先问一下人类？
- **超时怎么办？** `rm` 卡在 NFS 挂载点上 40 分钟，模型请求是不是就挂 40 分钟？
- **并发安全吗？** 模型一口气发了三个工具调用，两个都在写同一个文件呢？
- **失败了怎么写回历史？** 会话日志里，调用和结果怎么配对？下个回合模型怎么知道上一步失败了？
- **能审计吗？** 半年后出了安全事故，你能回答"当时谁批准了这次删除"吗？
- **能换执行环境吗？** 明天你想让命令跑在远程沙箱而不是本机，要改几个工具？

把两种实现摆在一起，差距一目了然：

```ts
// 课程作业版：五个问号一个都没回答
ctx.tools.register({
  name: 'bash',
  async execute(args) {
    const { stdout } = await exec(args.command)   // 无校验、无审批、无超时、无取消
    return { content: [{ type: 'text', text: stdout }] }  // "返回值"与"模型面"混在一起
  },
})
```

```ts
// DSH 版（示意）：同样的 args，穿过一条被治理的管线
const result = await ctx.tools.execute({
  callId, name: 'bash', arguments, agent, signal,   // 调用方拥有取消权
})
// 内部依次：物化冻结参数 → pre-execute 决策(可 ask 人类) → 单调 guard
//         → around-dispatch(超时/重试) → tool.execute → 输出 schema 校验
//         → post-execute 决策(可 block) → 无损物化 → tools/result 事件
```

把这条问题链回答完整，你就得到了本章的主角——`ToolRuntime` 的五阶段执行管线。它大约一千行代码，每一行都在回答上面某一个问号。我们的路线是：先看"工具是什么"（数据结构），再看"怎么注册和进入请求"（注册表），然后走一遍完整管线（执行），最后上升到理论（能力接缝）和产品面（UI 呈现、PTC 模式）。

## 正文

### 7.1 工具是什么：ToolDefinition

打开 [`packages/core/tools/src/index.ts`](../../packages/core/tools/src/index.ts) L223。一个注册进系统的工具就是一个 `ToolDefinition`（工具定义）：

```ts
export interface ToolDefinition extends ToolSchema {
  readonly output: ToolOutputDefinition
  execute(args: unknown, exec: ToolRunContext): Promise<unknown>
  timeoutMs?: number
  isConcurrencySafe?(args: unknown): boolean
  presentCall?(args: unknown): ToolCallView | undefined
  presentResult?(args: unknown, result: ToolResult): ToolResultView | undefined
}
```

它 `extends ToolSchema`——后者是**模型面**的三件套 `{ name, description, parameters, deferLoading? }`（定义在 `dsh-llm`，第6章讲过）。`ToolDefinition` 在其之上叠加的是**宿主面**的字段，我们逐个看：

- **`output: ToolOutputDefinition`**（L213）——强制声明的规范输出。包含 `schema`（一个 `JsonSchemaNode`，约束工具返回的 JSON 值）、`render(args, value): ContentBlock[]`（把规范值投影成模型看到的 content）、可选的 `presentationMeta(args, value)`（给 UI 回放用的持久化元数据，见 7.9）。
- **`execute(args, exec)`**——工具体。注意契约：它**只返回 canonical JSON 值**（规范值），不返回 content、不返回卡片。返回值会先被快照、校验、冻结，再由 `output.render` 投影成模型面文本。`exec` 是 `ToolRunContext`（L418），携带不可变调用身份、`signal`（取消信号）以及两个能力方法：`deferContext(UserMessage)`（把附加上下文挂到自己这次调用的结果上，下一次请求才生效）和 `concludeTurn()`（标记当前回合就此终止）。
- **`timeoutMs`**——协作式超时预算。它**不进模型请求**：由 `dsh-tool-call-timeout-policy` 插件作为 `tools/execute` 包装器执行；声明它等于承诺"我的 execute 会转发 `exec.signal`，信号中止后能排干到静止"。
- **`isConcurrencySafe(args)`**——并行分类器。**只有精确返回 `true` 才可并行**；省略、抛异常、返回非 `true`，一律独占（fail-closed）。
- **`presentCall` / `presentResult`**——纯函数 UI 意图声明，7.9 节展开。

一个关键分层在这里就定型了：**模型看到的只有 name/description/parameters**。注册表在组装请求时用 `schemas()`（L1260）做显式白名单投影——`output`、`execute`、`timeoutMs`、`isConcurrencySafe`、presenter 全部不会泄漏到模型请求里。

还有两个配套类型值得记。`ToolResult`（L302）是 `presentResult` 收到的完成态投影：`{ content, isError, meta? }`——注意它**不含规范值 `value`**（那是执行期局部数据，不持久化），只含模型面 content 和回放用的 `meta`。`ToolExecutionResult`（L596）是管线的规范产出，一个可辨识联合：

```ts
export type ToolExecutionResult = ToolExecutionSuccess | ToolExecutionFailure
// 成功：{ isError: false, value, content, meta?, additionalContexts?, concludesTurn? }
// 失败：{ isError: true, error: { message, info? }, content, meta?, additionalContexts? }
```

失败永远不带 `value`，成功永远不带 `error`——类型系统强制了"失败即无值"这条纪律。

### 7.2 schema 如何进入请求，以及 defineTool 类型化 DSL

第9章会细讲请求组装，这里只看工具这一路。`ToolRuntime` 构造函数（L848）里有一行：

```ts
ctx.systemPrompt.tools(context => this.wireSchemas(context.scope))
```

也就是说注册表把 `wireSchemas`（L1008）挂进系统提示的 `tools` 区，每次组装请求时按**调用方作用域**重新求值：先经 `view(scope)` 解析该作用域可见的工具集（7.3），再逐个投影成 `ToolSchema`。所以"schema 进入请求"不是注册时拷贝一份，而是**每次请求从注册表现查现投影**——工具集变化下一次请求立刻生效。

写工具时你几乎不会手写 `ToolDefinition`，而是用 [`schema.ts`](../../packages/core/tools/src/schema.ts) L554 的类型化 DSL `defineTool`：

```ts
ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: {
    path: { type: 'string', required: true, description: 'Absolute path' },
    limit: { type: 'number' },
  },
  output: {
    schema: { type: 'string' },
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute(args, exec) {
    return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
  },
}))
```

（例子来自 [`docs/cookbook/adding-a-tool.md`](../../docs/cookbook/adding-a-tool.md)。）

它做三件事。第一，**参数 DSL**：`ParameterSchemaSpec`（L103）是一个隐式的开放对象根——每个属性是一个 `ValueSchemaSpec`（L85，支持 `string/number/integer/boolean/null/array/object/json/oneOf`），必填用 `required: true` 标注。第二，**类型推断**：`InferArgs<S>`（L175）/`InferValue<S>`（L172）从 schema 推导出 `execute` 的参数和返回值 TypeScript 类型，所以上面 `args.path` 是 `string` 而不是 `unknown`。第三，**双层校验**：

- `execute` 前：`defineTool` 生成的包装器先 `validateArgs`，违规抛 `ToolArgsError`（L461，code `INVALID_ARGS`）——这是**硬校验**；
- `presentCall`/`presentResult` 前：走**软校验**（L613/L619），旧日志里的参数对不上当前 schema 时返回 `undefined` 降级为通用卡片——display 永远不能让一次日志回放崩掉。

两个包装器的对照值得抄一遍（schema.ts L597-630，节选）：

```ts
async execute(args: unknown, exec: ToolRunContext): Promise<JsonValue> {
  const violations = validate(args)
  if (violations.length > 0) throw new ToolArgsError(violations)   // 硬：直接失败
  return userExecute(args as InferArgs<S>, exec) as Promise<JsonValue>
},
// ...
tool.presentCall = (args: unknown): ToolCallView | undefined => {
  if (validate(args).length > 0) return undefined                  // 软：降级通用卡
  return userPresentCall(args as InferArgs<S>)
}
```

同一个 `validate`，两条路径两种失败策略——**执行路径 fail loud，显示路径 fail soft**。这是所有"回放系统"的通用设计准则，值得收进你的工具箱。

另外，直接持有原始 JSON Schema 的工具（如 MCP 外部工具）也可以绕过 DSL 直接注册，但校验自理：`assertSupportedJsonSchema`（[json-schema.ts](../../packages/core/tools/src/json-schema.ts) L385）强制一个受支持的子集，`validateJsonSchemaValue`（L654）执行校验。不支持的关键字会**拒绝**而不是默默放过——"misconfiguration fails loud"原则的体现。

### 7.3 注册表：ToolRuntime 与 scoped 分层

`ToolRuntime`（[index.ts](../../packages/core/tools/src/index.ts) L807，`extends Service`，即 `ctx.tools`）是本章的中枢。注册：

```ts
register(definition: ToolDefinition): () => void
```

（L1063）。返回值是精确的注销函数——**注册即 effect**（第3章的 Cordis 约定），插件 fiber 销毁时工具自动注销，不存在"插件卸了工具还在"的悬空状态。

底层是 `ScopedLayers`（来自 `dsh-scope` 包）的两级分层：**全局层**（global）与 **agent 作用域层**（scoped）。可见性解析在 `view(scope)`（L1178）一次完成：

- 继承面 = 全局层 + 作用域链上所有祖先层，**近层遮蔽远层**（scoped 同名工具遮蔽 global——这正是"给某个 agent 换一个专用 bash"的机制，术语叫 shadowing）；
- `restrict({allow?, deny?})`（L1097）过滤的是**继承面**，多个限制取交集；作用域**自己**的注册不受自己的限制影响（否则子 agent 会失去它应答所依赖的机制工具）；被过滤掉的工具在提示和执行两个面都等价于不存在；
- 名字 `run_code` 无条件保留给 PTC transport（L1080 附近显式拒绝），任何注册都不许占用。

伴生 API 一表记：

| 方法 | 行号 | 作用 |
| --- | --- | --- |
| `register(def)` | L1063 | 注册工具（全局或调用方作用域），返回注销函数 |
| `restrict({allow,deny})` | L1097 | 对该作用域的继承工具集施加过滤器 |
| `guard(fn)` | L1136 | 注册单调否决守卫（7.4 第②阶段之后） |
| `presentAs(mode)` | L974 | 声明该作用域的呈现模式（native/ptc/both，7.10） |
| `schemas(scope)` | L1260 | 模型面 schema 白名单投影 |
| `get(name, scope)` | L1230 | 按作用域查定义 |
| `executionMode(exec)` | L1303 | 并行/独占分类（7.5） |

### 7.4 五阶段执行管线（本章主图）

现在走主线。入口是 `ToolRuntime.execute`（L1369），它把一次调用送过五个阶段。先看全景图，再逐段拆解：

```text
 模型输出 tool_calls（JSON 字符串，尚未解析）
   │  agent-loop 解析 → ToolExecutionInput { callId, name, arguments, agent, signal }
   ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ① createExecution（L1391）                                            │
│    snapshotJsonValue 一次物化参数 + deepFreeze；分配 opaque token       │
│    PTC 折叠检查：mode:'ptc' 下模型直呼非 run_code                       │
│      → UNKNOWN_TOOL（错误信息里指路"请在程序内调用"）                    │
└──────────────────────────────────────────────────────────────────────┘
   ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ② tools/pre-execute waterfall —— PreToolDecision（L607）              │
│      = allow | deny{reason,info?} | cancel | ask                      │
│    ask → serviceAsk()（L1727）→ ctx.get('approval').request()         │
│          缺审批服务 / 无 agent → 降级 deny                             │
│    此后 guardReason()（L1145）跑单调守卫：任何 guard 可否决，           │
│    没有 allow 结果，监听顺序无法翻案                                    │
└──────────────────────────────────────────────────────────────────────┘
   ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ③ tools/execute waterfall（around-dispatch，L1605）                    │
│    超时/重试/指标包装器；唯一可变的是 exec.signal                        │
│    → dispatchToolBody()（L1564）→ resolveExecution() 查定义            │
│    → tool.execute(args, exec)（fuseToolSignals 融合回 caller signal）  │
└──────────────────────────────────────────────────────────────────────┘
   ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ④ 成功归一 createSuccessResult（L1832）                                │
│    snapshotToolValue → validateJsonSchemaValue(output.schema)         │
│    （违规 → ToolOutputError / INVALID_TOOL_OUTPUT）                    │
│    → deepFreeze → output.render(args, value) 生成模型面 content        │
│    → 顶层调用再算 output.presentationMeta                              │
└──────────────────────────────────────────────────────────────────────┘
   ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ⑤ tools/post-execute waterfall —— PostToolDecision（L617）            │
│      = accept{content?|value?, additionalContexts?}                   │
│      | block{feedback, additionalContexts?}                           │
│    → finalizeContent → materializeFinalResult（L1886，无损+deepFreeze） │
│    → notifyResult（L1695，冻结 exec，emit tools/result）               │
└──────────────────────────────────────────────────────────────────────┘
   ▼
 agent-loop appendToolResult（tool-calls.ts L269）
   session.append('tool/result', …, { surfaceOp:'append', sourceEventSeqs:[callSeq] })
```

逐段说明。

**① `createExecution`（L1391）**：把调用方的 `ToolExecutionInput` 变成注册表拥有的 `ToolExecution`。三件事：参数经 `snapshotJsonValue` 一次递归物化（防御参数对象在执行中途被模型侧或 getter 篡改）再 `deepFreeze`；分配一个不透明的 `ToolExecutionToken`（L319，branded `symbol`，只用于身份关联）；PTC 折叠检查——`mode:'ptc'` 下模型直呼非 `run_code` 的名字，直接在这里终止，错误是 `ToolNotFoundError` 且带指路信息"call X from inside a run_code program instead"（这是源码里真实拼的错误文案）。注意折叠的调用**不进**策略管线：pre-execute、审批、guard 都看不到它——一个注定失败的调用不该被任何人"批准"。

**② `tools/pre-execute`**：第一道闸门，waterfall 事件（第4章：不调 `next()` 就是短路）。默认决策是 `allow`，任何监听器可以改写为四种 `PreToolDecision`（L607）之一：

```ts
export type PreToolDecision =
  | { kind: 'allow' }
  | { kind: 'deny'; reason: string; info?: ToolErrorInfo }
  | { kind: 'cancel' }
  | { kind: 'ask'; reason?: string; displayReason?: { readonly en: string; readonly [locale: string]: string } }
```

- `deny{reason, info?}`——否决，`reason` 会物化成模型可见的 `Error: <reason>`，可选 `info` 携带结构化错误身份（如 `AUTO_REVIEW_DENIED`）供下游路由；
- `cancel`——按"派发前取消"的规范结果收尾，不呈现为策略否决；
- `ask{reason?, displayReason?}`——交人类裁决。`serviceAsk()`（L1727）经 `ctx.get('approval')` 拿 `ApprovalService`，把请求发到人类面前。注意它是**机会主义消费**（opportunistic）：这个接缝不进 `static inject`——注入会把整个工具注册表扣在"必须存在审批服务"上，所以运行时现查，缺了就地降级。四种审批结果的映射（L1752-1766）：`allowed-once` → allow；`rejected` → deny "the user rejected tool X"；`cancelled` → deny 且标记审批取消；`unavailable` → deny "no approval channel is available"。三种非授权的 deny 理由各不相同，**让模型能区分"人类说不"和"没有审批通道"**。没有审批服务、或调用没有 agent（无处审计）时同样降级 deny——审批通道缺失不能变成静默放行。

waterfall 结束后（且仅当决策是 allow）跑 `guardReason()`：遍历全局层和作用域链上所有通过 `guard(fn)` 注册的守卫。`ToolGuard`（L731）的返回类型是 `string | undefined`——**没有 allow 这个返回值**，这是刻意的类型设计：任何 guard 都能否决，没有任何 guard（也没有任何监听顺序）能把别人的否决翻案。权限只减不增，这就是"单调"（monotonic）。

pre-execute 和 guard 这两道关卡像机场的边检和安检：边检（可扩展的 waterfall）决定放行、拒绝还是请你补手续（ask）；安检（guard）只有权把你拦下，无权给任何人补发签证。

**③ `tools/execute`**：around-dispatch waterfall。它的消费者不是策略而是**包装器**：超时（`dsh-tool-call-timeout-policy`）、重试、指标。包装器拿到的是 `ToolDispatchExecution`（L405）——唯一可变的字段是 `signal`，调用身份不可变。注册表在真正进 body 前用 `fuseToolSignals`（L1928）把包装器替换的信号和原始 caller 信号融合：**包装器能加 deadline，但不能把调用方的取消权弄丢**。最终 `dispatchToolBody()`（L1564）经 `resolveExecution()`（L1247，带 PTC 折叠判定）查到定义，标记 `bodyInvoked = true`，调用 `tool.execute(args, exec)`。

**④ 成功归一 `createSuccessResult`（L1832）**：body 的返回值在这里依次完成全部规范化步骤：`snapshotToolValue` 无损快照（非 JSON 直接 `ToolOutputError`）→ `validateJsonSchemaValue` 对照 `output.schema` 校验（违规同样是 `ToolOutputError`，code `INVALID_TOOL_OUTPUT`）→ `deepFreeze` → `output.render(args, value)` 生成模型面 content → 顶层调用（`exec.parent === undefined`）额外计算 `presentationMeta`。所以**模型永远看不到工具的原始返回值，看到的是通过校验后由 render 投影出的 content**。

**⑤ `tools/post-execute`**：最后一道闸门，接收 `(exec, result)`。决策类型 `PostToolDecision`（L617）：

```ts
export type PostToolDecision =
  | { kind: 'accept'; content?: ContentBlock[]; value?: never; additionalContexts?: UserMessage[] }
  | { kind: 'accept'; value: JsonValue; content?: never; additionalContexts?: UserMessage[] }
  | { kind: 'block'; feedback: ContentBlock[]; additionalContexts?: UserMessage[] }
```

- `accept` 可以替换 `content`（展示策略）**或** `value`（值策略——替换值会**重新走一遍** `createSuccessResult` 的校验与渲染），但**不能同时替换**（L1796 有显式 TypeError）；
- `block{feedback}` 把结果改写为携带纠正反馈的 `isError`——注意语义：这是"把纠错指令作为失败喂回模型"，不是静默吞掉；
- 两种决策都可附 `additionalContexts`。

随后 `finishScheduledExecution`（L1669）调用定义自有的 `finalizeContent`（若有），`materializeFinalResult`（L1886）做最终的无损物化 + `deepFreeze`，`notifyResult`（L1695）冻结 `exec` 对象并 emit `tools/result`——到此，一个不可变的、可安全持久化的最终结果诞生了。`tools/result` 是 `@mode emit` 观察事件：监听器只能看不能改，监听器抛异常被隔离（只记 warn）——**观察通道永远不是第二个改写通道**。

**取消语义**要单独记：取消到达时看 `bodyInvoked`——body 未启动 → `ABORTED_BEFORE_DISPATCH`（L486）；已启动 → `ABORTED`（L483），且 promise 会被排干到静止（同进程代码不能被硬杀，只能协作式排干）。一个精细的边界：审批等待期间（ask 的 await 中）到达的取消，会被折叠为 pre-dispatch 取消而不是半途而废的执行。**三类结构化异常**：`ToolNotFoundError`（`UNKNOWN_TOOL`）、`ToolOutputError`（`INVALID_TOOL_OUTPUT`）、`ToolArgsError`（`INVALID_ARGS`），都 extends `HarnessError`，让下游（重试、沙箱、回放）能按 code 路由。

**附加结果**（additional results）是工具往"下一次请求"塞信息的两条通道：

```ts
// 工具体内：把上下文挂到自己这次调用的结果上
exec.deferContext(createUserMessage({ content, source: { kind: 'my-plugin' } }))
// 或标记回合就此结束（只有成功的最终结果可携带）
exec.concludeTurn()
```

`deferContext` 的上下文、post-execute 决策的 `additionalContexts`、以及被 block 时**只保留决策显式提供的**上下文（工具体 defer 的会被丢弃——被否决的结果没有资格附言），都由 agent loop 的 FIFO 批量接收，在 `tool/result` 之后注入下一次请求。PTC 的 `run_code` 桥接层还会从嵌套结果**转发**这两个标记（ptc.ts L640-654）：子调用的图像结果、附加上下文、回合终止都会冒泡到外层——组合工具对嵌套结果的这两个标记是透传的。

### 7.5 调度：loop 侧视角（衔接第5章）

第5章讲过 agent loop 每步把模型的 tool_calls 交给 `executeToolCalls`（[tool-calls.ts](../../packages/core/agent-loop/src/tool-calls.ts) L60）。它按 `ctx.tools.executionMode(exec)`（L1303）的返回值把调用序列切组：

- `isConcurrencySafe(args) === true`（且后续调用也持续满足）→ 归入**并行池**，上限 `maxParallelToolCalls`（默认 10，[constants.ts](../../packages/core/agent-loop/src/constants.ts) L6 的 `DEFAULT_MAX_PARALLEL_TOOL_CALLS = 10`，可在 loop 配置改）；
- 其余 → **exclusive 屏障**：单独跑，且它的完整管线（含 post-execute）提交完之前，后面的调用不许开始。

两个容易忽略的细节：**先 append `tool/call` 再执行**（`appendToolCall` L263）——日志里调用永远先于结果，崩溃回放才成立；调度器通过符号 `TOOL_RUNTIME_SCHEDULER`（L480）拿注册表的分阶段接口 `prepare/dispatch/finalize/finish`，让"有序的策略阶段"和"可重叠的 body 执行"解耦：

| 阶段方法 | 对应管线段落 | 调度语义 |
| --- | --- | --- |
| `prepare(exec)` | ①②物化 + pre-execute + guard | 按模型顺序串行（下一个调用的策略等上一个策略落地） |
| `dispatch(exec)` | ③around + body | 并行池 / exclusive |
| `finalize(exec, result)` | ⑤post-execute + 物化 | 按模型顺序串行提交 |
| `finish(exec, result)` | ⑤尾段（跳过 post-execute 的终态） | 同上 |

这个符号是 `@internal`，不是插件扩展点——分阶段是调度器和注册表之间的**实现协议**，插件作者只有一个入口 `ctx.tools.execute()`。另外注意"提交按模型顺序"的精确含义（L147-161 的 `commitReady`）：结果只在**连续就绪前缀**上推进——第 3 个调用先完成也得等第 1、2 个提交完；`additionalContexts` 在提交点被 `acceptContext` 收进当前批次。中止时的兜底：已启动的调用排干并按序提交，未启动的补写合成错误结果（`appendSkippedToolCall` L250）——**日志里每个 `tool/call` 永远有配对的 `tool/result`**，回放才不会出现悬空调用。

### 7.6 写回会话（衔接第8章）

管线终点之后，loop 侧的 `appendToolResult`（L269）把结果落进会话日志：

```ts
const message = createToolResultMessage({ callId: block.id, content: result.content, isError: result.isError })
session.append('tool/result', {
  turn, step, message,
  ...result.error?.info ? { error: result.error.info } : {},
  ...result.meta !== undefined ? { meta: result.meta } : {},
}, { surfaceOp: 'append', sourceEventSeqs: [callSeq] })
```

事件 schema 在 [packages/core/session/src/types.ts](../../packages/core/session/src/types.ts) L361-385：`tool/call`（`callId`/`name`/`arguments` 原始字符串）与 `tool/result` 以 `callId` 配对；`meta` 字段是**工具私有的持久化 presentation payload**——核心不解释它，由生产工具在 `presentResult` 里读回，回放时原样复现卡片。`sourceEventSeqs: [callSeq]` 把结果事件关联到它的调用事件（第8章的溯源机制）。记住第8章的总规则在这里的具体化：**模型可见 ⟺ 已记录**——工具结果既然要进下一次请求，就必须是可从日志重建的事件。

### 7.7 能力接缝：本章的理论核心

到目前为止我们把工具当孤立个体看。现在换视角：DSH 里"加一个能力"从来不是"写一个工具"，而是设计一条**能力接缝**（capability seam）。[docs/glossary.md](../../docs/glossary.md) L7-9 的定义：一条接缝是"一个可替换的能力"（a swappable capability），含三个角色：

1. **Service Definition**（服务定义）：拥有 `ctx.<key>` 和词汇类型的 Cordis `Service`——抽象类（如 `ShellExecutor`）或具体注册表（如 `WebRuntime`），但**绝不是**一个 TypeScript `interface`；
2. **Service Provider**（服务提供者）：实现该服务的一个或多个插件；
3. **Consumer**（消费者）：注入并使用该服务的一个或多个插件，其中模型可见的工具是最典型的一类。

**一条接缝是完整的能力，不是单独某个角色；只有其中一个角色不叫接缝。**加一个能力 = 同时设计全部三个角色。一个包可以兼多角色（`dsh-user-approval` 一个包拥有审批接缝的 Definition 和实现），但只写 Consumer 不写接缝，就是伪接缝。

**样本一：dsh-shell。**打开 [packages/shell/shell/src/index.ts](../../packages/shell/shell/src/index.ts) L64：

```ts
export abstract class ShellExecutor extends Service {
  abstract resolve(request: ShellExecRequest): ShellExecSpec
  abstract execute(spec: ShellExecSpec): Promise<ShellExecution>
}
```

- Definition：这个抽象类即 `ctx.shell` 的全部接口；
- Provider：`bash-local`、`bash-sandbox`、`pwsh-local`、`pwsh-sandbox` 四个包，**每个组合恰好挂载一个**——挂两个会在加载期因重复服务注册报错（cordis 标准行为，fail loud）；
- Consumer：`tool-bash` / `tool-pwsh`（模型面工具）、persistent 变体、`shell-env`。

注意 `resolve(request): ShellExecSpec` + `execute(spec)` 这对方法的分工：**默认值填充与上限钳制是 provider 拥有的显式 `resolve` 一步，绝不藏在 `run()` 里的 `?? default`**。这是根 AGENTS.md 点名的仓库级模板（"the dsh-shell request/spec split is the template"）：调用方说"我要什么"（request），拥有方说"实际给什么"（spec），边界处显式默认，而不是执行路径上暗默认。

**样本二：dsh-llm 本身。**第6章讲过的模型适配器就是一条接缝——`ctx.llm` 是 Definition，各 provider 是实现，agent loop 是 Consumer。你已经见过它了。

**同构家族**（你以后读代码会反复遇到这个模式）：

| ctx 键 | Definition 包 | Provider 例 | 模型面 Consumer |
| --- | --- | --- | --- |
| `ctx.fs` | `dsh-fs` | `fs-local` / `fs-sandbox` | `tool-fs`（read/write/edit…） |
| `ctx.shell` | `dsh-shell` | `bash-local` / `bash-sandbox` / pwsh×2 | `tool-bash` / `tool-pwsh` |
| `ctx.web` | `dsh-web` | 搜索后端（DeepSeek 等）/ fetch | `tool-web` |
| `ctx.lsp` | `dsh-lsp` | 各语言服务器 | `tool-lsp` |
| `ctx.computerUse` / `ctx.browserUse` | computer-use / browser-use | 各 backend | provider 自带工具，独占命名注册 |
| `ctx.subagents` | subagent | — | 委派工具 |

`ctx.lsp` 是理解"provider 注册能力而非工具"（[packages/lsp/README.md](../../packages/lsp/README.md) L31："Providers register capabilities, not tools"）的最佳入口：语言服务器往 `ctx.lsp` 注册的是"我能做 definition/references/hover"这些**能力**，而模型面的 `lsp` 工具名、schema、提示词只属于 `tool-lsp` 一个包——换 provider 永远不改变模型请求的样子。

**接缝的威力**在于组合迁移：fs 与 subprocess 的 provider 共享同一个"执行世界"（execution world）。把执行世界指向远程沙箱，Bash、PTY、LSP 一起迁过去，**没有任何 provider 需要分叉**。这是 7.8 节论证的地基。

最后给你一个实用的判断清单——什么时候**该**开一条接缝、什么时候不该：

- 该开：同一个能力会有多个实现（本机/沙箱/远程、不同后端），或模型面工具与实现会独立演进；
- 该开：治理（审批、沙箱、策略）必须作用于"所有系统访问"而非个别工具；
- 不该开：一次性、单实现、无消费者复用的能力——直接写在工具的 execute 里即可，为它造三角色是过度设计（接缝是能力级别的投资，不是代码风格）。

顺带解释一个你可能已经疑惑的现象：`ToolRuntime` 自己也是一条接缝——Definition 是 `ctx.tools`（注册表本体），Provider 是所有 `tool-*` 包（往注册表里注册），Consumer 是 agent loop（`execute`）和 API 代理（`schemas`）。它和 `ctx.shell` 的区别只在角色形状：一个是"注册表型"接缝（多方贡献、按名解析），一个是"抽象类型"接缝（恰好一个实现）。glossary 里"或一个具体注册表如 `WebRuntime`"说的就是前者。

### 7.8 为什么工具不直接调系统 API

学生问得最多的问题："`tool-bash` 的 execute 里直接 `exec(command)` 不就行了，为什么要经 `ctx.shell`，还分什么 local/sandbox？"分三层回答。

**第一层：治理必须住在调用路径上。**回看 7.4 的管线：`tools/pre-execute` 里挂权限策略，`ask` 接人类审批，`guard` 兜底否决，`tools/execute` 挂超时，`tools/result` 挂审计。这些治理点存在的前提，是**所有系统访问都流经同一条管线**。如果工具自己 `import { exec } from 'node:child_process'`，这条路就绕过了管线——超时、审批、审计、并发控制全部失效，而且**从外部看不出来**（工具名没变、schema 没变）。DSH 的答案是把"模型可见的工具"和"实际系统访问"拆成两个角色：工具是薄 Consumer，只负责把模型参数翻译成 provider request；真正的系统访问在 provider 里，被 `sandbox`（进程约束：`bash-sandbox`/`fs-sandbox` 按沙箱模式围栏写操作、拒绝越界路径段编码的遍历攻击）、`approval`（`ask` 决策路由到人类）、permission presets、路径治理层层看管。

**第二层：执行世界必须可替换。**"本机执行"和"沙箱执行"应该是**部署期的组合选择**，不是代码分支。接缝之下，`tool-bash` 写的是 `ctx.shell.execute(spec)`，至于是 `bash-local` 还是 `bash-sandbox` 在跑，工具一无所知——也不需要知道。明天你要加一个"远程容器执行" provider，只写一个新 Provider 包，所有工具零改动。

**第三层：审计要求一切可回放。**第8章的会话日志记录了每一次 `tool/call`/`tool/result`；配合管线各阶段的决策（deny 的 reason、ask 的审批记录、guard 的否决理由），事故复盘回答的是"当时谁批准的、为什么放行"。散落的直接 API 调用产生不了这些事件。

一句话总结：**工具是模型的世界，provider 是机器的世界，接缝是两者之间有守卫的门。**额外收益：审批、超时、守卫是统一挂载点——新工具自动获得全部治理，不需要每个工具作者重新发明一遍。

### 7.9 UI 呈现：纯函数 presenter 与浏览器侧派生

工具执行要给人看。设计约束一句话：**Host 侧 presenters 是纯函数；Web 侧卡片从原始事件派生。**

词汇表在 [presentation.ts](../../packages/core/tools/src/presentation.ts)：挂起态 `ToolCallView`（L46）= `GenericCallView | TerminalCallView | DiffCallView`（通用卡片 / 终端卡片 / 行内 diff 卡片）；完成态 `ToolResultView`（L140）= `Generic | Terminal | Diff | Search | Read | Web` 六种。全部是 `card` 字段判别的可辨识联合（switch on discriminant tags，仓库级约定）。工具经 `presentCall`/`presentResult` 声明"我这张卡长什么样"。

一个真实样本（tool-bash 的 `presentBashResult`，L130-143）：

```ts
function presentBashResult(args: unknown, result: ToolResult): ToolResultView | undefined {
  const block = result.content.length === 1 ? result.content[0] : undefined
  if (block === undefined || block.type !== 'text') return undefined
  const isBackground = …  // 后台/被转后台/出错：没有退出状态
  if (isBackground || isPromoted || result.isError) {
    return { card: 'generic', content: [{ type: 'text', text: `\`\`\`console\n…` }] }
  }
  const { body, ...exit } = parseExitStatus(raw)   // 拆出退出标记做"退出状态药丸"
  return { card: 'terminal', output: body, ...exit }
}
```

同一个工具按结果形态分叉成两种完成卡；`kind`（`ToolCallKind`，L15：`read/edit/delete/move/search/execute/fetch/other`）只负责给通用卡挑图标。注意 presenter 的一个常见困境在这里的解法：**调用时拿不到旧文件内容**，所以 `write` 的调用态 diff `oldText` 是 `null`（新文件/覆盖），真正的上下文 hunk 要等 `presentationMeta` 在结果里补——纯函数约束直接塑造了 API 的形状。

**纯函数是硬约束**：presenter 会在实时流式和日志回放两条路径上都跑，所以禁止 I/O、禁止读会话状态、禁时钟、禁随机——只依赖 `args`（和结果）。这两条路径 + `presentationMeta` 产物（持久化在 `tool/result` 的 `meta` 字段），保证回放时卡片和当年一模一样。presenter 像一张设计图纸：工具只声明意图，两端（Host 桥接、回放引擎）各自照图施工。

浏览器侧则走**另一条完全独立**的路线：[`packages/client/ui-tool`](../../packages/client/ui-tool/README.md) **不消费** presenter 值——Host 的 `presentCall`/`presentResult` 从不进入浏览器。Web 卡片由原始 `tool/call`/`tool/result` 事件 + 持久化的 `result.meta` 在客户端**派生**，按 wire 工具名经 keyed slot `tool.call.toolview` 分发（契约在 [packages/client/ui-tool/src/client/contract/slots.ts](../../packages/client/ui-tool/src/client/contract/slots.ts) L26）：

```ts
ctx.slots.inject('tool.call.toolview', () =>
  ctx.slots.register({ name: 'tool.call.toolview', key: '<wire tool name>' }, BusinessToolRow))
```

未注册的名字走通用 fallback 卡；PTC subCalls 递归渲染子调用树。为什么这么设计？因为浏览器拿不到 Host 进程里的函数，能拿到的只有事件流和 JSON 元数据——"从事件派生"是唯一能跨进程边界、且回放安全的方案。

最后一块拼图是 [agent-tool-presentation](../../packages/core/agent-tool-presentation/src/index.ts)（L59）：agent preset 用一行 `mode` 配置声明该作用域的呈现模式，插件内部调 `ctx.tools.presentAs('native' | 'ptc' | 'both')`（L64/L70）——这就是 7.10 的入口。

### 7.10 PTC 模式：同一条管线的另一种呈现

PTC（Program-Tool Calls）模式下，模型**不再看到一堆工具 schema**，而是只看到一个 `run_code` 工具加一段生成的 SDK（[ptc.ts](../../packages/core/tools/src/ptc.ts) 的 `createRunCodeTool` L334；`Config.mode: 'native' | 'ptc' | 'both'`，[index.ts](../../packages/core/tools/src/index.ts) L674）。模型写一段 TypeScript/Python 程序（`code` 参数），在程序里 `await tools.bash({...})` 这样调用工具——SDK 由 `renderToolsSdk`（ts-types.ts）/`renderToolsSdkPy`（py-types.ts）从可见工具的 schema 生成，连类型都推好。

关键认知：**PTC 不是一套新的工具系统**。SDK 子分发（sub-dispatch）携带 parent token（`exec.parent`）走**同一条**五阶段管线——同样的 pre-execute、审批、guard、post-execute。差别只在两处呈现：

- 模型面：schema 列表折叠成 `run_code` + SDK（7.4 第①步的折叠检查就为它服务：模型直呼原生工具名 → `UNKNOWN_TOOL` 带指路）；提示词里还有一条 `PTC_ONLY_INSTRUCTION`（L59）把规则**事先**告诉模型，而不是等它撞上错误——"模型只能靠被拒才能发现的规则，纠错太晚"；
- 日志面：每次子分发记 `tool/ptc-dispatch` 事件，且 `tools/ptc-dispatch-log` waterfall 可以改写**持久日志副本**（例如超大文本结果换成预览 + 定位器——spill 策略的挂接点），程序本身拿到的完整值和模型看到的外层结果都不受影响。

`run_code` 自己的参数也值得一瞥（ptc.ts L345-353 + `RUN_CODE_CONTROLS` L109）：`description`（必填，5-10 词，UI 标签用）、`code`（必填，异步函数体）、按运行时能力出现的 `timeoutMs` / `sandbox_permissions` / `justification`（沙箱升降级审批，和 bash 同一套 `approveEscalation` 机制）。子调用的并发由 `maxParallelSubCalls`（默认 10）约束，且沿用原生调度契约——`run_code` 程序内部的调度器（ptc.ts L468-522 的驱动循环）和 loop 侧一样：有序 prepare、可重叠 body、按提交序 finalize，exclusive 调用形成屏障。**两套调度器共享同一套语义，因为它们消费的是同一个 `TOOL_RUNTIME_SCHEDULER`**。

`preset ptc` 预设就是这个形态的产品化。给工具作者的好消息（cookbook 原话）：**PTC 模式免费到达你的工具**——可见工具自动成为 SDK 里的 `await tools.<name>()`，无需任何集成。

### 7.11 工具包清单（模型面）

按接缝分组过一遍模型面全家族（全量见生成的 [docs/tool-catalog.md](../../docs/tool-catalog.md)）：

- **shell 组**：`bash` / `pwsh` 及 persistent 变体。`bash` 支持 `run_in_background`（需 `ctx.jobs`）、`promoteOnTimeout`（超时转后台而不是杀）、`sandbox_permissions`/`justification`（沙箱升降级需审批）；
- **fs 组**：`read` / `read_image` / `write` / `edit`、搜索 `glob` / `grep`（内置 ripgrep 二进制）、`str_replace_editor`。`fs-observation-policy` 插件执行"读后才许写"（read-before-edit）策略；
- **web 组**：`web_search`（多搜索后端）/ `web_fetch`（匿名 HTTP(S) 抓取）；
- **lsp 组**：`lsp`（definition/references/implementations/hover）；
- **computer-use / browser-use**：provider 自带，独占命名注册；
- **交付与协作**：deliverables 的 `present`（声明交付文件）、`todo_write`、`ask_user_question`；
- **其他**：`job_output`/`job_kill`/`job_list`（后台作业）、`schedule`、`skill`、`workflow`、subagent、`session_search` 等。

deliverables 值得一句展开：`tool-present` 声明交付文件（需 `ctx.tools` + `ctx.fs`）；`workspace-changes` 监听 session 事件、在每个顶层 turn 汇总 git 工作树快照变更并追加 `workspace/changes` 事件；Web 端 `ui-deliverables` 在回合尾渲染——这是"工具系统 + 会话事件 + UI 派生"三个机制的完整闭环样本。

## 常见误区

**误区一："工具的返回值直接给模型。"** 错。`execute` 只返回 canonical JSON 值；它要先过 `snapshotToolValue` 无损快照、`validateJsonSchemaValue(output.schema)` 校验、`deepFreeze`，再由 `output.render(args, value)` 投影成 `ContentBlock[]` 才成为模型面 content。违规返回值不是"原样透传"，而是 `ToolOutputError`（`INVALID_TOOL_OUTPUT`）错误结果。这个设计让"程序化值"和"模型面叙述"彻底解耦——PTC 程序拿规范值，模型看 render 文本。

**误区二："guard 链里后注册的监听可以 allow 翻案。"** 错，而且方向反了。`ToolGuard` 的返回类型是 `string | undefined`——**根本没有 allow 这个结果**。任何 guard 能否决，没有任何机制能翻案，监听顺序只影响"谁先否决"，不影响"是否被否决"。权限单调递减是安全设计，不是实现偷懒。同理，pre-execute 的 `ask` 在审批服务缺失时**降级为 deny**，不会静默放行。

**误区三："`presentCall` 在浏览器里跑。"** 错。presenter 是 Host 进程里的纯函数（live 流式与日志回放双跑）；浏览器侧 `ui-tool` 根本不消费 presenter 值，卡片由原始 `tool/call`/`tool/result` 事件 + 持久化 `result.meta` 派生，按 wire 工具名经 `tool.call.toolview` keyed slot 分发。Host 与 Client 是两套独立渲染路线，共享的只有事件与 `meta` 数据。

**误区四："`isConcurrencySafe` 默认并行，标注 false 才独占。"** 错，恰恰相反。只有**精确返回 `true`** 才进并行池；省略该方法、抛异常、返回非 `true`（包括 truthy 的 1/"yes"）一律 exclusive。调度是 fail-closed 的：不确定就当不安全。`defineTool` 的包装器还会在分类前先跑参数校验，参数不合法直接按 false 处理。

**误区五："PTC 是第二套工具系统。"** 错。PTC 只是同一管线的另一种**呈现/分发形态**：模型面从 schema 列表折叠为 `run_code` + 生成 SDK，但 SDK 子分发携带 parent token 走同一条 pre-execute → guard → execute → post-execute 管线，受同样的审批、沙箱、超时治理。判断"是不是新系统"的试金石：治理点有没有被绕过——PTC 一个都没有。

**练习 4（写伪代码）**：为一个假想的 `now` 工具写 `defineTool` 伪代码（返回当前时间）。要求：无参数；输出 schema 是 `{ type: 'object', additionalProperties: false, properties: { iso: { type: 'string', required: true }, epochMs: { type: 'integer', required: true } } }`；`render` 把它拼成一行人类可读文本；想一想 `presentCall` 需不需要（提示：挂起态没有任何可显示的结果数据）。参考答案骨架：

```ts
ctx.tools.register(defineTool({
  name: 'now',
  description: 'Get the current time. No parameters.',
  parameters: {},                                    // 无参数也是显式的空对象根
  output: {
    schema: {
      type: 'object', additionalProperties: false,
      properties: {
        iso: { type: 'string', required: true },
        epochMs: { type: 'integer', required: true },
      },
    },
    render: (_args, v) => [{ type: 'text', text: `Current time: ${v.iso} (${v.epochMs} ms since epoch)` }],
  },
  isConcurrencySafe: () => true,                     // 无共享状态，读时钟可并行
  async execute(_args, exec) {
    exec.signal.throwIfAborted()                     // 协作式取消：能停就停
    const date = new Date()
    return { iso: date.toISOString(), epochMs: date.getTime() }
  },
  // 不写 presentCall：挂起态没有可展示数据，通用卡（标题 = "now"）即可
  // 不写 timeoutMs / presentationMeta：本地同步计算，无超时与回放元数据需求
}))
```

写完自查三个问题：它该并行吗（无状态 → `isConcurrencySafe` 返回 `true` 合理）？它需要 `timeoutMs` 吗（不需要——本地同步计算）？它的结果如何进会话日志（7.6 的 `meta` 什么时候才有值——只有声明了 `presentationMeta` 且是顶层调用才有）？

## 本章小结

1. 工具 = `ToolDefinition`：模型面三件套（name/description/parameters）+ 强制 `output` 声明 + 只返回 canonical JSON 值的 `execute` + 宿主面元数据（`timeoutMs`/`isConcurrencySafe`）+ 纯函数 UI 意图（`presentCall`/`presentResult`）。
2. schema 进入请求是**每次组装现查现投影**：`wireSchemas` 挂在 `ctx.systemPrompt.tools`，按调用方作用域解析可见集后做白名单投影，`output`/回调永不泄漏。
3. `defineTool` 提供 `ParameterSchemaSpec`/`ValueSchemaSpec` 双 DSL + `InferArgs`/`InferValue` 类型推断；execute 前硬校验（`ToolArgsError`/`INVALID_ARGS`），presenter 前软校验（降级通用卡片，回放永不崩）。
4. 注册表 `ToolRuntime`（`ctx.tools`）基于 `ScopedLayers` 两级分层：scoped 遮蔽 global，`restrict` 过滤继承面且取交集，注册即 effect 自动注销，`run_code` 名字保留。
5. 五阶段管线：物化冻结（①）→ pre-execute 决策 + 单调 guard（②）→ around-dispatch + body（③）→ 成功归一校验渲染（④）→ post-execute 决策 + 物化 + `tools/result`（⑤）。
6. 决策类型：`PreToolDecision = allow | deny | cancel | ask`（ask 经 ApprovalService，缺服务降级 deny）；`PostToolDecision = accept | block`。
7. guard 单调：返回类型没有 allow，任何 guard 可否决、无人可翻案——权限只减不增。
8. 取消语义二分：body 未启动 → `ABORTED_BEFORE_DISPATCH`，已启动 → `ABORTED` 且排干到静止；三类结构化错误 `UNKNOWN_TOOL` / `INVALID_TOOL_OUTPUT` / `INVALID_ARGS`。
9. 调度在 loop 侧：仅 `isConcurrencySafe === true` 进并行池（默认上限 10），其余 exclusive 屏障；先 append `tool/call` 再执行，结果按模型顺序提交。
10. 写回会话以 `callId` 配对 `tool/call`/`tool/result`，`meta` 持久化 presentation payload，`sourceEventSeqs` 溯源调用事件。
11. 能力接缝 = Service Definition + Provider + Consumer 三角色全set；加能力 = 设计全部三个；`dsh-shell` 的 `resolve(request): Spec` + `execute(spec)` 是 request/spec 拆分的仓库模板。
12. 工具不直接调系统 API：薄 Consumer + provider 内真实访问，换来沙箱/审批/路径治理的统一挂载、可替换执行世界、全链路可审计。
13. UI 双路线：Host presenter 纯函数（禁 I/O/时钟/随机，`presentationMeta` 持久化）；浏览器从原始事件 + `result.meta` 派生，经 `tool.call.toolview` keyed slot 分发，未注册走通用卡。
14. PTC 是同一管线的另一种呈现：模型只见 `run_code` + 生成 SDK，子分发携 parent token 走全管线，`tools/ptc-dispatch-log` 只改持久日志副本。
